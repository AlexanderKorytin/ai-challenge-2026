# День 3 (2026-09-02)

## Статус

`Executing`

## Задание

Взять одну задачу (логическую, алгоритмическую или аналитическую) и решить её через API
четырьмя способами:

1. прямой ответ без дополнительных инструкций;
2. с инструкцией «решай пошагово»;
3. модель сначала составляет промпт для решения задачи, затем этим промптом задача решается;
4. в промпте заведена группа экспертов (например аналитик, инженер, критик), решение
   получается от каждого.

Сравнить: отличаются ли ответы и какой способ дал наиболее точный результат.

Результат — несколько решений одной задачи и их сравнение.

Наша постановка: задача — короткая логическая загадка, ответ на которую однозначен и легко
проверяется. Само условие и эталонный ответ лежат в `data/` и в репозиторий не попадают:
инструмент от задачи не зависит, её меняют одним файлом.

## Ход работы

### Research

Разобрали, где в задании ловушки.

**Режим рассуждений DeepSeek включён по умолчанию.** Значит «прямой ответ без инструкций» на
самом деле уже пошаговый — модель разворачивает рассуждение внутри себя. Если ставить опыт на
умолчаниях, способы 1 и 2 сольются, и вывод «разницы нет» будет означать лишь то, что мерили
не то. Поэтому базовые клетки идут с выключенными рассуждениями, а к способу 2 добавлена
**контрольная клетка**: та же инструкция «решай пошагово», но без встроенных рассуждений.
Тогда сравнение читается однозначно: 1 против контрольной — вклад формулировки промпта,
контрольная против 2 — вклад рассуждений.

**Модель не может «поднять агентов» сама** — у неё нет доступа к API. Поэтому группа
экспертов сделана честно: наш код шлёт независимые запросы, каждый со своей системной
инструкцией, агенты не видят ответов друг друга, и только потом ведущий получает все ответы
разом и сводит их.

**Задача должна быть по силам, но не решаться сходу.** Первая попытка это показала: на
хрестоматийной загадке модель отвечала верно 12 раз из 12 даже самым слабым способом —
сравнивать было бы нечего. Ни переформулировка, ни переход на модель послабее не помогли:
такие загадки модель знает наизусть. Задачу заменили на ту, где ответ требует сменить уровень
рассмотрения — и базовый способ на ней проваливается.

**Точность нужно чем-то мерить.** Ответы здесь текстовые, поэтому вердикты выносит отдельный
судья — дешёвый запрос с выключенными рассуждениями и `temperature: 0`, сверяющий ответ с
эталоном. Судью проверяем глазами, прежде чем верить его цифрам.

### Plan

Пять клеток замера, каждая — профиль harness:

| Профиль | Способ | Что задаёт |
|---|---|---|
| `free` | 1 | ничего: голый вопрос, рассуждения выключены |
| `chain_of_thought_nothinking` | контроль | инструкция «решай пошагово», рассуждения выключены |
| `chain_of_thought` | 2 | та же инструкция при включённых рассуждениях |
| `meta_prompting` | 3 | шаг 1 — модель составляет промпт, шаг 2 — решает им задачу |
| `multiprompting` | 4 | четыре эксперта отвечают независимо, ведущий сводит их ответы в таблицу |

Эксперты группы: `analyst` (формализует условие), `skeptic` (ищет невысказанные допущения),
`critic` (работает на опровержение очевидного ответа), `linguist` (разбирает условие как
текст — синонимы, формы, игра слов).

Ведущий группы намеренно не выносит своего вердикта: он сводит ответы экспертов в таблицу
«эксперт — ответ — ключевой довод», как и просит задание («решение от каждого»). Плата за это
— итог группы нельзя сравнивать по точности с остальными способами напрямую, поэтому судья
размечает **ответ каждого эксперта отдельно**, и в сводке появляется вторая величина: в
скольких прогонах верный ответ нашёл хотя бы один эксперт. «Группа знала ответ» и «группа его
выдала» — разные вещи, и разница между этими двумя числами и есть самое интересное в
способе 4.

Режим рассуждений задаётся флагом `--thinking on|off` и переопределяет профиль вместе со
всеми, кого он поднимает: одна и та же группа с рассуждениями и без даёт разные результаты, и
сравнивать её со способом 2 честно только при одинаковом режиме.

Каждая клетка прогоняется серией: одного ответа мало — у API нет `seed`, и на задаче с
подвохом модель отвечает то так, то этак. Кроме доли верных ответов считаем цену: сколько
запросов, токенов и секунд стоил один ответ.

### Executing

**Доработки harness (ветка `main`, ссылки на фиксации в отчёте).** Задание потребовало от
инструмента того, чего в нём не было:

- **группа агентов** — профиль со списком `agents` поднимает агентов: вопрос уходит каждому со
  своей системной инструкцией, запросы идут одновременно, ответ каждого приходит на свой
  экран, ведущий сводит их в главном. Экраны переключаются кликом по вкладке, `Alt+N` или
  `Shift+←/→`; экраны агентов — только для чтения;
- **рабочие экраны** — профиль со списком `screens` раскладывает приём в несколько шагов по
  вкладкам: у каждого экрана своя инструкция, своя вводная и своя ветка разговора. Так сделан
  способ 3: на первом экране модель составляет промпт, на втором этот промпт применяется;
- **заготовка ввода** (`prefill`) — профиль может положить готовый текст в строку ввода;
- **мышь по `F2`** — полноэкранный режим перехватывал мышь целиком, и текст в логе нельзя
  было выделить для копирования. Теперь мышь можно отдать терминалу и вернуть обратно;
- попутно нашлась ошибка: подстановка `$переменных` в инструкции работала только с латинскими
  именами, `$слов` молча оставался в тексте.

**Замерная часть (`week_1/day_3/`).** Способ определяется по самому профилю, поэтому серия не
знает про «четыре способа»: обычный профиль — один запрос, профиль со `screens` — цепочка,
профиль с `agents` — группа.

```bash
cd week_1/day_3
uv run python -m reasoning.series --runs 20     # прогнать все способы
uv run python -m reasoning.judge                # разметить ответы по эталону
uv run python -m reasoning.judge --show free    # прочитать ответы и вердикты глазами
uv run python -m reasoning.web                  # страница сравнения на 127.0.0.1:8766
```

Промпт способа 3 составляется заново в каждом прогоне: иначе мы измеряли бы один удачно или
неудачно вышедший промпт, а не приём целиком.

### Validation

Модель `deepseek-v4-pro`, 8–12 прогонов на клетку.

| Способ | Верных (итог) | Верных у экспертов | Запросов | Токенов | Сек/ответ |
|---|---|---|---|---|---|
| 1. Без инструкций | 0/12 (0%) | — | 12 | 13 209 | 24,5 |
| 2к. «Пошагово», рассуждения выключены | 1/8 (12%) | — | 8 | 5 367 | 12,1 |
| 2. «Пошагово» + рассуждения | 6/8 (75%) | — | 8 | 33 258 | 68,3 |
| 3. Промпт от самой модели | 2/8 (25%) | — | 16 | 13 146 | 28,0 |
| 4. Группа, рассуждения выключены | таблица | 3/8 | 40 | 52 789 | 36,0 |
| 4. Группа + рассуждения | 5/8 (62%) | 8/8 | 40 | 226 747 | 197,5 |

У группы «верных (итог)» — доля прогонов, где судья принял сводную таблицу как ответ; ведущий
по инструкции ответа не выбирает, поэтому величина показывает скорее единодушие экспертов, чем
правильность. Содержательная величина для группы — соседняя колонка.

**Сверка судьи.** Ответы просмотрены глазами (`--show`). Вердикты обоснованы: в отказах судья
прямо называет причину — «описывает оригами и шитьё, а не игру слов», «перечисляет несколько
версий и не выбирает одну». Ошибок разметки не нашлось; ограничение у судьи одно и оно
известно — на сводной таблице он оценивает не правильность разгадки, а решительность ответа.

**Побочная находка.** Эксперты сами нашли второе словесное решение: «рубашка» → «пташка»
(замена начала слова). Эталон описывает путь через «сорочку», поэтому судья такие ответы не
засчитывает — это не ошибка разметки, а граница эталона.

## Результат

**Ответы способов различаются радикально — от 0% до 75% верных.** На задаче, где нужно
догадаться сменить уровень рассмотрения, голый вопрос не даёт ничего: модель двенадцать раз из
двенадцати обстоятельно объясняет, как сложить рубашку оригами.

**Инструкция «решай пошагово» сама по себе почти не помогает.** Без встроенных рассуждений она
подняла результат с 0/12 до 1/8 — в пределах случайности. Весь скачок до 6/8 дали именно
рассуждения модели. Вывод, важный для сегодняшнего дня: приём, который в старых моделях был
главным рычагом, теперь в основном уже встроен, и просить о нём словами почти нечего — надо
включать `thinking`.

**Промпт, составленный самой моделью, работает лучше короткой инструкции** (2/8 против 1/8 при
одинаково выключенных рассуждениях) — модель сама себе велит определить тип задачи, проверить
омонимы и игру слов, то есть пишет то, чего в «решай пошагово» нет. Но стоит это вдвое дороже
по запросам и всё равно проигрывает включённым рассуждениям.

**Группа экспертов надёжнее всех находит разгадку и хуже всех её выдаёт.** С рассуждениями
верный ответ был у кого-то из экспертов в 8 прогонах из 8 — благодаря ролям, которые смотрят на
условие под разными углами (знаток русского языка и скептик угадывали, аналитик и критик
уходили в рукоделие). Но ведущий по инструкции сводит ответы в таблицу и не выбирает победителя,
поэтому итог группы принят лишь в 5 прогонах из 8. Разница между 8/8 и 5/8 — это в чистом виде
цена агрегации: коллектив знал ответ, но не назвал его.

**Цена.** Группа с рассуждениями стоила 226 747 токенов и 197 секунд на ответ против 33 258 и 68
секунд у одной модели с рассуждениями — в семь раз дороже при более низкой доле принятых итогов.
Практический вывод: если задача с подвохом, дешевле включить рассуждения одной модели; группа
оправдана там, где важно не пропустить редкую гипотезу, и при условии, что кто-то — человек или
ведущий с правом решать — эту гипотезу из таблицы выберет.
