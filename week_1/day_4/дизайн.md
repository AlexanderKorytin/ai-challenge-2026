# Дизайн: день 4, температура

## Задача и видение

Условие: один и тот же запрос при `temperature` = 0, 0.7 и 1.2; сравнить ответы по точности,
креативности и разнообразию; сформулировать, для каких задач подходит каждая настройка.
Результат — примеры ответов и выводы. Формат — видео и код.

Видение пользователя: страница, где вверху переключателями выбирается вопрос, ниже показан его
текст, ниже таблица — столбцы по температурам, строки по прогонам. Нажатие кнопки запускает
прогон, таблица заполняется по мере ответов. В видео: выбрали вопрос, нажали, дождались,
перешли к следующему. Выводы по увиденному пользователь делает сам.

## Что решили и почему

### Рассуждения выключаются явно

Режим рассуждений DeepSeek включён по умолчанию и **отключает влияние `temperature`**
(`openspec/specs/params/spec.md`, требование «Параметры, обесценённые режимом рассуждений,
помечаются»). Без явного `thinking: disabled` три температуры разошлись бы только случайным
шумом, и вывод «температура не влияет» описывал бы режим рассуждений, а не температуру.
Проверяется на пробном прогоне до съёмки.

### Крутим ровно одну ручку

`top_p` не задаётся вовсе. Температура меняет форму распределения, `top_p` — ширину набора
кандидатов; при одновременном изменении непонятно, чей вклад в разброс. Модель
`deepseek-v4-flash` — умолчание инструмента (`myharness/config.py`), на ней работал день 3;
`max_tokens` фиксирован, `response_format` — обычный текст.

Отвергнут `json_object`: режим JSON сам по себе сушит и укорачивает текст внутри полей, и
эффект формата смешался бы с эффектом температуры. Для кода добавилось бы экранирование
переносов.

### Три прогона на клетку, а не один

Разнообразие — свойство набора ответов, а не одного ответа. Параметра `seed` у DeepSeek нет,
поэтому даже при `temperature = 0` повторяемость не гарантирована. Один ответ на температуру
не позволил бы судить о разнообразии в принципе.

Три прогона — это наблюдение, а не статистика: разница «3 из 3 против 2 из 3» неотличима от
случайности. Опираться можно на полные разрывы и на совпадение направления сразу на нескольких
вопросах.

### Ответ из двух частей, разметка разная для разных вопросов

Свободная часть — по ней видно разнообразие и стиль; финальная строка по строгой форме — по ней
читается точность. Единой разметки на все вопросы нет: там, где ответ и есть полезная нагрузка
(метафора, код), отдельный маркер мешает — в метафоре «не более двух предложений» он стал бы
третьим предложением.

Чем жёстче форма, тем меньше видна температура: доведя до предела, ответ одним числом совпал бы
при всех трёх температурах и дал бы ложный вывод. Поэтому форма дисциплинирует только последнюю
строку.

### Вопрос про вымышленного поэта переписан

Исходная форма «дата рождения: <дата>, факты: <список>» не оставляла места отказу — модель была
обязана что-то подставить, и мы измерили бы покорность форме, а не устойчивость к выдумке.
Решение «знаю / не знаю» вынесено в первое поле ответа. Персонаж вымышлен (проверено поиском),
поэтому любой прогон со `статус: известно` есть выдумка — без разбора смысла текста.

### Вопрос про яблоки идёт в двух версиях

Школьная арифметика решается верно при любой температуре — по оси точности наблюдений могло
не быть вовсе. Рядом с исходной формулировкой идёт усложнённая, с выбрасываемыми испорченными
яблоками. Сам потолок становится наблюдением: видно, где температура не вредит, а где начинает.

### Метрики не считаем

Расчёт разнообразия и креативности отвергнут: выводы делает человек, глядя на ответы.
Отвергнут и оценщик-модель — судья систематически принимает лексическую неожиданность за
качество, и вывод «выше температура — выше креативность» оказался бы самоисполняющимся.

### Страница вместо пакетного скрипта

Отвергнут вариант «всё внутри `myharness` набором способов»: набор не умеет ни повторных
прогонов, ни таблицы, пришлось бы дописывать инструмент под один день.

Отвергнуты и профили температур для `myharness` как живая демонстрация — страница показывает то
же самое нагляднее, а артефакт, который нигде не показывается, делать незачем.

## Устройство

```
week_1/day_4/
  README.md          постановка, ход по стадиям, выводы, ссылки
  дизайн.md          этот документ
  план.md            план шагов
  pyproject.toml     свой проект uv
  temperature/
    questions.py     пять вопросов, разметка ответа, извлечение значения
    grid.py          прогон клеток: одновременность, повторы при сбое, запись
    web.py           страница и поток событий
  data/
    grid.jsonl       сырые ответы, строка на вызов — в репозиторий
  test/              песочница живых прогонов
```

Страница: порт 8767, слушает только `127.0.0.1`. Вверху переключатели вопросов (одиночный
выбор), ниже текст выбранного вопроса, ниже таблица 3×3 — столбцы по температурам, строки по
прогонам. Кнопка запускает девять вызовов, ответы приходят потоком событий и заполняют клетки
по мере готовности. Одновременных вызовов четыре: больше — риск упереться в ограничение частоты
и получить в кадре ошибки вместо ответов.

**Заполненные таблицы сохраняются при переключении вопросов** — вернувшись к прежнему вопросу,
пользователь видит собранное. Повторное нажатие кнопки дописывает новые прогоны, а не стирает
прежние.

В клетке: строка с извлечённым значением (число для яблок, `известно`/`неизвестно` для
Пятигорского; для метафоры и кода строки нет), текст ответа с прокруткой, служебная строка с
токенами, временем и причиной остановки.

Сырые ответы пишутся в `data/grid.jsonl` строкой на вызов: ключ клетки, вопрос, температура,
номер прогона, время, модель, полный слепок параметров, фиксация кода, текст, причина остановки,
расход токенов, время ответа, статус. Ключ API через этот слой не проходит.

Стек: FastAPI и uvicorn (уже в стеке проекта), страница — один файл с обычным JavaScript, без
сборки. Слой обмена с API берётся из `myharness` как библиотека, инструмент не правится.

## Затронутые способности

Правок поведения `myharness` день не вносит, спецификации не меняются. Опираемся на:

- `openspec/specs/params/` — состав параметров, обесценивание температуры рассуждениями;
- `openspec/specs/api/` — пределы ожидания, потоковый ответ, явное закрытие потока.

## Границы

**Делаем:** страницу с прогоном и таблицей, пять вопросов, три температуры, три прогона,
запись сырых ответов, проверку кода Kotlin настоящей компиляцией и прогоном (отдельным
сообщением пользователю, не в таблицу).

**Не делаем:** расчёт метрик, оценщика-модель, профили температур для `myharness`, правки
инструмента.

### Проверка кода — настоящая, без установок

Компилятор Kotlin и среда выполнения Java лежат внутри установленной Android Studio:

```
/Applications/Android Studio.app/Contents/plugins/Kotlin/kotlinc/bin/kotlinc
JAVA_HOME=/Applications/Android Studio.app/Contents/jbr/Contents/Home
```

Проверено: сборка занимает около пяти секунд, собранная программа запускается. Значит девять
ответов с кодом проверяются компиляцией и прогоном на наборе строк (обычный палиндром, строка
с пробелами и знаками, пустая строка, один символ, не-палиндром), а не чтением. Ставить JDK
или компилятор отдельно не требуется.

## Риски

| Риск | Чем расплачиваемся |
|---|---|
| Рассуждения не выключились хоть в одном вызове | Таблица по клетке бессмысленна. Проверяется до съёмки |
| Ожидание в кадре | Около полуминуты на вопрос, до трёх минут за съёмку |
| Рваные ответы при 1.2 | Это результат, а не поломка — в кадре ценнее аккуратных |
| Три прогона — мало | Выводы формулируются как наблюдения, без видимости строгости |
| Компилятор берётся из Android Studio | Проверка кода привязана к установленной среде разработки; при её отсутствии шаг отпадает, остальной день не страдает |
