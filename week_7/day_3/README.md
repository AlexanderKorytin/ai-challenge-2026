# День 33. Ассистент поддержки пользователей

## Условие

Сделайте мини-сервис для поддержки пользователей.

Ассистент должен:

- отвечать на вопросы о продукте;
- использовать RAG (FAQ, документация);
- учитывать контекст пользователя или тикета.

Через MCP:

- подключите CRM
- или JSON с пользователями / тикетами.

Пример: «Почему не работает авторизация?» — ассистент отвечает с учётом данных тикета.

Результат: AI-ассистент для поддержки пользователей.

## Дизайн и план

Дизайн — `docs/поддержка.md`, план — `docs/план-поддержка.md` в ветке `main`.

## Устройство

Код `myharness` не менялся. Ассистент — профиль `поддержка` и песочница `test/` с двумя
серверами MCP. Оба сервера работают только на чтение.

```
человек: «Тикет T-1001. Почему не работает авторизация?»
   ▼ myharness, профиль «поддержка» (profiles/поддержка.json + .md)
   ▼ модель зовёт сервер support: тикет (get_ticket) и/или пользователь (find_user, list_tickets)
   ▼ модель ищет в документации сама: search сервера rag по тексту ошибки и окружению
   ▼ ответ: причина по полю тикета или пользователя + шаги из базы знаний + «Источники:»
```

| Часть | Файл | Что делает |
|---|---|---|
| CRM | `support/server.py`, `support/данные.json` | 5 пользователей и 5 тикетов. Контекст пользователя: окружение и история тикетов. Контекст тикета: текст ошибки, статус, переписка |
| FAQ | `FAQ.md` | 12 вопросов пользователей. Каждый ответ ссылается на требование `openspec/specs` |
| Индекс | `support.sqlite` | `FAQ.md` и `openspec/specs`, 310 кусков, `bge-m3`, `structure` |
| Профиль | `profiles/поддержка.*` | порядок действий модели. Поля `rag` нет: искать решает модель |
| Песочница | `test/.mcp.json`, `test/.claude/settings.json` | серверы `rag` и `support`. Модели разрешены `search`, `get_ticket`, `find_user`, `list_tickets` |

## Итог живого сценария

Один вопрос «Почему не работает авторизация?» в разных контекстах дал разные причины.
Ответы целиком — `test/ответы.md`.

| # | Реплика | Вызовы | Ответ |
|---|---|---|---|
| 1 | тикет T-1001 | тикет, пользователь, его тикеты, поиск по тексту ошибки | DeepSeek отклонил ключ → `/auth` |
| 2 | тикет T-1002 | тикет, пользователь, его тикеты, поиск по тексту ошибки | не авторизация: служба Ollama не запущена |
| 3 | почта Веры, без тикета | пользователь, его тикеты, поиск дважды | `OLLAMA_API_KEY` не задан при шлюзе по `https://`; ссылка на закрытый T-1003 |
| 4 | без почты и тикета | нет | просит почту или номер тикета |
| 5 | Telegram | поиск дважды | «В документации этого нет» |

5 из 5 верны. Первый прогон дал 4 из 5: поиск шёл один раз до обмена по реплике
человека и текста ошибки тикета не видел. По T-1002 он нашёл раздел о ключе DeepSeek,
и модель ответила «в документации этого нет». Теперь ищет сама модель (дизайн, пункт 8).

## Местная модель

Тот же сценарий на `ollama/qwen3.5:9b-q4_K_M-32k`: 2 мин 47 с на пять реплик, от 11 до 51 с
на реплику. Ответы целиком — `test/ответы-местная.md`.

| # | Реплика | Вызовы | Итог |
|---|---|---|---|
| 1 | тикет T-1001 | тикет, пользователь, поиск по ошибке | верно |
| 2 | тикет T-1002 | тикет, пользователь; поиска нет | частично: причина верна, шаги выдуманы (`brew install`, сетевой экран) |
| 3 | почта Веры | только пользователь; ни истории, ни поиска | частично: `OLLAMA_API_KEY` назван, T-1003 не учтён, ключ велено брать «на ollama.com» — выдумка |
| 4 | без почты и тикета | `list_tickets` и `find_user` по выдуманному `U-01`, поиск | **неверно: модель сама подставила чужого пользователя и выдала его тикет** |
| 5 | Telegram | поиск | верно: «нет информации» |

2 верно, 2 частично, 1 неверно — против 5 из 5 у `deepseek-v4-flash`. Местная модель
пропускает поиск и тогда отвечает своими знаниями, хотя инструкция это запрещает. Реплика 4 —
беда другого рода: незнакомому человеку показаны данные чужого пользователя. Сервер `support`
отдаёт любого пользователя по номеру, и проверить, кто спрашивает, ему нечем: личность
называет модель. В настоящей службе пользователя должна называть программа по входу
человека, а не модель по догадке.

## Ограничения

- Пользователи и тикеты выдуманы. Тексты ошибок взяты дословно из кода `myharness`.
- Разделы FAQ писались после того, как был составлен сценарий. Каждый опирается на требование,
  но совпадение тем облегчает поиск. Вопрос не из FAQ (Telegram) получил честный отказ.
- Ответ по T-1001 советует ввести ключ через `/auth`, хотя клиентка пишет в тикете, что уже
  пробовала. Модель учла ошибку тикета, но не его текст. Причина при этом названа верно.
- Отказ про Telegram дала модель: поиск вернул пять далёких кусков, порог их не отсёк.
- Живой прогон один, на одной модели. Ответы модели от прогона к прогону меняются.
- Пакетный режим не отдаёт модели инструменты MCP (отложенная задача 17). Поэтому сценарий
  идёт в окне.
- Сервер `rag` с доводом `context` сам зовёт DeepSeek, чтобы переписать вопрос. Инструкция
  запрещает модели передавать `context`: запрос составляет модель.
