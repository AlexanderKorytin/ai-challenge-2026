# День 33. Ассистент поддержки пользователей

**Стадия: Done** — 2026-10-14, результат подтверждён, отчёт сдан (ход стадий — `docs/состояние-поддержка.md` и `docs/состояние-веб-чат-поддержки.md`, копии в этой папке).

## Условие

Сделайте мини-сервис для поддержки пользователей.

Ассистент должен:

- отвечать на вопросы о продукте;
- использовать RAG (FAQ, документация);
- учитывать контекст пользователя или тикета.

Через MCP:

- подключите CRM
- или JSON с пользователями / тикетами.

Пример: «Почему не работает авторизация?» — ассистент отвечает с учётом данных тикета.

Результат: AI-ассистент для поддержки пользователей.

## Дизайн и план

Дизайн — `docs/поддержка.md`, план — `docs/план-поддержка.md` в ветке `main`.

## Устройство

Код `myharness` не менялся. Ассистент — профиль `поддержка` и песочница `test/` с двумя
серверами MCP. В песочнице `test/` оба сервера работают только на чтение. Запись тикетов есть
только в веб-чате (раздел «Веб-чат»).

```
человек входит как пользователь: SUPPORT_USER=U-03
   ▼ myharness, профиль «поддержка» (profiles/поддержка.json + .md)
   ▼ модель зовёт сервер support: свой тикет (get_ticket) и/или себя (find_user, list_tickets)
   ▼ модель ищет в документации сама: search сервера rag по тексту ошибки и окружению
   ▼ ответ: причина по полю тикета или пользователя + шаги из базы знаний + «Источники:»
```

| Часть | Файл | Что делает |
|---|---|---|
| CRM | `support/server.py`, `support/данные.json` | 5 пользователей и 5 тикетов. Контекст пользователя: окружение и история тикетов. Контекст тикета: текст ошибки, статус, переписка |
| Вход | `SUPPORT_USER` → `test/.mcp.json` (`${SUPPORT_USER}`) | кто спрашивает. Сервер отдаёт данные только этого пользователя, чужой тикет — «не ваш». Без переменной `myharness` не запускает сервер `support` и называет незаданную переменную. Разговор хранится в своём каталоге `state/<U-xx>` |
| FAQ | `FAQ.md` | 12 вопросов пользователей. Каждый ответ ссылается на требование `openspec/specs` |
| Индекс | `support.sqlite` | `FAQ.md` и `openspec/specs`, 310 кусков, `bge-m3`, `structure` |
| Профиль | `profiles/поддержка.*` | порядок действий модели. Поля `rag` нет: искать решает модель |
| Песочница | `test/.mcp.json`, `test/.claude/settings.json` | серверы `rag` и `support`. Модели разрешены `search`, `get_ticket`, `find_user`, `list_tickets` |

Почему вход задаёт запуск. В первой версии модель сама называла пользователя: по почте
или номеру тикета в реплике. Местная модель на вопрос без почты и тикета подставила `U-01`
и выдала незнакомому человеку чужой тикет. Теперь у инструментов нет доводов о личности,
и модели нечем спросить о другом человеке.

Один вопрос «Почему не работает авторизация?» у разных пользователей дал разные причины.
Ответы целиком — `test/ответы.md` и `test/ответы-местная.md`.

| # | Кто и что | `deepseek-v4-flash` | `ollama/qwen3.5:9b-q4_K_M-32k` |
|---|---|---|---|
| 1 | Анна: тикет T-1001 | ключ DeepSeek отвергнут → `/auth` | то же |
| 2 | Борис: тикет T-1002 | не авторизация: служба Ollama не запущена | причина верна; поиска не было, часть шагов своя (`curl`) |
| 3 | Вера, без тикета | `OLLAMA_API_KEY` не задан при шлюзе; закрытый T-1003 учтён | то же; поиска не было |
| 4 | Анна: чужой тикет T-1002 | отказ: тикет другого пользователя | отказ |
| 5 | Анна: Telegram | «В документации этого нет» | то же |

Время на реплику: DeepSeek 3–8 с, местная модель 8–36 с.

Как пришли к этому:
- первый прогон на DeepSeek дал 4 из 5. Поиск шёл один раз до обмена, по реплике
  человека, и текста ошибки тикета не видел. Теперь ищет сама модель (дизайн, пункт 8);
- первый прогон на местной модели выдал чужой тикет незнакомому человеку. Теперь вход
  задаёт запуск (дизайн, пункт 9). Оба прогона записаны в `docs/состояние-поддержка.md`.

## Ограничения

- Пользователи и тикеты выдуманы. Тексты ошибок взяты дословно из кода `myharness`.
- Вход — переменная при запуске, без пароля. Это граница доверия песочницы, а не настоящая
  проверка личности: в службе пользователя называет её вход.
- Разделы FAQ писались после того, как был составлен сценарий. Каждый опирается на требование,
  но совпадение тем облегчает поиск. Вопрос не из FAQ (Telegram) получил честный отказ.
- Ответ по T-1001 советует ввести ключ через `/auth`, хотя клиентка пишет, что уже пробовала.
  Модель учла ошибку тикета, но не его текст.
- Обе модели пробовали вызвать несуществующий инструмент: DeepSeek — `support__search`,
  местная — `mcp__search`. DeepSeek после ошибки вызвал настоящий поиск, местная
  модель в случае 3 ответила без поиска.
- Местная модель пропускает поиск и тогда добавляет свои шаги, хотя инструкция это запрещает.
- Отказ про Telegram дала модель: поиск вернул далёкие куски, порог их не отсёк.
- Живого прогона без `SUPPORT_USER` нет: проверено только кодом и требованием `mcp`.
- Прогон на каждой модели один. Ответы от прогона к прогону меняются.
- Пакетный режим не отдаёт модели инструменты MCP (отложенная задача 17). Поэтому сценарий
  идёт в окне.
- Сервер `rag` с доводом `context` сам зовёт DeepSeek, чтобы переписать вопрос. Инструкция
  запрещает модели передавать `context`: запрос составляет модель.

## Веб-чат

После сдачи окна ментор сказал: «чат логичнее» и «сделать из этого рабочий продукт». Поэтому
ассистент получил учебный веб-чат. Дизайн — `docs/веб-чат-поддержки.md`, план —
`docs/план-веб-чат-поддержки.md` в ветке `main`.

Запуск: `web/запуск.sh`, затем в браузере `http://127.0.0.1:8790`.

```
браузер ── HTTP ── web/app.py (Starlette)
                     ├─ Agent из myharness, профиль «поддержка»
                     └─ свой каталог сеанса на пользователя: .mcp.json с SUPPORT_USER
                           ├─ сервер support (свой процесс): чтение и запись тикетов
                           └─ сервер rag: поиск по FAQ и требованиям
```

- **Вход** — по имени, без пароля. Новое имя заводит пользователя `U-06`, `U-07` и дальше.
- **Изоляция пользователей.** У каждого пользователя свой процесс сервера `support`: номер пользователя
  записан в `.mcp.json` его каталога сеанса. Чужой тикет сервер не отдаёт и не меняет.
- **Запись в CRM** — три инструмента сервера `support`:
  - `create_ticket` заводит тикет;
  - `add_message` дописывает ответ ассистента в переписку;
  - `set_status` ставит «открыт», «ждёт специалиста» или «закрыт» с причиной.

  Запись идёт под блокировкой файла (`support/store.py`) в рабочую копию `web/данные.json`.
  Данные сценария в git чат не трогает.
- **Когда ассистент пишет**, решает модель по инструкции профиля, раздел «Тикеты»:
  - ответ по тикету записывается в тикет до текста ответа;
  - новый тикет заводится только с согласия пользователя;
  - «закрыт» ставится, только когда пользователь сказал, что всё работает.
- **Страница.** Ответ приходит потоком. Вызовы инструментов показаны серыми строками, справа список
  тикетов. Модель выбирается: DeepSeek или местная `qwen3.5:9b`.
- **Разговор** хранится по пользователю. Повторный вход его продолжает, «Новый разговор» начинает заново.
  Выход и повторный вход ждут конца идущего ответа и закрывают процессы серверов MCP.

Проверки: `support/check_server.py` — 28, `web/check_web.py` — 21, без модели.

Живой прогон на `deepseek-v4-flash`, новая пользовательница Ирина:

| Реплика | Что сделал ассистент |
|---|---|
| ошибка «Ollama не отвечает…» | ответ по FAQ, предложение завести тикет |
| «Да, заведите тикет» | завёл T-1006, дописал в него ответ |
| «Запустила ollama serve, всё заработало» | закрыл T-1006 с причиной |
| «Как подключить myharness к Telegram?» | «В документации этого нет», предложение передать специалисту |
| «Да, передайте специалисту» | завёл T-1007 со статусом «ждёт специалиста» |

Анна по T-1001: ответ про ключ DeepSeek, ответ записан в тикет. В первой версии инструкции
DeepSeek отвечал и не записывал: после текста ответа модель инструментов не зовёт. Правило
переставлено, запись идёт до текста, и в 2 прогонах из 2 запись прошла. Местная модель в
браузере ответила на вопрос о смене модели по найденному в документации.

На ролике веб-чата прогон шёл заново, и модель решала иначе. T-1006 Ирины заведён и закрыт, но
ответ в его переписку не записан. Местная модель ответила Борису по тикету и не искала в документации.

Ограничения веб-чата:

- Пароля нет: под именем Анны войдёт любой и увидит её тикеты. Адрес — только `127.0.0.1`.
- Модель сама решает, когда писать в CRM. Она может завести лишний тикет или не записать ответ.
  Все записи видны в списке тикетов.
- Страницы специалиста нет. Тикет «ждёт специалиста» виден только в файле данных.
- Сеанс, брошенный без выхода, держит процессы серверов MCP до остановки веб-сервера.
