## 1. U-01: Тикет T-1001. Почему не работает авторизация?

Время: 8 с. Вызовы: `mcp__support__get_ticket`, `mcp__support__find_user`, `mcp__support__search` — «ошибка "ключ не принят DeepSeek API (проверьте правильность)" — как исправить авторизацию, команда /auth», `mcp__support__list_tickets`, `mcp__rag__search` — «ключ не принят DeepSeek API, проверьте правильность ключа, авторизация через /auth в myharness»

```
Причина: в тикете T-1001 ошибка «ключ не принят DeepSeek API (проверьте правильность)» — это значит, что DeepSeek отклонил ключ: он либо отозван, либо скопирован с ошибкой. Сеть при этом работает (при сбое сети сообщение было бы другим — «не удалось проверить ключ: …»). По вашим данным (U-01, Анна Смирнова) провайдер deepseek, и переменных окружения, влияющих на это, не задано. Прежних тикетов по этой теме у вас нет.

Что делать:
1. Откройте кабинет DeepSeek и проверьте, что ключ не отозван.
2. Скопируйте ключ заново, без пробелов по краям.
3. Введите `/auth` и вставьте ключ — команда работает и тогда, когда её нет в меню.
4. После строки «авторизация сохранена» ключ вводить заново не нужно.
5. Если ключ «пропал» после запуска с другой `MYHARNESS_CONFIG_DIR` — уберите переменную или введите ключ заново через `/auth`; ключ хранится в `~/.config/myharness/config.json`.

Источники: week_7/day_3/FAQ.md › Почему не работает авторизация: ключ не принят DeepSeek API; week_7/day_3/FAQ.md › Где хранится ключ DeepSeek и кто может его прочитать. Тикет T-1001.
```

## 2. U-02: Тикет T-1002. Почему не работает авторизация?

Время: 8 с. Вызовы: `mcp__support__get_ticket`, `mcp__support__find_user`, `mcp__support__search` — «Ollama не отвечает по адресу http://127.0.0.1:11434 — проверьте, что служба запущена, местная модель, авторизация», `mcp__support__list_tickets`, `mcp__rag__search` — «Ollama не отвечает по адресу 127.0.0.1:11434 — проверьте, что служба запущена. Как подключить местную модель Ollama»

```
Причина: в тикете ошибка «Ollama не отвечает по адресу http://127.0.0.1:11434 — проверьте, что служба запущена», а у вас в окружении `OLLAMA_HOST` и `OLLAMA_API_KEY` не заданы. Это не про авторизацию: местной службе на своей машине токен не нужен — по адресу просто никто не принимает соединений.

Шаги:

1. Запустите службу Ollama: приложение Ollama либо команду `ollama serve`.
2. Проверьте адрес: myharness берёт его из `OLLAMA_HOST`, а без переменной — `http://127.0.0.1:11434`. Если служба стоит на другой машине — задайте `OLLAMA_HOST` с полной схемой и портом.
3. Проверьте, что модель скачана: `ollama list`. Имя в myharness пишется с приставкой `ollama/` — у вас `ollama/qwen3.5:9b-q4_K_M-32k`.
4. Если служба не на своей машине и за шлюзом, который требует токен, — задайте `OLLAMA_API_KEY=<токен>` в том окружении, из которого запускаете myharness; адрес шлюза указывайте с `https://`.

Источники: week_7/day_3/FAQ.md › Ollama не отвечает: местная модель не подключается; week_7/day_3/FAQ.md › Шлюз отвечает «нет токена либо токен неверен»; openspec/specs/api/spec.md › Requirements › Requirement: Поставщика называет имя модели. Тикет T-1002.
```

## 3. U-03: Почему не работает авторизация?

Время: 7 с. Вызовы: `mcp__support__find_user`, `mcp__support__list_tickets`, `mcp__rag__search` — «ошибка авторизации шлюза OLLAMA_API_KEY не задан нет токена либо токен неверен», `mcp__rag__search` — «как задать OLLAMA_API_KEY для Ollama за шлюзом авторизация myharness»

```
Причина: в вашем окружении `OLLAMA_API_KEY` — «не задан», а `OLLAMA_HOST` указывает на чужую машину за шлюзом (`https://gpu.example.com:443`). Без токена myharness отправляет заглушку, и шлюз отвечает отказом 401 — то же самое было в тикете T-1003 («нет токена либо токен неверен»).

1. Получите токен у администратора шлюза.
2. Задайте `OLLAMA_API_KEY=<токен>` в окружении, из которого запускаете myharness.
3. Адрес шлюза в `OLLAMA_HOST` пишите полностью: с `https://` и портом, который назвал администратор. По открытому `http://` на чужую машину токен не уходит — обмен прерывается с ошибкой, называющей адрес.

Источники: week_7/day_3/FAQ.md › Шлюз отвечает «нет токена либо токен неверен»; openspec/specs/api/spec.md › Requirements › Requirement: Поставщика называет имя модели. Тикет T-1003.
```
