## Итоговая схема: домашний сервер

Условие допускает VPS или домашний сервер. Итог дня — домашний сервер, решение пользователя
2026-10-09.

```
клиент в сети (myharness, curl)
   │ HTTP, заголовок Authorization: Bearer <токен>
   ▼
шлюз на Маке, порт 8780           токен → путь → модель → поля → частота → окно → журнал
   ▼
Ollama 127.0.0.1:11434 на Маке    qwen3.5:9b-q4_K_M-32k; наружу порт не открыт
```

- Запуск службы: `test/служба.sh`. Токены клиентов — `~/.config/llm-gateway/tokens.env`
  (права 600, вне git). Журнал — `~/.config/llm-gateway/journal.jsonl`, без текста запросов.
- Чат: `test/показ.sh` — `myharness` с профилем `служба` (рассуждения выключены).
- Доступ по сети: `test/без-токена.sh`. Два соединения с очередью: `test/два-соединения.sh`.
- Ограничения: `test/ограничения.sh` — окно и частота, 15 запросов.
- Два чата рядом: `test/показ.sh mac` и `test/показ.sh guest` в двух окнах.
- Обвязка перед Ollama — шлюз. Очередь ведёт Ollama: модель отвечает по одному запросу.
- Шлюз слушает HTTP без шифрования: годится для домашней сети, в открытую сеть так не выставлять.

Первый вариант — вход через VPS с HTTPS и обратным туннелем ssh — собран, замерен и описан ниже.
От него отказались: VPN на Маке перестал пускать соединения к серверу мимо себя
(раздел «Что пошло не так»).

## Постановка

Условие дня: развернуть местную языковую модель как службу — на VPS или домашнем сервере,
с HTTP API и чатом. Проверить доступ к модели по сети, стабильность при нескольких запросах
и базовые ограничения: частоту запросов и размер окна. Итог — приватная служба.

## Первый вариант: вход через VPS

Модель `qwen3.5:9b-q4_K_M-32k` работает в Ollama на Маке (домашний сервер). Оба VPS проекта
малы: 1 ядро и 956 МБ памяти, модель в 7,3 ГБ туда не помещается. VPS даёт вход из сети.

```
клиент (myharness, curl)
   │ HTTPS, заголовок Authorization: Bearer <токен>
   ▼
Caddy :443 на 188.120.230.58          сертификат на IP
   ▼
шлюз 127.0.0.1:8780 (systemd)         токен → путь → модель → поля → частота → окно → журнал
   ▼
127.0.0.1:11435 на VPS                конец обратного туннеля ssh
   ▼ туннель держит Мак (агент launchd)
Ollama 127.0.0.1:11434 на Маке        наружу порт не открыт
```

- **HTTP API** — формат OpenAI: `POST /v1/chat/completions`, `GET /v1/models`. Любой клиент
  OpenAI работает с адресом `https://188.120.230.58/v1` и токеном как ключом.
- **Чат** — `myharness` на любой машине: `OLLAMA_HOST=https://188.120.230.58:443`,
  `OLLAMA_API_KEY=<токен>`, модель `ollama/qwen3.5:9b-q4_K_M-32k`.
- **Приватность.** У Ollama проверки токена нет, и её порт наружу не выходит. Шлюз пускает
  только клиента с токеном и только к чату и к чтению сведений о разрешённой модели (список,
  окно, словарь). Загрузить, удалить и создать модель снаружи нельзя. Текст запросов и ответов шлюз в журнал не пишет.
- **Туннель.** У Мака нет внешнего адреса. Мак сам открывает соединение ssh к VPS и просит VPS
  слушать порт. Ключ туннеля разрешает только это одно действие.

Код лежит в ветке `main`:

| Что | Где |
|---|---|
| шлюз, его проверки и файлы выкладки | `llm_gateway/` |
| токен службы в клиенте Ollama | `myharness/src/myharness/providers.py`, `api.py` |
| требования | `openspec/specs/api/` — «Поставщика называет имя модели» |
| выкладка на сервер | `docs/vps.md`, раздел `llm-gateway` |
| дизайн и план | `docs/местная-служба.md`, `docs/план-местная-служба.md` |

В этой папке — программа замера `проверка.py`, её итог `проверка.md` и проверка двух устройств
`два_устройства.sh`.

## Итог проверки

Прогон `проверка.py` 2026-10-09, полный вывод — `проверка.md`.

| Что проверяли | Итог |
|---|---|
| доступ без токена и с чужим токеном | 401 |
| чат с Мака (домашняя сеть) | «Париж.», 2,6 с |
| чат с сервера `challenge` (другая сеть) | «56», 3,3 с вместе с ssh |
| загрузка модели снаружи (`/api/pull`), чужая модель | 404 |
| 20 запросов подряд | шлюз ответил на 20 из 20; медиана 5,3 с, максимум 13,7 с по его журналу |
| те же 20 запросов глазами клиента на Маке | 19 из 20: один ответ потерян на пути (обрыв TLS) |
| 8 запросов одновременно | 8 из 8; от 9,1 до 56,8 с — модель отвечает по одному, остальные ждут |
| два устройства одновременно: Мак и сервер `challenge` | оба получили ответ; 11,6 и 17,5 с по журналу шлюза |
| 20 запросов одного клиента разом при пределе 12 в минуту | 13 прошли, 7 получили 429 и `Retry-After: 5` |
| запрос в 40 099 токенов при окне 32 768 | шлюз — 400 `context_length_exceeded` |
| тот же запрос напрямую в Ollama | код 200, служба молча оставила 16 386 токенов и ответила |

Выводы:

- **Два устройства одновременно.** Мак и сервер `challenge` послали по запросу в одну секунду,
  оба получили ответ: 11,6 и 17,5 с по журналу шлюза (`два_устройства.sh`).
- **Очередь есть, и ведёт её Ollama.** Модель отвечает по одному запросу, остальные ждут: восемь
  одновременных запросов выполнились все, от 9,1 до 56,8 с. Обвязка перед Ollama — шлюз: токен,
  частота, окно. Своей второй очереди в шлюзе нет: она дублировала бы работающую.
- **Проверка окна в шлюзе нужна.** Ollama на длинный запрос ошибкой не отвечает: она молча
  обрезает его до половины окна. Шлюз отказывает до отправки.
- **Путь от Мака к серверу ненадёжен.** В прогоне один ответ из 20 потерян на пути (обрыв TLS),
  шлюз при этом ответил на все 20.

## Что пошло не так

Замер был больше, чем просит условие: 20 запросов подряд, 8 одновременно, 20 разом на частоту и
повторы прогона — около 170 запросов за 40 минут на учебный сервер с одним ядром. Около 15:25
путь от домашней сети Мака к порту 443 сервера закрылся: соединение TCP есть, ответа на
приветствие TLS нет. Сервер здоров, из другой сети служба отвечает за 0,16 с, ssh работает.
Причина на пути не установлена. Умолчания `проверка.py` уменьшены до 5 запросов подряд и 2
одновременных.

Затем отказал и ssh. Настоящая причина найдена вечером: виноват не сервер и не нагрузка, а VPN
на Маке. Около 15:25 VPN переподключился, и адреса серверов перестали идти мимо него. В обход
VPN (`curl --interface en0`, `ssh -o BindInterface=en0`) сервер отвечает за 0,09 с, в журнале
sshd за 4 часа нет ни одного отказа по перегрузке. Агент туннеля снят, служба на VPS без туннеля
отвечает 503. Шлюз и пользователь туннеля на сервере остались, их уборка — отдельная работа.

## Ограничения службы

| Ограничение | Значение | Отказ |
|---|---|---|
| частота | 12 запросов чата в минуту на клиента | 429, заголовок `Retry-After` |
| окно | вход плюс `max_tokens` не больше 32 768 токенов | 400 `context_length_exceeded` |
| модели | одна: `qwen3.5:9b-q4_K_M-32k` | 404 `model_not_found` |
| одновременная работа | модель отвечает по одному запросу, остальные ждут в очереди Ollama | — |
| доступность | служба работает, пока Мак включён и не спит | 503 `upstream_unavailable` |
| поиск по базе знаний | профиль с полем `rag` через шлюз не работает: сервер поиска читает тот же `OLLAMA_HOST`, токен не шлёт, пути `/api/embed` у шлюза нет | 401 |
