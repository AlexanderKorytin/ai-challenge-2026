## Как проверяем и почему так

- **Строгий цикл «тест → падение → код → проход»** — на весь `plan.py`: разбор, белые списки,
  волны, распределение знаков, сборка запроса, выбор листьев. Это чистые функции с краями,
  которые в живом прогоне не поймать: цикл в графе, план на четырнадцать пунктов, зависимость
  длиннее потолка.
- **Ручной прогон по сценарию** — на интерфейс: живая строка, экран утверждения, цикл правок,
  отмена. Строгий цикл на отрисовку стоит дороже пользы.
- **Сквозная проверка в `check_app.py`** — на связку целиком, с подставным клиентом, отдающим
  по сценарию план, затем запросы, затем ответы исполнителей.

## Шаг 1. Пределы конвейера и разбор поля `pipeline`

**Файлы**: `src/myharness/plan.py` (новый), `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Пределы прогона задаются профилем»
**Проверка**: проверки на умолчания и на обрезку каждого предела проходят.

**Содержание**. Модуль-заголовок с объяснением, почему логика плана отделена от оркестратора
(проверяется без сети и без терминала). Константы:

```python
PLANNER_MODEL = "deepseek-v4-pro"
WRITER_MODEL = "deepseek-v4-flash"
MAX_ITEMS = 8              # умолчание
ITEMS_CEILING = 10         # потолок, выше не поднять профилем
TOKENS_DEFAULT = 2048      # max_tokens пункта, если планировщик не назвал
TOKENS_MIN, TOKENS_MAX = 256, 4096
TOKENS_TOTAL = 24_000      # сумма по всем пунктам
ROLE_CHARS = 2000
CONCURRENCY_DEFAULT, CONCURRENCY_CEILING = 2, 4
# Потолок на весь блок выходов зависимостей. Число то же, что у памяти агента, и по той же
# причине: около трети окна контекста. Второй константы на ту же величину не заводим.
from .agent import HISTORY_CHARS_MAX as CARRY_CHARS
```

```python
@dataclass
class Settings:
    planner_model: str = PLANNER_MODEL
    writer_model: str = WRITER_MODEL
    max_items: int = MAX_ITEMS
    concurrency: int = CONCURRENCY_DEFAULT
    max_tokens: int = TOKENS_DEFAULT
    notes: list[str] = field(default_factory=list)

    @staticmethod
    def from_profile(profile, known_models: list[str]) -> Settings
```

`from_profile` читает `profile.pipeline`. Каждая поправка кладётся строкой в `notes` — молча не
правим: `notes` печатаются при выборе профиля. Правила: неизвестная модель → умолчание;
`max_items` вне 1…`ITEMS_CEILING` → обрезка; `concurrency` вне 1…`CONCURRENCY_CEILING` →
обрезка; `max_tokens` вне `TOKENS_MIN`…`TOKENS_MAX` → обрезка; не словарь в `pipeline` →
умолчания и предупреждение.

**Тесты (пишутся первыми)**: пустой словарь даёт умолчания; `max_items: 40` даёт 10 и пометку;
`concurrency: 0` даёт 1 и пометку; `planner_model: "gpt-9"` даёт `deepseek-v4-pro` и пометку;
`pipeline: "да"` даёт умолчания и пометку.

## Шаг 2. Структуры плана и его сериализация

**Файлы**: `src/myharness/plan.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «План — машиночитаемая запись работ»
**Проверка**: `to_json(parse(текст))` даёт JSON, который снова разбирается в равный план.

**Содержание**.

```python
class PlanError(Exception):
    """План не годен к исполнению. Текст — замечание, которое уйдёт планировщику."""

@dataclass
class Executor:
    model: str
    thinking: bool
    temperature: float | None   # None, когда рассуждения включены: API её игнорирует
    role: str

@dataclass
class Item:
    id: str
    work: str
    depends_on: list[str]
    executor: Executor
    check: str
    max_tokens: int
    request: str = ""                               # дописывает постановщик
    notes: list[str] = field(default_factory=list)  # пометки поправок, видны при утверждении

@dataclass
class Plan:
    task: str
    items: list[Item]

    def by_id(self, item_id: str) -> Item | None

def to_json(plan: Plan) -> str
```

`to_json` пишет русские ключи и `ensure_ascii=False`; поле `запрос` включается, только если оно
непусто; `temperature` — только если она не `None`. Это тот текст, который уйдёт планировщику
как «прежний план» при правках, поэтому в нём должна быть уже **исправленная** программой
версия, а не то, что модель прислала изначально.

## Шаг 3. Разбор плана: поля пункта и белые списки

**Файлы**: `src/myharness/plan.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Значения плана проверяются как непроверенный ввод»
**Проверка**: каждая поправка из таблицы дизайна воспроизведена проверкой и даёт пометку в `notes`.

**Содержание**. `def parse(raw: str, *, known_models: list[str], settings: Settings) -> Plan`.

Разбор `json.loads`; не объект, нет `план`, `план` не список, пустой список → `PlanError` с
замечанием для планировщика.

Поля пункта, поправки — с пометкой в `item.notes`, отклонения — `PlanError`:

| Поле | Правило | При нарушении |
|---|---|---|
| `id` | непустая строка; отсутствует → номер по порядку | пометка |
| `работа` | непустая строка | `PlanError` |
| `зависит_от` | список строк; не список → пустой | пометка |
| `исполнитель.модель` | из `known_models` | `settings.writer_model`, пометка `модель «X» неизвестна` |
| `исполнитель.рассуждения` | логическое | `False`, пометка |
| `исполнитель.temperature` | 0…2 | обрезка, пометка |
| `исполнитель.temperature` при `рассуждения: true` | обнуляется в `None` | пометка `temperature не действует при рассуждениях` |
| `исполнитель.роль` | непустая строка ≤ `ROLE_CHARS` | пусто → `PlanError`; длинная → обрезка и пометка |
| `проверка` | строка | пусто → пометка `критерий проверки не задан` |
| `max_tokens` | целое `TOKENS_MIN`…`TOKENS_MAX` | не задано → `settings.max_tokens`; вне — обрезка, пометка |

Логическое значение отсеивается до целого — в Python `bool` разновидность `int`, иначе `true`
прошло бы как `max_tokens = 1`. Тот же приём уже применён в разборе `history_window`.

**Тесты**: по проверке на каждую строку таблицы; отдельно — `рассуждения: true` вместе с
`temperature: 0.2` даёт `temperature is None` и пометку.

## Шаг 4. Разбор плана: отклоняющие правила

**Файлы**: `src/myharness/plan.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Негодный план человеку не показывается»
**Проверка**: каждое правило даёт `PlanError`, и текст замечания называет причину поимённо.

**Содержание**. В конце `parse`, после сборки пунктов:

- повторяющиеся `id` → `PlanError("в плане повторяются id: 2")`;
- ссылка `зависит_от` на несуществующий пункт → `PlanError("пункт 3 зависит от несуществующего 9")`;
- цикл в графе → `PlanError("в плане цикл: 2 → 3 → 2")` (цикл ищется тем же обходом, что и волны, см. шаг 5);
- пунктов больше `settings.max_items` → `PlanError("пунктов 14, укрупни до 8")`;
- сумма `max_tokens` больше `TOKENS_TOTAL` → `PlanError("суммарный потолок вывода 31000 токенов при разрешённых 24000, сократи план")`.

Замечание пишется так, чтобы его можно было отправить планировщику дословно: причина плюс
что сделать.

## Шаг 5. Топологические волны

**Файлы**: `src/myharness/plan.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Пункты исполняются волнами»
**Проверка**: линейная цепочка даёт три волны по одному, ромб — три волны 1/2/1, цикл — `PlanError`.

**Содержание**. `def waves(plan: Plan) -> list[list[Item]]`.

Обход Кана: волна — все пункты, у которых не осталось незакрытых зависимостей; порядок внутри
волны совпадает с порядком в плане (порядок не косметика — по нему идут экраны исполнителей и
итоги). Если после исчерпания очередной волны остались пункты, значит в них цикл: собрать
любой замкнутый путь и бросить `PlanError` с ним в тексте.

`parse` зовёт `waves` в самом конце, чтобы негодный граф не дошёл до показа человеку.

## Шаг 6. Распределение потолка знаков и сборка запроса исполнителя

**Файлы**: `src/myharness/plan.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Выход зависимости передаётся целиком до потолка»
**Проверка**: короткая зависимость отдаёт остаток длинной; обрезка помечена в тексте запроса.

**Содержание**.

```python
def carry_shares(lengths: list[int], budget: int = CARRY_CHARS) -> list[int]
```

Наполнение по уровню: доля поровну, зависимости короче своей доли берут сколько есть и
отдают остаток остальным, деление повторяется, пока есть кому отдавать. Единственная длинная
зависимость получает почти весь бюджет.

```python
def build_request(item: Item, answers: dict[str, str]) -> str
```

Собирает: блок на каждую зависимость в порядке `depends_on`, затем `item.request`. Блок:

```
[выход пункта 1]
<текст, обрезанный до своей доли>
(ответ обрезан: показано 60000 из 82431 знаков)
```

Последняя строка ставится, только если обрезка была. Отсутствующий в `answers` пункт даёт блок
`(пункт 1 ответа не дал)` — исполнителю честнее знать, что вход неполон, чем получить пустоту.

**Тесты**: две зависимости по 100 знаков при бюджете 1000 — обе целиком; одна на 5000 и одна на
10 при бюджете 1000 — вторая целиком, первая 990; обрезанный блок несёт пометку с обоими
числами; порядок блоков совпадает с `depends_on`.

## Шаг 8. Встроенные инструкции и сборщики запросов

**Файлы**: `src/myharness/plan.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Инструкции планировщика и постановщика встроены»
**Проверка**: обе инструкции содержат слово «json» и пример структуры; запрос правки несёт и прежний план, и текст правок.

**Содержание**. Тексты по-русски, константами:

- `PLANNER_INSTRUCTION` — роль планировщика, точная структура ответа с примером, пределы
  (не больше `$пунктов` пунктов — подстановка через `vars` профиля), правило «параллельность
  выражается только через `зависит_от`», перечень допустимых моделей, запрет на поля, которых нет
  в структуре.
- `WRITER_INSTRUCTION` — роль постановщика: получает задачу целиком и один пункт, возвращает
  `{"запрос": "..."}` — готовый текст запроса исполнителю, без роли (роль уже есть) и без
  пересказа зависимостей (их подставит программа).

Слово «json» и пример обязаны стоять в самой инструкции: без них DeepSeek отклоняет запрос с
`response_format: json_object`.

```python
def planner_profile(settings: Settings) -> Profile      # pro, thinking enabled, json_object, temperature НЕ задаётся
def writer_profile(settings: Settings) -> Profile       # flash, thinking disabled, temperature 0.2, json_object
def planner_request(task: str) -> str
def revision_request(plan: Plan, corrections: str) -> str
def repair_request(plan_text: str, remark: str) -> str
def writer_request(plan: Plan, item: Item) -> str
def parse_written_request(raw: str) -> str              # достаёт поле «запрос»; пусто — пустая строка
```

`revision_request` кладёт `to_json(plan)` и текст правок с требованием «исправь только то, чего
касаются правки; `id` пунктов не меняй». `repair_request` — прежний ответ модели и замечание
программы, для того самого единственного автоматического захода.

## Шаг 10. Скрытый обмен без панели

**Файлы**: `src/myharness/output.py`, `tests/check_units.py`
**Требование**: `openspec/specs/agent/spec.md` → «Скрытый агент работает без панели»
**Проверка**: обмен проходит без единого экрана; ошибка, обрезка памяти и сбой журнала попадают в главный экран.

**Содержание**.

```python
@dataclass
class HiddenRun:
    label: str          # «планирую», «ставлю задачи по плану»
    started: float      # time.monotonic()
    tokens: int | None = None   # None, пока обмен идёт: расход приходит одним событием в конце

async def run_hidden(state, agent_obj, content, *, label, agent_name=None, run_id=None) -> Turn
```

Ставит `state.hidden`, поднимает задачу-тикер (`asyncio.sleep(0.1)` + `refresh`) — сама по себе
перерисовка не идёт, `prompt_toolkit` рисует по `invalidate`. `on_event` не передаёт: показывать
нечего. В `finally`: гасит тикер с ожиданием его отмены (как это делает `run_turn` со счётчиком
ожидания), проставляет `hidden.tokens` по `turn.usage`, снимает `state.hidden`, зовёт
`warn_journal`, при неуспехе пишет ошибку в главный экран, при `turn.dropped_pairs > 0` — там же
сообщение об обрезке. Панели у скрытого агента нет, а требование «об обрезке сообщается
пользователю» действует и здесь — поэтому адресат главный экран.

**Тесты**: обмен скрытого агента без экранов проходит и возвращает текст; при отказе клиента
сообщение об ошибке лежит в ленте главного экрана; `state.hidden` снят и после успеха, и после
отказа.

## Шаг 11. Живая строка скрытой работы

**Файлы**: `src/myharness/ui.py`, `src/myharness/cli.py`, `tests/check_units.py`
**Требование**: `openspec/specs/interface/spec.md` → «Скрытая работа показана живой строкой»
**Проверка**: строка появляется на время скрытого обмена и исчезает после; во время работы вместо расхода стоит прочерк.

**Содержание**.

```python
def hidden_status_fragments(label: str, elapsed_ms: int, tokens: int | None, frame: int) -> Fragments

```

Первая — живая строка `⠹ планирую…            8.2 с        —`; форматы времени и токенов берутся
у `format_duration` и `format_tokens`, теми же, что в списке агентов: разнобой «12.4 с» здесь и
«12.4s» там недопустим. Кадр вращения — из `SPINNER_FRAMES`.
Вторая — итоговая строка в ленте: `· планирование: 11.3 с · ↓ 9.4k`.

В `cli.build_app` — однострочное окно в `ConditionalContainer` с условием `state.hidden is not
None`, между лентой и строкой ввода. То же устройство, что у строки состояния и списка агентов.

## Шаг 13. Режим ожидания утверждения

**Файлы**: `src/myharness/cli.py`, `src/myharness/pipeline.py`, `tests/check_app.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «План утверждается человеком»
**Проверка**: пустой Enter утверждает, текст уходит правкой, меню команд при ожидании не открывается, Ctrl+C отменяет конвейер и возвращает строку ввода в обычный режим.

**Содержание**. В `pipeline.py`:

```python
@dataclass
class PlanReview:
    future: asyncio.Future   # результат: "" — утверждаю, иначе текст правок
```

В `cli.State` — `awaiting_plan: PlanReview | None = None`.

В `handle_submit` ветка **третьей по счёту, но обязательно ДО** строк
`text = raw_text.strip()` / `if not text: return` — иначе пустой Enter «утверждаю» будет
проглочен ранним возвратом и до режима не дойдёт:

```python
if state.awaiting_plan is not None:
    review = state.awaiting_plan
    state.awaiting_plan = None
    if not review.future.done():
        review.future.set_result(raw_text.strip())
    return
```

В `HarnessCompleter.get_completions` — `awaiting_plan` в ранний выход рядом с `awaiting_key` и
`awaiting_custom`: иначе правка, начатая с «/», откроет меню команд, и Enter подставит
дополнение вместо отправки правки.

Подсказка печатается в ленту главного экрана в момент показа плана — тем же приёмом, что
приглашение ввести ключ: `«Enter — утверждаю · текст — правки · Ctrl+C — отменить»`.

## Шаг 15. Оркестратор: постановщики параллельно

**Файлы**: `src/myharness/pipeline.py`, `tests/check_units.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Запросы исполнителей пишутся до утверждения»
**Проверка**: на три пункта уходит три запроса, одновременно не больше `concurrency`; не ответивший постановщик даёт пометку, а не пустой запрос.

**Содержание**.

```python
async def write_requests(state, plan: Plan, settings: Settings, run_id: str) -> None
```

По агенту на пункт — `Agent(f"постановщик:{item.id}", plan_mod.writer_profile(settings))`,

нельзя, а валить весь прогон из-за одного пункта — тем более: человек увидит пометку при

## Шаг 16. Оркестратор: цикл утверждения и правок

**Файлы**: `src/myharness/pipeline.py`, `src/myharness/plan.py`, `tests/check_app.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Правки уходят планировщику с прежним планом»
**Проверка**: правка порождает второй запрос планировщику, несущий прежний план и текст правки; изменённые пункты помечены в новом показе; цикл повторяется до пустого Enter.

**Содержание**. В `plan.py` — `def changed_ids(old: Plan | None, new: Plan) -> set[str]`:
сравнивает `work`, `depends_on`, `executor`, `check`, `max_tokens`, `request`; пункт, которого в
прежнем плане не было, считается изменённым.

В `pipeline.py`:

```python
async def approve(state, plan: Plan, changed: set[str]) -> str
```

Печатает `ui.plan_fragments(plan, changed)` и подсказку в главный экран, ставит
`state.awaiting_plan = PlanReview(future)`, ждёт `future`. Возвращает `""` (утверждено) либо
текст правок.

Цикл в `run`: планирование → постановка → показ → правки → `revision_request` → снова разбор и
постановка → показ с пометками. Выход из цикла только по пустому ответу.

## Шаг 17. Оркестратор: исполнение волнами и экраны исполнителей

**Файлы**: `src/myharness/pipeline.py`, `src/myharness/screens.py`, `tests/check_app.py`
**Требование**: `openspec/specs/pipeline/spec.md` → «Пункты исполняются волнами», `openspec/specs/interface/spec.md` → «Исполнители видны в списке агентов»
**Проверка**: независимые пункты идут одновременно, зависимые — после; экраны заводятся на ходу; второй прогон не дописывает в ленты первого; пункт с невыполненной зависимостью пропускается, независимые ветки доработывают.

**Содержание**.

```python
async def execute(state, plan: Plan, settings: Settings, run_id: str) -> dict[str, str]
```

Волны — `for wave in plan_mod.waves(plan): await asyncio.gather(*(run_item(i) for i in wave))`,
всё внутри одной корутины. **Ни одной задачи наружу** — задача, живущая сама по себе, отмены от
Ctrl+C не получит. **Без `return_exceptions=True`** — он превратил бы отмену в элемент списка,
и очередь запросов о ней не узнала бы; ошибки модели этим не теряются, потому что `run_turn`
при сбое не бросает, а возвращает результат с признаком неуспеха.

Экран на пункт: `Screen(key=f"{run_id}:{item.id}", title=item.work[:40],
profile=plan_mod.executor_profile(item))`. Номер прогона в ключе обязателен: без него второй
запуск конвейера продолжил бы ленты первого — та же беда, из-за которой в наборе способов
появился составной ключ вкладки шага. Экраны прежнего прогона выбрасываются в начале нового.

Ограничитель одновременности — тот же `Semaphore(settings.concurrency)`, общий на волну.

Пункт, у которого хоть одна зависимость не дала ответа, не запускается: в его ленту пишется
`✕ пункт пропущен: зависимость 2 ответа не дала`, ответа в `answers` он не оставляет, и его
потомки пропускаются тем же правилом. Независимые ветки продолжают работать — это новое правило
против «цепочка прервана» у набора способов, и оно записывается в требования.

## Шаг 19. Попутная ошибка: словарь окон панелей

**Файлы**: `src/myharness/cli.py`, `tests/check_units.py`
**Требование**: `openspec/specs/interface/spec.md` → «Прокрутка принадлежит панели»
**Проверка**: панель, заведённая после выброса прежней, получает своё окно, а не чужую прокрутку.

**Содержание**. Словарь окон в `build_app` ключуется по `id(pane)` и никогда не чистится.
`id()` в Python после сборки мусора переиспользуется, поэтому новая панель может унаследовать
окно старой вместе с её прокруткой. Сегодня панели выбрасываются редко и это сходит с рук;
конвейер создаёт и выбрасывает их каждый прогон. Ключ меняется на саму панель
(`dict[screens_mod.Pane, LogWindow]` — `Pane` не хешируется как `dataclass(eq=True)`, поэтому
объявить его `@dataclass(eq=False)`, тогда работает хеш по личности объекта, а сравнение
панелей по значению нигде не используется).
