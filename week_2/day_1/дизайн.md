# Дизайн: День 6 — первый агент

## Задача и видение

**Условие дня.** Агент принимает запрос пользователя, отправляет его в LLM через API, получает
ответ, выводит результат в интерфейсе. Важно: агент — **отдельная сущность**, а не один вызов
API; логика запроса и ответа **инкапсулирована в агенте**.

**Видение пользователя, подтверждённое ментором** (три уточнения из переписки):

1. Сущность держит системную инструкцию, параметры генерации, отправку и приём — наружу отдаёт
   только результат. Ментор добавил: она же берёт на себя **складывание стека сообщений**.
2. Это «коробка» со своей политикой входа, политикой выхода и, если нужен, своим судьёй —
   отдельный модуль внутри приложения, изолированный от остальных. Ментор: «максимально точно».
3. Устройство обязано выдерживать **сто агентов с разными настройками**, поднятых мгновенно.
   Ментор: не сто копий приложения, а один процесс и сто экземпляров агента внутри.

**Дополнительное задание пользователя:** режим, в котором инструмент не ждёт человека в цикле, а
сразу исполняет то, что сказано в конфигурации.

## Что решили и почему

### Агент — модуль `agent.py`, не отдельная служба

Отдельная служба по REST отвергнута: инструмент однопользовательский и терминальный, сеть между
своими частями добавила бы задержку и точку отказа при нулевой выгоде.

Изоляция обеспечивается проверяемым фактом, а не обещанием: `agent.py` не импортирует ни
`prompt_toolkit`, ни `screens`, ни `cli`. Признак — `grep -rn "from \. import cli" src/myharness/`
даёт ноль.

### Внутреннее устройство

```
Agent  (один экземпляр = один разговор)
├─ политика входа   системная инструкция; окно истории (N пар); обрезка блоками по
│                   границам пар; аварийный потолок по объёму; новый вопрос ровно один раз
├─ обмен            вызов клиента, разбор потока событий; куски уходят вниз, в обработчик
│                   отрисовки
├─ политика выхода  пустой ответ — не успех; обрыв по max_tokens отмечен, а не выдан за целый
│                   ответ; при ошибке или отмене висячий вопрос снимается с истории;
│                   запись в журнал прогонов при любом исходе
├─ судья            сегодня — детерминированные проверки выхода выше. Судья-модель отложен.
│                   Пустой заглушки не заводим: пустой ящик с подписью хуже его отсутствия
└─ память           свой стек сообщений; снаружи его не трогает никто
```

Открытый интерфейс:

```python
class Agent:
    def __init__(self, name: str, profile: Profile) -> None: ...
    async def exchange(self, client, model, content, *,
                       on_event=None, agent=None, run_id=None) -> Turn: ...
    def forget(self) -> None: ...
    def history(self) -> list[dict]: ...   # копия, только для чтения
```

Единственное возвращаемое значение — `Turn`. `on_event` — не выход наружу, а вывод вниз: агент
через него отдаёт, а не отчитывается.

### Три спорных решения, принятых явно

| Вопрос | Решение | Почему |
|---|---|---|
| Клиент API | **аргумент вызова**, не поле агента | `/auth` подменяет клиент на живом инструменте (`cli.py:491`), `/model` меняет модель (`cli.py:500`), проверки подставляют клиент в `State` (`check_app.py:99`). Поле сломало бы все три. Оно же сделало бы сто агентов сотней пулов соединений |
| Журнал прогонов | **пишет агент**, через развязанный `journal.append` | Запись обязана произойти и при отмене по Ctrl+C: сейчас она в `finally` (`cli.py:406-423`). Вынести наружу — потерять записи об отменённых прогонах. `journal.append` — чистая функция, возвращает текст ошибки, не бросает; показ предупреждения остаётся снаружи |
| Составные режимы | **экземпляр агента на исполнителя** | Иначе настройки едут параметром в каждый вызов — ровно то, от чего уходим. И четыре одновременных запроса группы писали бы в одну историю |

Группа экспертов, цепочка шагов и набор способов — **оркестраторы над множеством агентов**, а не
агенты: своей сессии с моделью у них нет. Ведущий группы — агент без истории, его вход
синтезируется из ответов экспертов.

### Потоковый вывод против «наружу только результат»

Противоречие мнимое: результат и вывод — два разных выхода, и второй не обязан быть
возвращаемым значением. Инкапсуляция ломается не тогда, когда наружу идут куски текста, а когда
наружу утекают клиент, формат сообщений и правило складывания стека. Сейчас утекает всё три.

Механизм — **функция обратного вызова**, не асинхронный генератор. Два независимых довода:

* `asyncio.gather`, на котором держится параллельность в `team.py`, с генераторами не работает;
* над `client.stream_chat` уже есть один асинхронный генератор, и он **уже** стоил обхода дефекта
  библиотеки (`api.py:101-106`, `cli.py:1140-1159`). Второй слой — сознательно наступить на те же
  грабли.

### Память — скользящее окно, не сжатие

Экономического довода за управление памятью почти нет: за сеанс в 50 обменов экономия ~13 центов.
Настоящие причины две: сеанс упирается в стену контекста примерно на сотом обмене (или на первом,
если в вопрос вставлен файл), и модель дрейфует на длинной истории уже обменов с тридцати.

Взято: окно по числу обменов (умолчание 10 пар), **обрезка блоками** (дошли до 15 пар — выбросили
5), только по границам пар «вопрос — ответ», сообщение пользователю о факте обрезки, аварийный
потолок по объёму.

Сжатие истории отвергнуто сознательно, в пользу приёма «избегать пересказа» из обучающего
материала: пересказ дешевле, но вносит в разговор текст, которого никто не говорил, и отладить
это потом нечем. Забывание честнее — пользователь видит строку об обрезке.

Правила обрезки, нарушение которых ломает разговор молча:

* никогда не выбрасывать системную инструкцию, текущий вопрос и последнюю полную пару;
* резать только целыми парами: ответ без вопроса заставляет модель защищать свою реплику,
  вопрос без ответа — отвечать второй раз;
* после системной инструкции первым обязан идти `user`, иначе сервер откажет в случайный момент.

**Гипотеза, требующая проверки на живом прогоне:** блочная обрезка сохраняет неизменным начало
запроса четыре хода из пяти, а значит и льготную цену повторно используемого начала
(`prompt_cache_hit_tokens` в `usage`). Полей `usage` мы ещё не видели — журналов в репозитории
нет. Результат замера идёт в отчёт как факт, а не как ожидание.

### Пакетный наряд — задание без человека в цикле

Файл наряда (JSON) описывает, кого поднять и что спросить; один профиль-заготовка плюс подстановка
`vars` (механизм уже есть в `profiles.py`) описывает сто разных агентов двадцатью строками.

```json
{ "model": "deepseek-v4-flash", "concurrency": 8,
  "tasks": [ { "agent": "физик", "profile": "expert",
               "vars": {"область": "физика"}, "ask": "..." } ] }
```

Запуск `myharness --batch наряд.json`: интерфейс не поднимается, человека никто не ждёт,
результаты идут в журнал, на экран — сводка.

**Это проверка изоляции делом.** Если агент действительно развязан от интерфейса, режим пишется
в ~80 строк и не импортирует `prompt_toolkit` ни разу. Декларацию «модуль изолирован» проверить
нечем, а этот режим либо запускается без терминала, либо нет.

Настоящее ограничение — не число агентов, а число одновременных запросов: сто разом упрутся в
пределы частоты поставщика. Ограничитель одновременности обязателен, умолчание 8.

## Отвергнутые подходы

| Отвергнуто | Причина / порог возврата |
|---|---|
| Узкий разрез (агент только для главного экрана) | Оставил бы **два разных механизма истории** — `Agent.messages` и `Pane.messages`. Похожие функции ведут себя предсказуемо, два механизма расходятся молча. Хуже нынешнего состояния, а не лучше |
| Агент владеет клиентом API | Сто агентов = сто пулов соединений и сто закрытий по 50 мс. Ломает `/auth`, `/model` и подстановку клиента в проверках |
| Асинхронный генератор событий наружу | Не работает с `asyncio.gather`; второй слой над уже проблемным генератором |
| Общая очередь событий | Самая чистая граница, но лишний долгоживущий цикл и адрес панели, просачивающийся в событие. Порог: появление второго потребителя событий |
| Судья-модель | Отдельный день. Сегодня судья — детерминированные проверки выхода |
| Сжатие и пересборка истории | Вносит несказанное; проверить детерминированно нельзя |
| Векторная память | Нужна вторая модель и хранилище. Порог: корпус, переживающий сеанс и не влезающий в окно |
| Послойная память | Порог: второй пользователь или общее хранилище между сеансами |
| Саморефлексивная память | Порог: хранение между запусками плюс интерфейс просмотра и удаления — иначе молча накопит неверные факты |
| Память по правилам | **Уже есть**: профиль с системной инструкцией. Второй такой механизм не нужен |
| Ветви по темам | Не приём памяти, а свойство интерфейса. Отложено, не отвергнуто |
| TOON | В запросе нет структурированных данных |
| Отдельная служба по REST | Однопользовательский терминал; сеть между своими частями — задержка и точка отказа даром |
| Планирование, инструменты, вызов функций | Дни про `PLANNING` и `TOOL ORCHESTRATION` из обучающего материала |

## Затронутые способности

Новые: `openspec/specs/agent/` (сущность, политики, память), `openspec/specs/batch/` (наряд без
человека в цикле).

Правятся: `profiles` (окно истории), `commands` (`--batch`, поведение `/clear`), `interface`
(панель без истории), `team` и `methods` (переформулированы через агентов и оркестраторы),
`journal` (кто пишет запись).

Не трогаются: `api`, `params`, `config`, `work-screens`.

## Границы: что делаем

1. `agent.py` — сущность с политикой входа, обменом, политикой выхода, своей памятью. Все четыре
   пути инструмента идут через неё.
2. `output.py` — вывод в ленту отдельно; круговая зависимость исчезает совсем.
3. `Pane.messages` удаляется — история уезжает из элемента интерфейса.
4. Скользящее окно памяти с блочной обрезкой и сообщением об обрезке.
5. Пакетный наряд `--batch` с ограничителем одновременности.
6. Проверки агента без терминала и без сети (см. ниже).

## Как проверяем

Разделение, принятое по итогам разведки: **unit-проверки покрывают детерминированный каркас,
оценки — то, что предсказать нельзя.** После перестройки весь агент детерминирован при подставном
клиенте, поэтому сегодня достаточно первой ступени — это правильная граница, а не срезанный угол.

Три ступени по возрастанию цены, берём первые две:

1. **Правила** — точное совпадение, длина, наличие подстроки, соответствие схеме. Мгновенно и
   бесплатно.
2. **Золотой набор** — список входов с ожидаемым поведением.
3. **Судья-модель** — отложено.

Подставляем на границе клиента, а не внутри логики агента; граница уже есть — `FakeClient`
(`check_app.py:45`).

**Правило, нарушение которого обесценивает весь набор: ожидаемые значения не пишет ИИ.** Модель,
сочиняя ожидания, закрепляет текущее поведение, включая ошибочное. Ожидания считаются руками.

Сценарии (все — `check_units.py`, подставной клиент, без `prompt_toolkit`):

1. Сборка сообщений: инструкция первой; при `keep_history=false` ровно `[system, user]`; при
   `keep_history=true` вопрос дописан **ровно один раз**.
2. **Два вопроса подряд с историей** дают `u, a, u, a`. Сегодня такой проверки нет нигде.
3. Висячий вопрос снят при сбое: история не выросла.
4. Порядок событий: `reasoning` → `content` → `meta`; склейка кусков равна `turn.text`.
5. Отмена по Ctrl+C: `CancelledError` проброшен, история чиста, в журнале запись со статусом
   не `ok`.
6. Журнал: один обмен — одна запись; `agent` и `run_id` только когда переданы; ключа нет никогда.
7. `Turn.ok` и `Turn.error` при исключении клиента.
8. **Два агента параллельно не смешивают истории.**
9. Ошибка обработчика отрисовки не выдаётся за ошибку сети.
10. Окно памяти: обрезка блоками, только по границам пар, инструкция и последняя пара на месте.
11. **Сто агентов с разными настройками создаются в одном процессе** — замер времени, без сети.

## Риски и чем расплачиваемся

1. **Весь риск в одном шаге** — перенос самого обмена (112 строк, где перемешаны поток, рисование,
   история и журнал). Прикрыт существующими проверками полного приложения (~90 утверждений на все
   четыре пути). Не сходится за 40 минут — откатываем шаг, остальное остаётся рабочим.
2. **Дыра в покрытии до начала работ:** ни одна проверка не задаёт два вопроса подряд при
   включённой истории — все профили проверок с `keep_history: false`. Закрывается нулевым шагом,
   до единой правки исходного кода.
3. **Две сборки сообщений различаются побочным действием**, а не видом: `screens.build_messages:107`
   дописывает вопрос в историю сама, `cli.build_request_messages` — нет. Слить неаккуратно —
   вопрос попадёт дважды или не попадёт; вылезет только на втором вопросе подряд.
4. **Гипотеза о выгоде блочной обрезки не проверена** (см. выше). В отчёт идёт замер, а не ожидание.
5. **Сто агентов упрутся в пределы частоты поставщика** — ограничитель одновременности обязателен.
6. **День без запаса:** ~7 ч 20 мин. Если время кончится, режется слой памяти (пункт 4 границ) —
   он из обучающего материала, а не из условия дня. Резать только с ведома пользователя.

## Демонстрация

На видео — наряд на пару агентов, не на сотню: сотня остаётся свойством устройства и проверяется
замером в `check_units.py`, а не номером на экране.
