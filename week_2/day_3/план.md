## Как проверяем

- **Логика** (счёт токенов, тариф, калибровка, бюджет, поля журнала) — строгий цикл:
  сначала проверка, убедиться, что падает, потом код, потом убедиться, что проходит.
- **Текстовый интерфейс** (строка ожидания, свёртка размышлений, команды) — прогон по
  записанному сценарию в `check_app.py` плюс ручной прогон живого запуска.
  Строгий цикл на отрисовку стоит дороже пользы: проверка там сводится к сверке текста,
  который сам же и пишется в шаге.

## Шаг 2. Счёт текста и предсказание веса запроса

**Файлы**: `myharness/src/myharness/tokens.py`, `myharness/tests/check_units.py`
**Требование**: `openspec/specs/tokens/spec.md` → «Точный счёт офлайн», «Вес запроса известен до отправки»
**Проверка**: строгий цикл. Проверки в `check_units.py`: пустой список сообщений даёт надбавку;
счёт текста монотонен; при `MYHARNESS_TOKENIZER=/несуществующий/файл` счёт идёт запасным путём и
`exact()` возвращает `False`.
**Содержание**:
```python
BASE_OVERHEAD = 83          # измерено 2026-09-09 на четырёх запросах к deepseek-v4-pro
PER_MESSAGE_OVERHEAD = 1.5  # там же: 4 реплики дали 87 вместо 83
FALLBACK_CHARS_PER_TOKEN = 3.5

def vocabulary_path() -> Path       # $MYHARNESS_TOKENIZER либо data/deepseek_v4_tokenizer.json
def exact() -> bool                 # словарь и библиотека на месте
def count_text(text: str) -> int    # точно либо len(text)/FALLBACK_CHARS_PER_TOKEN
def count_messages(messages: list[dict], *, overhead: int = BASE_OVERHEAD) -> int
```
Словарь грузится лениво, один раз, в модульную переменную; отсутствие библиотеки или файла —
не ошибка, а переход на запасной путь. Ключевое: `count_messages` считает только тексты
сообщений плюс `overhead + PER_MESSAGE_OVERHEAD * (len(messages) - 1)`, округление вниз.

## Шаг 3. Тариф и деньги

**Файлы**: `myharness/src/myharness/tokens.py`, `myharness/tests/check_units.py`
**Требование**: `openspec/specs/tokens/spec.md` → «Деньги считаются по таблице с датой»
**Проверка**: строгий цикл. Известная модель и `usage` с попаданиями в кэш дают ожидаемое число;
час пик удваивает цену; незнакомая модель даёт `None`, а не ноль.
**Содержание**:
```python
@dataclass(frozen=True)
class Tariff:            # доллары за миллион токенов, льготные часы
    cache_hit: float
    cache_miss: float
    output: float

TARIFFS = {              # снято 2026-09-09 с https://api-docs.deepseek.com/quick_start/pricing
    "deepseek-v4-flash": Tariff(0.007, 0.22, 0.66),
    "deepseek-v4-pro": Tariff(0.022, 0.66, 1.98),
    "deepseek-v4-flash-vision-exp": Tariff(0.007, 0.22, 0.66),
}
PEAK_WINDOWS = ((1, 4), (6, 10))   # часы UTC, пн–пт; в них тариф вдвое дороже

def peak(moment: datetime) -> bool
def price(usage: dict, model: str, moment: datetime | None = None) -> float | None
def format_price(dollars: float) -> str   # < $0.01 — центами: «0.04 ¢», иначе «$1.24»
```
Незнакомая модель даёт `None` — показ обязан сказать «тариф неизвестен», а не соврать нулём.

## Шаг 4. Накопление расхода

**Файлы**: `myharness/src/myharness/tokens.py`, `myharness/tests/check_units.py`
**Требование**: `openspec/specs/tokens/spec.md` → «Итог сеанса складывается из обменов»
**Проверка**: строгий цикл. Сложение двух `usage` даёт покомпонентную сумму; пустой `usage`
ничего не портит; строка вместо числа в поле не роняет сложение.
**Содержание**:
```python
FIELDS = ("prompt_tokens", "completion_tokens", "total_tokens",
          "prompt_cache_hit_tokens", "prompt_cache_miss_tokens", "reasoning_tokens")

def normalize(usage: dict) -> dict[str, int]   # достаёт reasoning_tokens из completion_tokens_details
def add_usage(acc: dict[str, int], usage: dict) -> dict[str, int]
def total_usage(items: Iterable[dict]) -> dict[str, int]
```
`normalize` — единственное место, где разбирается вложенность ответа DeepSeek. Нечисловые
значения отбрасываются: `usage` приходит от сервера, и падать на нём нельзя.

## Шаг 5. Счётчики сеанса, калибровка и вес истории в агенте

**Файлы**: `myharness/src/myharness/agent.py`, `myharness/tests/check_units.py`
**Требование**: `openspec/specs/agent/spec.md` → «Агент считает расход текущего сеанса»
**Проверка**: строгий цикл. Агент после двух поддельных обменов несёт покомпонентный
`session_usage`; восстановление пар с диска `session_usage` не меняет и `history_tokens()`
увеличивает; после обмена, где сервер вернул `prompt_tokens`, надбавка агента подстроена.
**Содержание**:
- поля: `self.session_usage: dict[str, int] = {}`, `self._overhead = tokens.BASE_OVERHEAD`,
  `self.restored_pairs = 0` (пополняется в `restore`);
- `def history_tokens(self) -> int` — сумма `tokens.count_text` по `self._messages`; это вес
  памяти, который уйдёт в следующий запрос, без системной инструкции и без нового вопроса;
- `def predict_tokens(self, messages: list[dict]) -> int` — `tokens.count_messages(messages, overhead=self._overhead)`;
- в `exchange` перед запросом запомнить `text_tokens` (предсказание без надбавки) и
  `predicted = self.predict_tokens(request_messages)`;
- в `finally`: `self.session_usage = tokens.add_usage(self.session_usage, usage)`, и если сервер
  вернул `prompt_tokens` — `self._overhead = max(0, usage["prompt_tokens"] - text_tokens)`.
  Калибровка на агента и на сеанс: число в коде — начальное приближение, а не закон.

## Шаг 6. Бюджет запроса в обрезке памяти

**Файлы**: `myharness/src/myharness/agent.py`, `myharness/src/myharness/profiles.py`, `myharness/tests/check_units.py`
**Требование**: `openspec/specs/agent/spec.md` → «Обрезка срабатывает и по весу запроса»
**Проверка**: строгий цикл. Профиль с `budget_tokens=200` и памятью, перевешивающей бюджет,
после сборки запроса теряет пары блоками по пять; при `budget_tokens=0` поведение не меняется
ни на одну пару; последняя пара не выбрасывается никогда.
**Содержание**:
- `Profile.budget_tokens: int = 0` (0 — бюджет выключен), разбор из JSON профиля и строка в
  `Profile.snapshot()`;
- `_trim` получает довесок: `def _trim(self, content: str) -> int`, и после двух действующих
  ограничителей — третий цикл: пока `budget_tokens > 0` и предсказанный вес собранного запроса
  больше бюджета и в памяти больше одной пары — выбрасывать `WINDOW_SLACK_PAIRS` пар (или
  остаток, если их меньше), считая выброшенные;
- `build_messages` передаёт в `_trim` текст вопроса: без него вес запроса неизвестен;
- порядок сохранён: обрезка идёт до сборки, иначе ограничение не работает там, ради чего заведено.

## Шаг 10. У каждого запроса своя строка ожидания, и она замирает

**Файлы**: `myharness/src/myharness/output.py`, `myharness/tests/check_app.py`
**Требование**: `openspec/specs/interface/spec.md` → «Строка ожидания несёт живой расход»
**Проверка**: прогон по сценарию: во время потока строка `думаю…` несёт `↑`/`↓`/`Σ` и числа
меняются; после ответа строка осталась в ленте со знаком исхода и серверными числами; после
второго вопроса в ленте ДВЕ строки, и числа в первой не изменились.
**Содержание**:
- строка ожидания печатается один раз, в начале обмена, и дальше **заменяется на месте**, а не
  переписывается обрезкой ленты: `marks["wait_at"]` — номер первого фрагмента строки,
  `marks["wait_len"]` — сколько их. Помощник
  `_show_wait(state, pane, marks, *, mark, frozen=False)` собирает строку и кладёт её срезом
  `pane.log[at:at + length] = fragments`. Строка всегда занимает ровно одну строку ленты, поэтому
  `line_count` не меняется, а печать ответа ниже ей не мешает — обрезка ленты из этого места
  уходит совсем;
- `marks` пополняются: `"outgoing"` (предсказание, кладёт `run_turn` до запроса),
  `"incoming"` (растёт на единицу за каждое событие потока рода «рассуждение» и «содержимое» —
  замер показал кусок = токен), `"session"` (итог сеанса до этого обмена);
- `draw_event` со строкой ожидания больше ничего не делает: печатает свой кусок ниже;
- в `finally` у `run_turn` строка замирает: знак исхода (`ok`/`error`/`cancelled`), числа —
  серверные из `usage`, если они пришли, иначе последние живые с пометкой `~`. Стирания строки
  нет ни в одном пути: у каждого запроса своя строка, и она остаётся в ленте навсегда.

**Файлы**: `myharness/src/myharness/output.py`, `myharness/src/myharness/ui.py`, `myharness/tests/check_app.py`

## Шаг 14. Требования OpenSpec
