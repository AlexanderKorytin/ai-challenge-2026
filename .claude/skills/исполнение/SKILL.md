# /исполнение — работа по плану

Стадия `Executing`. Вход — согласованный `week_<N>/day_<M>/план.md`.

Язык — русский, транслитерация запрещена.

## Роли

| Роль | Что получает | Что делает |
|---|---|---|
| **Исполнитель** | один шаг плана целиком, без истории беседы | пишет код, гоняет проверки, останавливается на границе шага |
| **Проверяющий** | текст шага и различия по коду | отвечает на два вопроса: сделано ли то, что требовалось, и годен ли код |
| **Повторный проверяющий** | только различия исправления | отвечает на один вопрос: снято ли замечание |
| **Итоговый проверяющий** | ветка целиком | смотрит связность всего, что сделано за день |

Смысл разделения: каждый получает ровно нужное. Исполнитель, которому вывалили весь день
беседы, теряет шаг из виду; проверяющий, который сам писал код, не видит в нём изъянов.

## Порядок

1. Взять очередной шаг плана.
2. Отдать шаг агенту-исполнителю. Задание самодостаточное: путь к файлу, требование, проверка,
   содержание — всё из плана, плюс ограничение «за границы шага не выходить».
3. Отдать различия отдельному агенту-проверяющему. Не проверять свою работу самому.
4. Замечания есть — исполнитель правит, повторный проверяющий смотрит **только исправление**,
   а не весь код заново. Пересмотр всего кода на каждой итерации — самый дорогой способ ничего
   не найти.
5. Замечаний нет — фиксация в git, следующий шаг.

**Независимые шаги запускать одним ответом** — тогда исполнители работают одновременно. Условие
независимости жёсткое: шаги трогают разные файлы и результат одного не нужен другому. Если
сомневаешься — значит, зависимы, делать по очереди.

Собирая результаты параллельных исполнителей: сверить, не правили ли они одно и то же место,
и прогнать весь набор проверок целиком, а не только тесты затронутых шагов.

## Границы

- Из плана не выходить. Всплыло нужное, чего в плане нет, — вернуться в `/план` или `/штурм`
  (переходы `Executing → Research` разрешены), а не дописывать по ходу.
- Не принимать «потом поправим» и «сойдёт для прототипа»: временные решения становятся
  постоянными. Если пользователь настаивает на костыле — риски назвать вслух и записать в отчёт.
- Поменялось поведение `myharness` — в том же шаге обновить `openspec/specs/<способность>/spec.md`
  и прогнать `openspec validate --specs --strict`.

## Конец стадии

Все шаги закрыты → объявить переход `Executing → Validation` и вызвать навык `/проверка`.
