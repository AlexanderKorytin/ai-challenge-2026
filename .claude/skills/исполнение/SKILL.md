# /исполнение — работа по плану

Стадия `Executing`. Вход — согласованный план (`week_<N>/day_<M>/план.md` либо план из чата).

Язык — русский, транслитерация запрещена.

## Роли

| Роль | Кем запускается | Что получает | Что делает |
|---|---|---|---|
| **Исполнитель** | `general-purpose`, модель `opus` | один шаг плана целиком, без истории беседы | пишет код, останавливается на границе шага |
| **Проверяющий** | `general-purpose`, модель `opus` | текст шага, его критерий и относящиеся к шагу изменения | отвечает на два вопроса: сделано ли то, что требовалось, и годен ли код |
| **Повторный проверяющий** | `general-purpose`, модель `opus` | исходное замечание, критерий его снятия и только изменения исправления | отвечает на один вопрос: снято ли замечание |
| **Разбор рисков** | навык `/security-review` | шаг, где цена ошибки — утечка, необратимое действие или чужой ввод в роли указаний | называет угрозу и остаточный риск |
| **Итоговый проверяющий** | `general-purpose`, модель `opus` | изменения всей задачи целиком | смотрит связность того, что сделано |
| **Механика** | `general-purpose`, модель `haiku` | поручение без выбора: перенос, переименование, сверка списков | делает ровно сказанное |

Исполнение и проверка идут на `opus`: там цена ошибки максимальна, и экономить нельзя. Дешевле
берётся только работа без выбора — механические поручения на `haiku`. Модель задаётся при
запуске помощника, а не переписыванием его определения.

Смысл разделения: каждый получает ровно нужное. Исполнитель, которому вывалили весь день
беседы, теряет шаг из виду; проверяющий, который сам писал код, не видит в нём изъянов.
Поэтому **свою работу не проверяет никто**, включая ведущего.

Помощник не видел разговора: путь к файлу, требование, критерий, содержание — всё из плана,
плюс ограничение «за границы шага не выходить».

## Порядок

1. Взять очередной шаг плана.
2. Отдать шаг исполнителю.
3. Отдать относящиеся к шагу изменения отдельному проверяющему.
4. Замечания есть — исполнитель правит, повторный проверяющий смотрит **только исправление** и
   получает исходное замечание. Пересмотр всего кода на каждой итерации — самый дорогой способ
   ничего не найти; различия без исходного вопроса — самый быстрый способ проглядеть недоделку.
5. Замечаний нет — ведущий фиксирует в git **файлы этого шага**, а не всё дерево разом, и
   переходит к следующему шагу.

**Независимые шаги запускать одним вызовом** средства запуска — тогда исполнители работают
одновременно. Независимость определена в плане полем «Зависит от» и единоличным владением
файлами; сомневаешься — значит, зависимы, делать по очереди.

## Что исполнителям запрещено

Пока над общим рабочим деревом одновременно идёт несколько шагов, исполнителям нельзя:

- запускать проверки, сборку и форматирование — чужая незаконченная правка даст ложное падение;
- фиксировать что-либо в git;
- трогать файлы, которыми владеет другой шаг.

Прогон проверок ведёт ведущий на неподвижном дереве: после того как исполнители закончили.
Строгий цикл «тест → падение → код → проход» от этого не отменяется — шаги, которым он нужен
внутри работы, план заранее пометил последовательными.

## Границы

- Из плана не выходить. Всплыло нужное, чего в плане нет, — вернуться в `/штурм`
  (переход `Executing → Research` разрешён), согласовать, обновить план и только потом делать.
  Прямого пути `Executing → Plan` нет.
- Не принимать «потом поправим» и «сойдёт для прототипа»: временные решения становятся
  постоянными. Если пользователь настаивает на костыле — риски назвать вслух и записать в отчёт.
- Поменялось поведение `myharness` — в том же шаге обновить `openspec/specs/<способность>/spec.md`.
  Общий прогон `openspec validate --specs --strict` делает ведущий на стадии `Validation`, а не
  каждый исполнитель посреди чужих правок.

## Конец стадии

Все шаги закрыты → объявить переход `Executing → Validation` и вызвать навык `/проверка`.
