# /задание — конвейер работы

Один вызов на задачу. Ведёт от условия и видения пользователя до подтверждённого результата.
Стадии и разрешённые переходы — из `CLAUDE.md`, этот навык их не заменяет, а наполняет
процедурами.

Язык всей работы — русский, транслитерация английских слов запрещена.

## Перед Research — выбрать ведущую среду

Выбрать **Claude Code** либо **OMP/OpenAI** до объявления `Research`. Одна выбранная среда ведёт
разговор, вызывает только свои нативные роли и отвечает за весь путь до `Done`. Передавать
начатую задачу между средами нельзя; другую среду можно выбрать только для следующей задачи.

```
условие + видение
   │
   ▼ Research     /штурм       разбор → профильные помощники параллельно → подходы → дизайн → «да»
   ▼ Plan         /план        одна наблюдаемая способность и договор на один просмотр; широкий шаг делится заранее
   ▼ Executing    /исполнение  быстрый: ведущий → независимый просмотр шва; полный: исполнитель → независимый просмотр → исправление → повторный просмотр → целевая проверка ведущим
   ▼ Validation   /проверка    итоговый независимый просмотр связности → исправления → один полный проход на неподвижном дереве
   ▼ Report       /отчет       для дня — запись экрана, Google Диск, GitHub; для общей задачи — сводка
   ▼ Done         результат подтверждён пользователем
```

## Сначала — какого рода работа

| Род | Признак | Что заводим |
|---|---|---|
| **Задание дня** | пришло условие дня челленджа | папку дня, ветку дня, строку в таблице заданий, видеоотчёт |
| **Общая задача** | правка инструмента, навыков, документации, соглашений | ничего из перечисленного: работаем в `main`, отчёт — сводкой в чате |

Стадии и утверждения одинаковы для обоих родов. Различается только то, где живут артефакты и
чем кончается стадия `Report`. Ошибиться родом дорого: лишняя ветка и папка дня для общей
правки разводят инструмент по веткам, откуда его потом собирать вручную.

## Задание дня: что делается до ветки и что после

Первым идёт `Research`, и он же отвечает на вопрос, **нужна ли правка общего инструмента**.
Ответ решает порядок дальнейшего:

- **правка нужна** — она идёт в `main` своим проходом по стадиям, со своим утверждением и
  фиксацией, и только после этого заводится ветка дня. Так ветка дня с рождения несёт
  актуальный инструмент, и подтягивать `main` в неё задним числом не приходится;
- **правка не нужна** — ветка дня заводится сразу.

Поэтому пункты ниже выполняются **после** `Research`, а не до него. До `Research` не заводится
ничего: ни ветка, ни папка, ни `README.md`.

1. **Завести ветку дня** — `w<номер недели>d<номер дня>`, от `main`, своей рабочей копией:
   `git worktree add ~/challenge/w2d4 -b w2d4 main`. Ветки первой недели названы иначе
   (`day2-fish-facts` и подобные) — это историческое исключение, переименованию не подлежит.
   Ветка дня в `main` не сливается.
2. **Завести папку дня** `week_<N>/day_<M>/` — **только если пользователь этого просил**
   (правило `CLAUDE.md`). Перед созданием проверить, что папки нет, чтобы не затереть работу.
   Папки нет — нет и её `README.md`: артефакты дня появляются вместе с папкой, а не до неё.
3. **Прочитать требования** затронутых способностей в `openspec/specs/` — это источник правды
   по действующему поведению `myharness`, а не таблица в `CLAUDE.md`. Читать их надо ещё в
   `Research`; здесь пункт стоит как напоминание, что перед планом они прочитаны.
4. **Завести `week_<N>/day_<M>/README.md`** с постановкой задания. Дальше он пополняется по
   стадиям и в конце принимает ссылки.

## Перед первой стадией — для общей задачи

Ветка `main`, рабочая копия `~/challenge/main`, новых папок не заводим. Дизайн и план живут в
чате, если пользователь не попросил файлы. Требования правим там же, где они лежат, —
в `openspec/specs/`.

## Правила, действующие на всех стадиях

- **Стадию называть вслух** при каждой смене: «`Research → Plan`». Неразрешённых переходов нет.
  Из `Executing` в `Plan` напрямую нельзя: через `Research`, с новым утверждением.
- **Статусы обновлять самому**, без напоминаний: для дня — стадия в его `README.md` и строка в
  таблице заданий `CLAUDE.md`.
- **Право не соглашаться.** Видение пользователя ведёт к костылю, дыре в безопасности или
  техдолгу — возразить и предложить альтернативу. Настаивает — риски назвать и записать в отчёт.
- **Качество выше скорости.** «Потом поправим» и «сойдёт для прототипа» не принимаются.
- **Пользователь ничего не делает руками.** Весь код, запуск, отладка, git — на ведущем.
  Пользователю задача ставится только там, где нужен недоступный доступ: пароль, веб-консоль
  провайдера, секрет, разрешение macOS.
- **Попутно объяснять.** Пользователя учат с нуля: новые понятия разжёвывать, полезны параллели
  с миром Kotlin и JVM.
- **Живые прогоны — из песочницы** `week_<N>/day_<M>/test/`. Это порядок в файлах прогона, а не
  защитная граница: относительные и абсолютные пути наружу оттуда работают ровно так же.

## Кто выполняет работу

Имена в двух правых столбцах нативны для своей среды. Подменять их именем из соседнего столбца
нельзя.

| Работа | Claude Code | OMP/OpenAI |
|---|---|---|
| **ведущий** | текущий разговор Claude Code | текущий разговор OMP |
| сбор фактов по коду и документации | `Explore` | `scout` на Luna |
| профильный разбор в `Research` | одно из десяти проектных имён на `opus` | одно из десяти имён из `.omp/agents/` на Astra |
| исполнение шага | `general-purpose` на `opus` | `task` на Sol |
| отдельная проверка шага, шва и итоговых изменений | `general-purpose` на `opus` | `reviewer` на Sol |
| разбор рисков безопасности | `general-purpose` на `opus` с узким поручением о рисках | `security-reviewer` на Sol |
| строго механическое поручение без выбора | `general-purpose` на `haiku` | `sonic` на Spark |
| фиксация в git | `general-purpose` на `haiku` | роль `commit` на Luna |

Ведущий сохраняет решения, утверждения и весь контекст задачи; помощник получает только
самодостаточное поручение своей роли. Экономить на профильном разборе, исполнении и проверке
нельзя: там цена ошибки максимальна.
