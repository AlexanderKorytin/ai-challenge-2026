# /задание — конвейер работы

Один вызов на задачу. Ведёт от условия и видения пользователя до подтверждённого результата.
Стадии и разрешённые переходы — из `CLAUDE.md`, этот навык их наполняет процедурами.

Язык всей работы — русский, транслитерация английских слов запрещена.

## Перед Research — выбрать ведущую среду

Выбрать **Claude Code** либо **OMP/OpenAI** до объявления `Research`. Одна выбранная среда ведёт
разговор, вызывает только свои нативные роли и отвечает за весь путь до `Done`.

```
условие + видение
   ▼ Research     /штурм       разбор → профильный разбор, если задача незнакома → подходы → дизайн файлом → «да»
   ▼ Plan         /план        шаги с причиной хода; живой прогон не зависит от интерфейса
   ▼ Executing    /исполнение  крупные ходы, независимый просмотр шва, целевая проверка
   ▼ Validation   /проверка    один просмотр связности → один полный проход → замер расхода
   ▼ Report       /отчет       для дня — запись экрана, Диск, GitHub; для общей задачи — сводка
   ▼ Done         результат подтверждён пользователем
```

## Рубежи очистки — главное правило расхода

Каждый обмен оплачивает весь накопленный контекст. Замер дней 7–12: 1,08 миллиарда токенов и
1872 доллара за шесть дней, при том что уникального текста в дне около миллиона. **Токен,
попавший в разговор на обмене i, оплачивается ещё (N−i) раз.**

**Рубеж ставится, когда накопленное сверх пола превысило стоимость восстановления** (план,
`git diff`, вердикты — 15–25 тысяч токенов). На практике это после каждого закрытого шага и на
каждой границе стадии. Правило считается, а не назначается числом: шаг из двух обменов, почти
ничего не накопивший, рубежа не требует.

**Рубеж запрещён** в трёх местах, где состояние живёт только в разговоре:

- посреди круга «замечание → исправление → повторный просмотр»;
- между написанием кода и его независимым просмотром — изменение останется в дереве без вердикта;
- посреди утверждения дизайна, пока не получено «да» и оно не записано.

### Носитель знания через рубеж

| что | где живёт |
|---|---|
| что сделано | `git diff` по карте файлов плана |
| вердикт просмотра | сообщение фиксации шага: «шаг N: способность; просмотрел — кто; сценарий — какой» |
| замысел и отвергнутое на уровне замысла | `дизайн.md` |
| границы модулей, шаги, ход, проверки | `план.md` |
| поведение инструмента | `openspec/specs/` |
| устные решения пользователя после плана, отвергнутое внутри шага, открытые вопросы | `docs/состояние-<задача>.md` |
| согласие пользователя на дизайн и на план | там же, строкой с датой |
| вердикт итогового просмотра стадии `Validation` и чем подтверждён результат | там же |
| род работы (задание дня или общая задача) и выбранная ведущая среда | там же, первой строкой |

**Файл состояния заводит ведущий первым делом на стадии `Research`** — первой строкой род работы
и выбранную среду — и дописывает его **перед каждым рубежом**, а не когда-нибудь. Он короткий и
содержит только то, чего в дереве нет вовсе.

**Подъём после рубежа**: прочитать `CLAUDE.md`, навык текущей стадии, дизайн, план, файл
состояния, затем `git log` с вердиктами и `git diff` по карте файлов плана — и объявить стадию
вслух. Читать историю разговора неоткуда: её нет, и в этом весь смысл рубежа. Без записанного вердикта
просмотра новый разговор не отличит просмотренное от непросмотренного — и правило «свою работу не
проверяет никто» сломается молча. Это единственная настоящая угроза от рубежей.

Что не переживает рубежа ничем: калибровка доверия к проверяющему и неявные приоритеты,
считанные с тона. Это принимается как потеря.

## Сначала — какого рода работа

| Род | Признак | Что заводим |
|---|---|---|
| **Задание дня** | пришло условие дня челленджа | папку дня, ветку дня, строку в таблице заданий, видеоотчёт |
| **Общая задача** | правка инструмента, навыков, документации, соглашений | ничего из перечисленного: работаем в `main`, отчёт — сводкой в чате |

Стадии и утверждения одинаковы. Ошибиться родом дорого: лишняя ветка и папка дня для общей
правки разводят инструмент по веткам.

## Задание дня: что до ветки и что после

`Research` идёт первым и отвечает, **нужна ли правка общего инструмента**. Нужна — она идёт в
`main` своим проходом по стадиям и своей фиксацией, и только потом заводится ветка дня. Не нужна
— ветка дня заводится сразу. До `Research` не заводится ничего.

1. **Ветка дня** — `w<неделя>d<день>`, от `main`, своей рабочей копией:
   `git worktree add ~/challenge/w2d4 -b w2d4 main`. Ветка дня в `main` не сливается.
2. **Папка дня** `week_<N>/day_<M>/` — только если пользователь просил.
3. **Требования** затронутых способностей в `openspec/specs/` прочитаны ещё в `Research`.
4. **`README.md` дня** с постановкой, дальше пополняется по стадиям.

## Правила, действующие на всех стадиях

- **Стадию называть вслух** при каждой смене. Из `Executing` в `Plan` напрямую нельзя: через
  `Research`, с новым утверждением.
- **Соразмерность цене ошибки.** Аппарат проверки оправдан там, где ошибка стоит денег, теряется
  молча или ложится на диск. У тренировочной задачи цена ошибки — переделать час работы.
- **Право не соглашаться.** Видение ведёт к костылю или дыре — возразить и предложить
  альтернативу; настаивает — риски назвать и записать в отчёт.
- **Пользователь ничего не делает руками.** Весь код, запуск, отладка, git — на ведущем.
  Задача пользователю ставится только там, где нужен недоступный доступ.
- **Попутно объяснять**: пользователя учат с нуля, полезны параллели с миром Kotlin и JVM.
- **Живые прогоны — из песочницы** `week_<N>/day_<M>/test/`.
- **Изложение в чат — короткое.** Дизайн и план лежат файлами; в разговор идёт выжимка и вопрос.

## Кто выполняет работу

| Работа | Claude Code | OMP/OpenAI |
|---|---|---|
| **ведущий** | текущий разговор | текущий разговор OMP |
| разведка по коду и документации | `Explore` | `scout` на Luna |
| профильный разбор, если задача незнакома | имя из `.claude/agents/` на `opus` | зеркало из `.omp/agents/` на Astra |
| исполнение шага | `general-purpose` на `opus` | `task` на Sol |
| независимый просмотр | `general-purpose` на `opus` | `reviewer` на Sol |
| разбор рисков безопасности | `general-purpose` на `opus`, узкое поручение | `security-reviewer` на Sol |
| механика без выбора: перенос, сверка, фиксация | `general-purpose` на `haiku` | `sonic` на Spark |

**Помощник получает одно поручение и возвращает один ответ.** Долгий разговор с помощником
запрещён, кроме круга снятия замечаний: в дне 9 медиана длины разговора помощника была 23
обмена, и помощники дали треть расхода дня.

## В конце задачи

Замерить расход: `python3 bin/расход.py --день <дата>` (задача заняла
несколько дней — `--с <дата> --по <дата>`) — вместе с помощниками, иначе видно
меньше половины.
