# /отчет — отчёт по работе

Навык только для рабочих копий челленджа AI SDLC — они живут в `~/challenge/`
(`~/challenge/main` для ветки `main`, `~/challenge/w<N>d<M>` для ветки дня). Запускается в самом
конце, **после** того как пользователь подтвердил результат — на переходе `Validation → Report`
из `CLAUDE.md`.

## Два вида отчёта

| Вид работы | Что делаем |
|---|---|
| **Задание дня** | запись экрана, Google Диск, отправка кода дня, ссылки в `README.md` дня и в чат |
| **Общая задача** | сводка в чате: что изменено, чем подтверждено, что осталось; фиксации в `main` уже сделаны по ходу |

Видео для общей задачи не записываем: показывать нечего, а ролик про правку документации —
работа ради формы. Всё, что ниже, относится к заданию дня.

## Разовая предварительная настройка (проверить при первом запуске)

- **Разрешение на запись экрана.** `ffmpeg` захватывает экран через `avfoundation` от имени
  приложения-хозяина этой оболочки. Без разрешения «Экранная запись» (System Settings → Privacy
  & Security → Screen Recording) процесс не отдаёт кадров. Тогда: остановить процесс через
  средство управления процессами по его имени, попросить пользователя выдать разрешение
  приложению-хозяину вручную и **полностью перезапустить** это приложение (macOS не подхватывает
  разрешение на лету) — тот редкий случай, когда действие может выполнить только пользователь.
- **GitHub.** `gh auth status` зелёный, `git remote -v` указывает на репозиторий челленджа.
- **Google Диск.** Папка отчётов: `AI SDLC Challenge`,
  id `1z12ya5LX-V0fsnBFgqpdqA52DLuydiu6`
  (https://drive.google.com/drive/folders/1z12ya5LX-V0fsnBFgqpdqA52DLuydiu6).
  Доступ «по ссылке — просмотр» пользователь выставляет папке один раз вручную в веб-интерфейсе;
  файлы внутри нужного `parentId` наследуют его автоматически.

## Ход работы

### 1. Определить день

Найти папку `week_<N>/day_<M>`, к которой относится работа. Уточнить у пользователя, если
неоднозначно.

### 2. Получить сценарий демонстрации у пользователя

Спросить, какой сценарий показать: какие команды и сообщения вводить, каких ответов дожидаться,
чем закончить. Дождаться ответа и следовать ему дословно — не импровизировать, не сокращать и
не добавлять шагов от себя.

Демонстрацию ведёт ведущий, а не пользователь — часть общего принципа «пользователь руками не
пишет». Пользователь показывает сам, только если явно так попросил.

Полноэкранной программе нужен настоящий терминал: подача строк в поток ввода её не заменяет.
Такую демонстрацию ведём через доступную автоматизацию видимого окна терминала. При русской
раскладке текст кладём в буфер обмена и вставляем Cmd+V: посылка кодов клавиш превращает
латиницу в кириллицу (`/profile` → `/ффффффф`).

### 3. Подготовить рабочую песочницу

Перейти в `week_<N>/day_<M>/test/` (создать, если нет) и вести прогон оттуда. Это порядок в
файлах прогона, **не** ограничение доступа: пути наружу оттуда работают как обычно. Рабочий
мусор прогона в git не отправлять без необходимости.

### 4. Определить устройство захвата экрана

```bash
ffmpeg -f avfoundation -list_devices true -i "" 2>&1
```

Взять номер перед `Capture screen 0`. Индекс меняется при подключении внешнего монитора —
проверять каждый раз заново, в навык не вписывать.

### 5. Начать запись

Файл — во временную папку вне репозитория (`*.mp4` и `*.mov` в `.gitignore`).

Запускать **средством управления долгоживущими процессами** под именем `запись-экрана`, с явным
рабочим каталогом. Обычный запуск команды здесь не годится: процесс живёт весь показ, ему
понадобится сигнал и ожидание выхода.

```
application: ffmpeg
args: -f avfoundation -i <индекс>:none -r 12 -pix_fmt yuv420p
      -vcodec libx264 -preset veryfast -crf 26 -y <путь>/day<M>_report.mp4
```

Строка `ffmpeg version …` доказывает только запуск программы, не захват. Подтверждение записи —
**растущий файл**: через 5–10 секунд его размер должен увеличиваться. Не растёт — остановить и
разбираться, начиная с разрешения на запись экрана.

### 6. Провести сценарий и остановить запись

Выполнить сценарий из шага 2 дословно. После последнего шага — послать процессу `запись-экрана`
сигнал `SIGINT` **по имени** и дождаться его выхода. Поиск процессов по образцу командной
строки и `kill -9` запрещены: под образец попадают чужие процессы, а жёсткое завершение
оставляет файл без правильного окончания, и он может не открыться.

Дождавшись выхода, проверить файл:

```bash
ffprobe -v error -show_entries format=duration,size -of default=noprint_wrappers=1 <файл>
```

Резать только с пересжатием, а не копированием потока: разрез по опорным кадрам съезжает на
секунды (при 12 кадрах в секунду опорный кадр примерно раз в 20 с).

```bash
ffmpeg -v error -ss <начало> -i <файл> -t <длительность> \
  -c:v libx264 -preset veryfast -crf 28 -pix_fmt yuv420p -movflags +faststart -y <обрезанный>
```

### 7. Выгрузить видео на Google Диск

```bash
rclone copy <файл> challenge:week_<N>/day_<M>/
rclone link challenge:week_<N>/day_<M>/day<M>_report.mp4
```

Вывод не прятать: предупреждения `rclone` нужны для разбора неполадок, а успехом считается
итог самой команды передачи. Раскладка на Диске — по папкам дней, `rclone copy` создаёт
недостающие сам. Связь проверяется командой `rclone lsf challenge:`.

Загружать ролик средством создания файлов на Диске нельзя: оно принимает содержимое строкой
внутри вызова, а запись экрана — миллионы знаков. Проверено на дне 4.

### 8. Отправить код дня в GitHub

Добавлять **файлы этой работы**, а не всё дерево разом: `git add -A` затянет чужой мусор
прогонов и файлы, попавшие в рабочую копию случайно.

```bash
git add week_<N>/day_<M> <прочие файлы работы>
git commit -m "week_<N>/day_<M>: <короткое описание>"
git push
```

### 9. Обновить README дня и зафиксировать

В `week_<N>/day_<M>/README.md`, в разделе «Ссылки», проставить ссылку на видео и ссылку на код
дня **на ветке**: `https://github.com/<owner>/<repo>/tree/<ветка>/week_<N>/day_<M>`. Затем:

```bash
git add week_<N>/day_<M>/README.md
git commit -m "week_<N>/day_<M>: добавить ссылки на отчёт"
git push
git rev-parse HEAD
```

### 10. Отдать результат пользователю

В чате — ссылка на видео и ссылка на код. В чат идёт **постоянная ссылка на последнюю
фиксацию**: `https://github.com/<owner>/<repo>/tree/<sha>/week_<N>/day_<M>` — она уже содержит
проставленные ссылки и больше не меняется. В `README.md` остаётся ссылка на ветку: фиксация не
может ссылаться на саму себя. Ветку дня после сдачи не трогаем, поэтому обе ведут к одному коду.

Сказать, что стадия `Report` завершена и работа переходит в `Done`.

## Ограничения, которые нужно держать в голове

- **Общий ключ `rclone` к Google Диску выводится из обращения в течение 2026 года** — при
  выгрузке печатается предупреждение. Когда перестанет работать, завести собственный ключ
  приложения по инструкции https://rclone.org/drive/#making-your-own-client-id и прописать его в
  подключение `challenge`. Разовая настройка в консоли Google, делает пользователь.
- Доступ «по ссылке — любой» через API этого подключения не выставляется — он держится на
  разовой ручной настройке папки. Папку пересоздали — предупредить, что настройку надо повторить.
- Управление видимым окном терминала зависит от среды: перед записью убедиться, что нужная
  автоматизация доступна, а не полагаться на то, что она была в прошлый раз.
