# Дизайн: счёт токенов местной модели словарём модели

Отложенная задача 16. Общая задача в `main`. Род по `/штурм` — точечная правка одной
способности (`tokens`) с новым запросом к службе (`api`).

## Задача и видение

`myharness` считает вес запроса до отправки словарём DeepSeek. У местной модели свой словарь.
Замер дня 26: на «Столица Австралии?» предсказано 134 токена, служба насчитала 60. Оценка завышена,
и сжатие срабатывает раньше нужного. Окно местной модели — 32 768 токенов, поэтому ошибка в
десятки токенов на реплику здесь заметна, а при окне DeepSeek в миллион — нет.

Видение пользователя (2026-10-06): считать токены местной модели по её словарю.

## Замеры 2026-10-06

Модель `qwen3.5:9b-q4_K_M-32k`, служба Ollama 0.34.4.

**Словарь.** `POST /api/show` с `"verbose": true` отдаёт словарь за 0,1 с: 248 320 токенов,
247 587 слияний, тип каждого токена. Вид словаря — `gpt2` (попарное слияние байтов, BPE),
предварительная разбивка — `qwen35`.

**Счёт.** Из этих полей библиотека `tokenizers` собирает счётчик в памяти. Его число сверено с
числом службы (`/api/generate`, `raw: true`, `prompt_eval_count`):

| Текст | Знаков | Служба | Наш счёт |
|---|---|---|---|
| «Столица Австралии?» | 18 | 5 | 5 |
| английский с числами | 77 | 34 | 34 |
| `CLAUDE.md`, начало | 6000 | 1770 | 1770 |
| `tokens.py`, начало | 6000 | 1769 | 1769 |
| `openspec/specs/tokens/spec.md`, начало | 6000 | 1714 | 1714 |
| JSON схемы инструмента | 128 | 40 | 40 |
| составные знаки, эмодзи, иероглифы, служебная метка | 72 | 47 | 47 |

Совпадение точное на всех семи. Нормализация NFC счёт ломает (43 против 47) — её не включать.

**Обёртка разговора.** Служба прибавляет 5 токенов на каждую реплику и 7 сверх них
(5 при включённых рассуждениях). Проверено на 1, 2, 3 и 5 репликах.

**Обёртка инструментов.** Одна схема — 199 токенов сверх её JSON, три схемы — 197.
У DeepSeek действует 190 (`tokens.ОБЁРТКА_ИНСТРУМЕНТОВ`).

**Рассуждения.** `usage` службы поля `reasoning_tokens` не содержит.

## Что решили и почему

1. **Словарь берём у службы, а не из файла GGUF.** Служба отдаёт его готовым. Разбор двоичного
   файла на 7 ГБ и поиск его в каталоге Ollama не нужны.
2. **Словарь запрашиваем там же, где окно** — в `api.Clients.prepare`. Модель сменили — счётчик
   собрали заново. На диск счётчик не кладём: файл весит 20 МБ и устаревает при замене модели
   под тем же именем. Служба нужна для обмена в любом случае.
3. **Счётчик собираем только для знакомого вида словаря.** Знакомый — `tokenizer.ggml.model =
   gpt2` и `tokenizer.ggml.pre` из таблицы «имя → выражение разбивки». В таблицу входят `qwen2` и
   `qwen35`. Выражения берём из исходников Ollama и llama.cpp, а не подбираем. Незнакомая модель
   остаётся на оценке, экран помечает число знаком «≈», как сейчас. Точным неточное не называем.
4. **Функции счёта получают имя модели доводом.** Сейчас `count_text(text)` модели не знает. В
   группе агентов модели разные, поэтому общий «текущий словарь» дал бы неверный счёт молча.
   Запомненные подсчёты получают ключ «словарь + текст».
5. **Новых чисел обёртки не заводим.** Агент уже подстраивает надбавку по модели после первого
   обмена (`Agent._overhead`). Точный счёт текста делает эту подстройку точной. До первого
   обмена местная модель берёт надбавку DeepSeek — 83 вместо 12. Ошибка — 71 токен на один
   запрос из окна в 32 768.
6. **Токены рассуждений местной модели считаем сами** — её словарём по тексту рассуждений из
   потока. Служба этого числа не даёт, а строка «из них рассуждения» показывает 0.
7. **`ОСТАТОК_НА_ОТВЕТ = 500` убираем.** Число отличает две причины обрыва ответа по длине:
   кончилось окно либо сработал `max_tokens`. Причину называет сравнение без числа: выход достиг
   `max_tokens` — виноват предел; вход вместе с выходом достиг окна — окно; иначе — общая
   строка. Третий исход добавлен на стадии `Plan`: DeepSeek обрывает ответ и по своему
   умолчанию `max_tokens`, и называть это окном было бы неправдой.

Отвергнуто:

- **Надбавка обёртки по поставщику числом** (первый путь постановки). Счёт остался бы оценкой,
  а число пришлось бы мерить на каждой модели.
- **Пробные запросы при загрузке модели, чтобы замерить обёртку.** Три лишних запроса на запуск
  ради 71 токена в первом обмене.
- **Файл словаря на модель в пакете.** 20 МБ на модель и ручное обновление.

Сверка с образцами. Claude Code и Codex свой словарь не держат: берут `usage` последнего ответа
и оценивают только прирост. Наша подстройка надбавки делает то же. Точный словарь нужен нам
дополнительно: окно в 32 768 мало, и решение о сжатии принимается до первого ответа службы.

## Затронутые способности

- `openspec/specs/tokens/` — требование «Точный счёт офлайн»: счёт местной модели точен, когда
  служба отдала знакомый словарь. Сценарий «модель местная, словарь на месте» меняется.
  Требование о расходе рассуждений — число для местной модели считает программа.
- `openspec/specs/api/` — запрос словаря у службы вместе с окном; сбой запроса не роняет запуск.
- `openspec/specs/agent/` — причина обрыва по длине без порога 500.

## Границы

Делаем: словарь из службы, счётчик для `gpt2` с разбивкой `qwen2` и `qwen35`, имя модели в
функциях счёта, токены рассуждений местной модели, причина обрыва без числа, проверки без службы
на малом словаре, живой замер «предсказано против службы» до и после.

Не делаем:

- словари вида `llama` (SentencePiece, модели Gemma и Llama) — остаются на оценке;
- обёртку инструментов по поставщику — 190 против 198, разницу снимает подстройка надбавки;
- обновление индекса RAG и проверку MCP на местной модели — это пункты 2 и 3 просьбы,
  отдельные общие задачи после этой.

## Риски и чем расплачиваемся

- **Служба сменит разбивку в новой версии.** Счёт разойдётся молча. Защита: подстройка надбавки
  после каждого обмена поглощает расхождение; живой замер повторяем при обновлении Ollama.
- **Имя модели доводом — правка около десяти мест вызова.** Пропущенное место считает словарём
  DeepSeek. Защита: проверка на каждое место вызова из списка плана.
- **Сборка счётчика занимает время.** Замер — около 0,5 с. Она идёт в `prepare`, до первого
  обмена, и отрисовку не держит; точное место и поток называет план.
- **Память.** Счётчик на 248 320 токенов живёт в памяти процесса на каждую местную модель сеанса.
  Размер не замерен — замерить в плане.

## Продолжение 2026-10-06: цена обёртки реплики

Пункт 5 выше («новых чисел обёртки не заводим») оставил остаток. После подстройки основы
предсказание занижалось на 7 токенов за обмен: реплика стоит у службы 5 токенов, а инструмент
закладывал 1,5 — замер DeepSeek. Пользователь спросил, почему остаток отложен. Отложен он был
зря: замер показал точную закономерность, а правка мала.

Решение. Обёртка запроса равна основе плюс цене каждой реплики сверх первой. Агент хранит
последний замер обёртки и выводит цену реплики из двух ответов службы:

```
обмен 1:  обёртка₁ = основа + цена × (n₁ − 1)
обмен 2:  обёртка₂ = основа + цена × (n₂ − 1)
отсюда    цена = (обёртка₂ − обёртка₁) / (n₂ − n₁)
```

- Числа в код не вписаны. Способ общий для любой модели с точным счётом текста, в том числе
  для DeepSeek.
- Образец тот же: Claude Code и Codex берут число последнего ответа сервера и оценивают только
  прирост.
- Цена выводится только при точном счёте текста, при том же весе описаний инструментов и том же
  числе звеньев вызовов инструментов в обоих замерах. Иначе действует прежняя цена.
- Отрицательная цена не выводится. Замер с неправдоподобной основой отвергается целиком: по
  весу запроса режется память.
- Экран и `/tokens` берут обёртку запроса у агента (`Agent.request_overhead`). Иначе показ
  занижал бы вес на цену каждой реплики памяти.

Итог живого наряда на `qwen3.5:9b-q4_K_M-32k`, разница «предсказано − служба»: разговор +69, −7,
0; вставка в 6000 знаков +69, −7. Точным предсказание становится с третьего обмена: на два
неизвестных нужны два ответа службы.

Что осталось неточным:

- первый обмен (+69): основа до первого ответа — замер DeepSeek, 83 против 14;
- второй обмен (−7): цена реплики до второго ответа — замер DeepSeek;
- словари вида `llama` и надбавка обёртки инструментов — отложенная задача 16.
