## Договоры модулей

### api
**Владеет**: ничем, кроме соединения.
**Отдаёт**: `stream_chat(model, messages, params=None, tools: list[dict] | None = None) -> AsyncIterator[StreamEvent]`;
`StreamEvent.kind` — `"reasoning" | "content" | "tool_calls" | "meta"`; новое поле
`StreamEvent.calls: list[dict]` — каждый элемент `{"id": str, "type": "function",
"function": {"name": str, "arguments": str}}`.
**Обещает**: событие `"tool_calls"` приходит не больше одного раза за поток, после всех
кусков текста и до `"meta"`; куски склеены по `index`; `tools=None` или `[]` — в запрос
`tools` не уходит вовсе, поведение байт в байт прежнее.
**Не делает**: доводов не разбирает (строка JSON как пришла), инструментов не исполняет.

### memory (запись разговора)
**Владеет**: файлом разговора.
**Отдаёт**: `SessionStore.append_pair(user, assistant, meta=None, *, приложение: dict | None = None) -> str | None`;
`Restored.приложения: list[dict]` — той же длины и в том же порядке, что `Restored.pairs`
(окно режет оба одинаково), пустой словарь у пары без приложения.
**Обещает**: приложение — словарь с ключами `reasoning_content: str` и `звенья: list[dict]`
(сообщения круга: ответ модели с `tool_calls` и своим `reasoning_content`, результаты с ролью
`tool`); оба пишутся ПОЛЯМИ записи ответа, отдельных строк не появляется; запись без этих полей
читается как пара без приложения; поле неверного вида отбрасывается с предупреждением, пара
остаётся.
**Не делает**: не проверяет смысл звеньев.

### agent
**Отдаёт**:
- `@dataclass Инструменты: схемы: list[dict]; исполнить: Callable[[str, str], Awaitable[str]]` —
  имя инструмента и строка доводов на вход, текст результата на выход;
- `Agent(..., инструменты: Callable[[], Инструменты | None] | None = None)`;
- `remember(question, answer, *, model="", приложение: dict | None = None)`;
- `restore(pairs, приложения: list[dict] | None = None)`;
- `раскрыть(сообщения: list[dict], полные: bool) -> list[dict]` (функция модуля);
- `Turn.звенья: list[dict]`.

**Обещает**:
- `_messages` по-прежнему строго чередует `user`/`assistant`, приложение живёт ключом `"приложение"`
  у сообщения ответа и никогда не уходит в API как есть;
- `раскрыть(..., полные=False)` отдаёт `{"role", "content"}` и ничего больше;
- `раскрыть(..., полные=True)` отдаёт вопрос, звенья, ответ с `reasoning_content` (пустая
  строка, если рассуждений не было — см. шаг 1);
- инструменты запрашиваются у поставщика один раз за обмен; `None` — обмен как прежде;
- исключение исполнителя становится текстом результата «ошибка инструмента: …», круг
  продолжается;
- неотвеченный или отменённый обмен не оседает в памяти ни вопросом, ни звеньями.

**Не делает**: смысла инструментов не знает; предела числа кругов не ставит.

### machine
**Владеет**: ничем на диске сам — пишет через `workspace`.
**Отдаёт**:
- `@dataclass(frozen=True) Стадия: имя: str; цель: str; утверждение: bool; консилиум: tuple[str, ...]; дальше: tuple[str, ...]`;
- `@dataclass(frozen=True) Карта: стадии: tuple[Стадия, ...]` с методами `стадия(имя) -> Стадия | None`,
  `начальная -> Стадия` (свойство), `конечная(имя) -> bool`;
- `имя_стадии(текст: str) -> str` — единственное приведение имени стадии (`" ".join(split()).upper()`), его же зовёт `workspace.set_stage`;
- `разобрать_карту(raw: Any, есть_профиль: Callable[[str], bool], *, свой_профиль: str | tuple[str, ...] = "") -> tuple[Карта | None, list[str]]`;
- `в_список(карта: Карта) -> list[dict]` — обратное разбору, для записи профиля;
- `СХЕМЫ: list[dict]` — описания трёх инструментов;
- `набор(state) -> Инструменты | None`.

**Обещает**: имя стадии приводится `имя_стадии`; переход в неизвестную стадию и повтор имени
отбрасываются с предупреждением; неизвестный профиль консилиума ОСТАЁТСЯ в карте с
предупреждением и проверяется при созыве (шаг 6); сам профиль в консилиуме отбрасывается;
стадия, у которой были переходы, но ни одного годного не осталось, делает негодной всю карту;
карта без конечной стадии или без единой стадии — `None` и предупреждение; `набор` отдаёт
`None`, если нет хотя бы одного из трёх условий Р9 (профиль с картой, открытая задача этого
профиля, не пауза) или стратегия профиля `branching`.

**Не делает**: не распознаёт согласия; не применяет переход через ворота.

### team
**Отдаёт**: `async созвать(state, вопрос: str, имена: list[str]) -> list[tuple[str, str]]` —
пары «имя профиля, текст ответа» только ответивших.
**Обещает**: запросы одновременные, панели исполнителей видны, не ответившие названы вслух;
`run` пользуется `созвать` и ведёт себя как прежде.

## Шаг 2. Пара несёт приложение и переживает перезапуск

**Файлы**: `memory.py`, `tokens.py`, `agent.py` (только `remember`, `restore`, `раскрыть`, `_preview`, `history_tokens`, сборка `selected_messages` в `build_messages`), `conversation.py`, `openspec/specs/memory/spec.md`, `openspec/specs/agent/spec.md`, `openspec/specs/tokens/spec.md`, `tests/check_units.py`
**Зависит от**: шаг 1
**Ход**: полный, потому что файл разговора читают прежние версии кода и подъём при запуске, а вид памяти читает круг шага 3; и это именованное исключение — восстановление после обрыва записи
**Требование**: `memory` → «Разговор пишется дописыванием дословно», «Испорченная запись не роняет восстановление»; `agent` → «Память выдаётся копией и пополняется единственным способом»; `tokens` → «Вес запроса известен до отправки»
**Проверка**: пара с приложением записана, файл прочитан заново — приложение на месте и в том же порядке при окне 2 из 3 пар; парная проверка: пара без приложения читается с пустым словарём; `build_messages` без инструментов не несёт ни одного ключа, кроме `role` и `content` (предусловие: в памяти лежит пара с приложением)
**Содержание**:
- `append_pair`: `приложение` кладётся полями `reasoning_content` и `звенья` в запись ответа, после `meta` и не перекрывая служебные поля.
- `read_session`: поле `звенья` — список словарей, у каждого `role` из `assistant`/`tool`; иначе предупреждение «строка N: звенья испорчены — пара без них» и пустое приложение. `reasoning_content` не строка — так же.
- `Agent.remember`: `приложение` ложится ключом `"приложение"` в сообщение ответа только если непусто и передаётся в `append_pair`. Стратегия `branching` приложение не пишет (Р9: инструментов там нет).
- `раскрыть` вызывается ровно в одном месте `build_messages` — над `selected_messages` обеих ветвей; `полные` в этом шаге всегда `False`, признак подаёт шаг 3.
- `_preview` и `history_tokens` взвешивают `раскрыть(self._messages, полные)` — ровно то, что уйдёт.
- `tokens.count_messages`: к `content` прибавляются `count_text(reasoning_content)` и `count_text(json.dumps(tool_calls, ensure_ascii=False))`, если они есть; новая `count_tools(схемы) -> int` — `count_text` от JSON схем.
- `conversation.restore_conversation` передаёт `restored.приложения` в `agent.restore`.

## Шаг 3. Круг вызовов инструментов внутри обмена

**Файлы**: `api.py`, `agent.py` (`Инструменты`, `Turn.звенья`, `exchange`, признак `полные` в `build_messages`), `openspec/specs/api/spec.md`, `openspec/specs/agent/spec.md`, `openspec/specs/params/spec.md`, `tests/check_units.py`
**Зависит от**: шаг 2
**Ход**: полный, потому что вид событий потока читает отрисовка (шаг 8), а договор `Инструменты` — автомат (шаг 5)
**Требование**: `api` → «Потоковый ответ разделяет рассуждения и ответ»; `agent` → «Пустой ответ не считается успехом», новое «Круг вызовов инструментов идёт внутри одного обмена»
**Проверка**: поддельный клиент отдаёт сначала вызов, потом текст — в памяти одна пара, у ответа два звена, в журнале `звенья`, `usage` сложен из двух запросов; второй запрос несёт `tools`, звенья и `reasoning_content`; парная проверка: поставщик вернул `None` — в запросе нет `tools`, круг не начинается; отмена во время исполнения инструмента — памяти не прибавилось
**Содержание**:
- `api.stream_chat`: куски `delta.tool_calls` копятся словарём по `index` (`id`, `function.name`, склейка `function.arguments`), одно событие `"tool_calls"` перед `"meta"`.
- `exchange`: `набор = self._инструменты() if self._инструменты else None` один раз; `build_messages(content, model, полные=набор is not None)`; `params` запроса — профиля плюс `tools=набор.схемы`. Круг: пока поток кончился событием `"tool_calls"` — звено ответа `{"role": "assistant", "content": текст круга, "reasoning_content": рассуждения круга, "tool_calls": calls}`, затем по каждому вызову `await набор.исполнить(name, arguments)` и звено `{"role": "tool", "tool_call_id": id, "content": результат}`; звенья дописываются к `request_messages`, поток запускается заново. `usage` кругов складывается `tokens.add_usage`. `on_event` получает и новое событие.
- Пустой ответ: ошибкой считается только итоговый круг без текста и без вызовов.
- Успех: `remember(content, answer_text, model=model, приложение={"reasoning_content": рассуждения итогового круга, "звенья": звенья})`, если инструменты были в запросе.
- `predict_tokens` прибавляет `tokens.count_tools(набор.схемы)`.
- Журнал: `entry["звенья"]`, если непусто.

## Шаг 5. Автомат ведёт задачу: план со статусами и переходы

**Файлы**: `machine.py` (`СХЕМЫ`, `набор`, исполнители `update_plan` и `move_stage`), `workspace.py`, `state.py`, новая `openspec/specs/task-machine/spec.md`, `openspec/specs/memory/spec.md`, `tests/check_units.py`
**Зависит от**: шаги 3, 4
**Ход**: полный, потому что доводы модели ложатся на диск в файл, который правит человек, и файл читает прежний код дня 11
**Требование**: новая `task-machine` → «Переход проверяется картой», «Ворота открывает только человек», «Пауза снимает инструменты», «Продолжение после перезапуска»; `memory` → «Рабочая память задачи лежит файлом…» (новые ключи, снятие оговорки о карте)
**Проверка**:
- на задаче в `RESEARCH` вызов `move_stage` в `PLAN` — этап не сменился, `ждёт: человек`, `предложено: PLAN`, результат говорит «ждёт утверждения»; парная: из `PLAN` в `EXECUTING` при `утверждение: false` у `PLAN` в тестовой карте — этап сменился;
- `move_stage` в `DONE` из `RESEARCH` — отказ «нет такого перехода», файл не изменён;
- `update_plan` с двумя `идёт` — отказ; с одним — «План» со статусами, «Сейчас» — этот шаг;
- довод со строкой `"шаг\n## Чужой раздел"` не порождает раздела;
- после сброса памяти агента первый запрос несёт в блоке стадию, цель, допустимые переходы, шаг, «ждёт», «ожидается»;
- **живой обмен** — скрипт ведущего на `Agent` с настоящим ключом и `набор` из этого шага, без окна: «составь план из трёх шагов и предложи переход» — в файле задачи план со статусами и `предложено`.
**Содержание**:
- `Задача`: поля `профиль: str = ""`, `ждёт: str = ""`, `ожидается: str = ""`, `предложено: str = ""`, `пауза: bool = False`; ключи заголовка `профиль`, `ждёт`, `ожидается`, `предложено`, `пауза` (`да`); пустые в файл не пишутся.
- `workspace.обновить(задача, **поля) -> tuple[bool, str]` — снимок, правка полей, `_записать`; строки проходят `" ".join(текст.split())`.
- `workspace.записать_план(задача, шаги: list[tuple[str, str]]) -> tuple[bool, str]` — «План» строками `[ ] шаг` / `[>] шаг` / `[x] шаг`, «Сейчас» — шаг `[>]`, сделанные дописываются в «Сделано» без повторов.
- `workspace.блок(задача, карта: Карта | None = None)` — при карте после строки этапа: «Цель стадии: …», «Дальше можно: …», «Ждёт: человек — …» или «Ожидается: …», «Задача на паузе», и строка «Есть «Сейчас» — продолжай с него, не начинай заново».
- `набор(state)`: профиль главного экрана, задача с `профиль == имя профиля`, не пауза, стратегия не `branching`. `исполнить` разбирает JSON доводов; разбор не удался — результат «доводы не разобраны: …».
- `перейти(стадия, итог)`: стадия не в `дальше` — отказ; текущая стадия с `утверждение` — `обновить(ждёт="человек", предложено=стадия, ожидается="утвердить итог стадии <текущая>")` и результат «ждёт утверждения человека — остановись и покажи итог»; иначе `этап=стадия`, `ждёт=""`, `предложено=""`, строка итога в «Сделано».
- Инструкция автомата — описания схем; в системную часть ничего не добавляется, кроме того, что сами схемы несут.
- `state.главный_агент` передаёт `инструменты=lambda: machine.набор(state)`.
- Строка в ленту о каждом вызове — через шаг 8; здесь исполнитель возвращает текст результата.
