# Дизайн: автомат состояний задачи (день 13)

## Задача и видение

Условие дня: состояние задачи как конечный автомат — этап, текущий шаг, ожидаемое действие;
пример `planning → execution → validation → done`; проверить паузу на любом этапе и продолжение
без повторных объяснений.

Видение пользователя (2026-09-16): глобальный профиль «разработчик», заведённый командой
`/profile new`. Стадии и переходы — ровно как в нашем конвейере:

```
RESEARCH   → PLAN | EXECUTING      (дизайн: ведущий зовёт консилиум, выбирает лучшее, выносит на утверждение)
PLAN       → EXECUTING             (план на утверждение)
EXECUTING  → VALIDATION | RESEARCH
VALIDATION → REPORT | EXECUTING | RESEARCH
REPORT     → DONE
```

Модель двигает автомат **вызовом инструментов** — решение пользователя 2026-09-16, принятое
вместе с названной ценой (см. «Риски»).

## Что решили и почему

### Р1. Автомат — программа, модель предлагает, человек открывает ворота

Автомат — таблица переходов, проверка и запись файла; агентом он не является. Роли:

- **модель** зовёт инструменты: отмечает шаги и предлагает переход;
- **программа** сверяет предложенное с картой и пишет файл задачи; переход вне карты
  отвергается, и об этом говорится модели результатом инструмента и человеку строкой в ленте;
- **человек** открывает ворота — переход из стадии, помеченной утверждением (дизайн в
  `RESEARCH`, план в `PLAN`), применяет только команда `/task утвердить`.

Утверждение не распознаётся из текста реплики: «ну вроде норм» не становится согласием. Образец
расплатился за обратное: у Claude Code модель принимала постороннее сообщение за утверждение
выхода из режима плана (issue #37576). У образцов устроено так же: `ExitPlanMode` модели плюс
окно утверждения программы (Claude Code), `update_plan` со статусами (Codex), `interrupt` с
продолжением только внешней командой (LangGraph).

Отвергнуто: двигает только человек (это нынешний `/task этап` — модель не знает, что шаг
кончился, и «ожидаемое действие» остаётся пустым); двигает только модель (ворота проходятся
самовольно).

### Р2. Три инструмента

| Инструмент | Доводы | Что делает программа |
|---|---|---|
| `update_plan` | список шагов, у каждого статус `ждёт` / `идёт` / `сделан`; необязательное «ожидаемое действие» | переписывает раздел «План» со статусами; шаг со статусом `идёт` становится «Сейчас»; сделанные — в «Сделано». Больше одного `идёт` — отказ результатом |
| `move_stage` | стадия, итог стадии | нет в карте — отказ; стадия с воротами — переход НЕ применяется, задача получает «ждёт: человек, утвердить …», модели возвращается «ждёт утверждения человека — остановись и покажи итог»; без ворот — переход применяется |
| `call_council` | вопрос | только в стадии, где карта называет консилиум: вопрос уходит группе профилей одновременно (механизм `team`), их ответы возвращаются модели результатом, панели исполнителей видны человеку. Выбирает лучшее и выносит на утверждение сама модель-ведущий |

Образцы — `TodoWrite` у Claude Code и `update_plan` у Codex (список со статусами, один в работе).
«Текущий шаг» — это шаг со статусом `идёт`, а не отдельное поле: два хранилища одного знания
разошлись бы.

Предела на число кругов «вызов → результат → продолжение» нет: его нет у образца в
интерактивном режиме, а остановку даёт отмена обмена человеком, которая уже работает.

### Р3. Карта стадий живёт в профиле

В json профиля появляется поле `stages` (имена инструментов и ключей — латиницей: так требует DeepSeek и так устроены все ключи профиля) — упорядоченный список:

```json
{"stages": [
  {"name": "RESEARCH", "goal": "…", "approval": true,
   "council": ["архитектор", "безопасник"], "next": ["PLAN", "EXECUTING"]},
  …
  {"name": "DONE", "next": []}
]}
```

Первая стадия — начальная, стадия без `next` — конечная. Программа проверяет карту при
загрузке: переход в неизвестную стадию и отсутствие конечной стадии отбрасываются вслух;
имя консилиума не из существующих профилей остаётся с предупреждением и проверяется при
созыве — иначе `/profile save` в другой папке стёр бы его с диска (правило «мусор в профиле не роняет профиль»). Карта без
единой годной стадии — профиля без карты.

Консилиум — **отдельное поле стадии, а не список `agents`.** Профиль с непустым `agents`
отправляет группе каждый вопрос (способность `team`); у «разработчика» группа нужна только на
дизайне. Второй смысл у `agents` — техдолг.

Отвергнуто: карта в коде (один конвейер на все профили — мастер ничего не заводит; у занятия
«роман» стадии другие).

### Р4. Мастер `/profile new` заводит карту

Область «ход работы» мастера дня 12 уже спрашивает, как вести задачу. Сборщик профиля получает
право вернуть поле `стадии`, когда описание и ответы называют стадии; перечень существующих
профилей для консилиума уже уходит в запрос (Р5 дня 12). Своего перечня стадий программа не
навязывает — называет модель, проверяет программа (Р3).

### Р5. Состояние задачи — в файле задачи, новые ключи заголовка

К заголовку файла рабочей памяти (`memory`, требование «Рабочая память задачи…») добавляются:
`профиль` (в каком профиле заведена), `ждёт` (`человек` / `модель`), `ожидается` (текст),
`предложено` (стадия, ждущая утверждения), `пауза` (`да` / нет ключа). Файл остаётся `.md`,
правимым руками.

- Новая задача профиля с картой начинается с первой стадии карты.
- Этап задачи не из карты текущего профиля (задачу завели в другом профиле) не сбрасывается
  молча: расхождение называется, инструменты не предлагаются, человек правит `/task этап`.
- Профиль без карты — поведение дня 11 без изменений: `этап` — любое слово.

### Р6. Пауза — отметка поверх стадии

`/task пауза` ставит отметку, `/task продолжить` снимает. На паузе инструменты автомата модели
не предлагаются, а блок состояния говорит «задача на паузе». Ожидание утверждения — частный
случай: «ждёт: человек».

Отвергнуто: пауза отдельной стадией — из каждой стадии нужна была бы дуга в паузу и память о
том, куда вернуться, то есть второй этап.

### Р7. Продолжение без повторных объяснений — через блок состояния

Эфемерный блок `<рабочее-состояние>` дополняется стадией, целью стадии из карты, допустимыми
переходами, текущим шагом, тем, кто ждёт, и ожидаемым действием. Инструкция о продолжении
(«есть «Сейчас» — продолжай с него, не начинай заново и не пересказывай») и описания
инструментов — в неизменной части запроса, ради кэша поставщика.

Проверяемо программой: после перезапуска и очистки разговора первый запрос несёт в блоке стадию,
шаг, ожидаемое действие, «Ограничения», «План» и «Сделано». Разговор очищается нарочно — иначе
проверяется слой разговора, а не автомат.

### Р8. Вызов инструментов в обмене — круг внутри одной пары

Весь инструмент держится на правиле «память — пары вопрос–ответ»: сжатие, окно памяти, четыре
стратегии, восстановление и счёт пар. Правило **сохраняется**:

- круг «вызов → результат → продолжение» идёт внутри одного обмена (`agent.exchange`);
- промежуточные сообщения (ответ модели с вызовами и её рассуждениями, результаты инструментов)
  и рассуждения итогового ответа ложатся **полем записи ответа**, а не отдельными записями;
- при сборке запроса С инструментами пара раскрывается в полную цепочку сообщений с
  `reasoning_content` — этого требует DeepSeek; без инструментов пара уходит как сейчас;
- старый читатель файла разговора лишние поля пропускает — совместимость сохраняется;
- выжимка по-прежнему строится из пар: вопроса и итогового ответа.

Остальное, что трогается: поток (`api`) собирает куски вызовов по номеру; итоговый ответ без
текста при `finish_reason = tool_calls` — не пустой ответ; счёт веса учитывает описания
инструментов, вызовы и возвращаемые рассуждения; отрисовка показывает каждый круг своим
свёрнутым рассуждением и строкой вызова.

Отвергнуто: класть вызовы отдельными записями разговора — ломает чередование в десятке мест
и в пяти спецификациях.

### Р9. Инструменты только там, где есть автомат

`tools` уходят в запрос лишь при трёх условиях: профиль с картой, открытая задача этого профиля,
не пауза. Служебные агенты (архивариус, сжиматель, разметчик памяти, факты разговора,
исполнители консилиума) инструментов не получают.

### Р10. `/profile new` пишет в личный каталог (решение пользователя 2026-09-16, после Validation)

Прежнее правило дня 12 (Р7 `docs/персонализация.md`): новый профиль ложится в первый
существующий каталог поиска. Из папки внутри репозитория это `profiles/` репозитория, и профиль,
задуманный глобальным, виден только внутри репозитория. Для видео пришлось бы подставлять
переменную окружения — обход, а не устройство.

Новое правило — как у образца (Claude Code кладёт новый стиль ответа в личный каталог):
- без уточнения `/profile new` пишет в `$MYHARNESS_PROFILES`, если переменная задана (это увод
  для проверок), иначе в личный `~/.config/myharness/profiles`;
- `/profile new --проект <описание>` пишет в ближний `profiles/` вверх от рабочего каталога, а
  если его нет — заводит `profiles/` в рабочем каталоге.

Довод дня 12 «ближний перекроет дальний, и человек будет править не тот файл» при создании не
срабатывает: мастер отказывает, если имя занято в ЛЮБОМ каталоге поиска.

## Затронутые способности

- `openspec/specs/api/` — куски вызова в потоке, новый род события.
- `openspec/specs/agent/` — круг вызовов внутри обмена, пустой ответ, раскрытие пары.
- `openspec/specs/memory/` — поля записи ответа; новые ключи заголовка рабочей памяти; снятие
  оговорки «карты переходов сегодня нет».
- `openspec/specs/tokens/` — вес инструментов, вызовов и рассуждений.
- `openspec/specs/profiles/` — поле `стадии`, проверка карты; мастер заводит карту.
- `openspec/specs/commands/` — `/task утвердить`, `/task отклонить <замечание>`,
  `/task пауза`, `/task продолжить`.
- `openspec/specs/team/` — консилиум: ответы группы возвращаются вызвавшей модели, без сводки.
- `openspec/specs/interface/` — круги рассуждений и строки вызовов; стадия и «ждёт» в строке
  под вводом.
- Новая способность `openspec/specs/task-machine/` — автомат: карта, переходы, ворота, пауза,
  три инструмента.

## Границы

Делаем: вызов инструментов в главном обмене; три инструмента автомата; карту стадий в профиле и
её заведение мастером; ворота, паузу, продолжение; проверки; живой прогон: заводим профили
консилиума и «разработчика» через `/profile new`, ведём одну задачу через все стадии с паузой
на каждой и перезапуском.

НЕ делаем: инструменты для работы с файлами и командами (отложенные задачи 2 и 3 — вызов
инструментов станет им основой); предел числа кругов; распознавание согласия из текста;
инструменты у служебных агентов и в стратегии `branching`, если раскрытие пары там потребует
перестройки узла ветви — тогда называется отдельно на стадии `Plan`.

Порядок веток: код и требования — в `main`; затем ветка `w3d3` и папка `week_3/day_3/` под
песочницу живого прогона и видеоотчёт, как в дне 12.

## Риски и чем расплачиваемся

- **Рост входа.** С инструментами рассуждения всех прошлых ходов уходят в каждый запрос
  (документация DeepSeek, `guides/thinking_mode`). Смягчение — Р9, и сжатие выжимкой работает
  как прежде. Цена принята пользователем.
- **Объём.** Перестройка обмена — больше одного дня: поток, память, файл разговора, счёт
  токенов, отрисовка, девять способностей.
- **Файл разговора растёт** — в нём лежат рассуждения и вызовы.
- **Доводы инструментов — данные от модели, которые ложатся на диск.** Строки проверяются так
  же, как ввод `/task`: перевод строки и решётка не должны порождать заголовков и разделов в
  файле задачи; имя стадии — только из карты.
- **Модель может не звать инструменты.** Тогда автомат стоит, а человек видит это по строке под
  вводом и двигает `/task этап` сам. Живой прогон покажет, хватает ли описаний инструментов.
