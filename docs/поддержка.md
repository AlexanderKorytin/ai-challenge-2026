# Дизайн: ассистент поддержки пользователей (день 33)

## Задача и видение

Условие дня 33 просит мини-сервис поддержки пользователей. Ассистент:

- отвечает на вопросы о продукте;
- ищет ответ по FAQ и документации (RAG — поиск по документам перед ответом);
- учитывает данные пользователя и тикета;
- получает пользователей и тикеты через MCP: из CRM либо из файла JSON.

Пример условия: «Почему не работает авторизация?» Ассистент отвечает с учётом данных тикета.

Продукт — сам `myharness` (решение пользователя от 2026-10-14). Документация продукта
настоящая: требования `openspec/specs`. Пользователи и тикеты выдуманы, но описывают настоящие
беды `myharness`: нет ключа, служба Ollama не запущена, сервер MCP не отвечает.

## Что решили и почему

```
человек: «Тикет T-1001. Почему не работает авторизация?»
   ▼ myharness, профиль «поддержка»
   ▼ поиск: сервер `rag`, индекс поддержки (FAQ + openspec/specs)
   ▼ модель зовёт сервер `support`: тикет (get_ticket) и/или пользователь (find_user, list_tickets)
   ▼ ответ: причина по данным тикета + шаги по документации + источники
```

1. **Правка `myharness` не нужна.** Все каналы уже есть:
   - поле профиля `rag` называет сервер поиска (день 22);
   - `.mcp.json` рабочего каталога подключает серверы (день 16);
   - `permissions.allow` разрешает модели инструменты (день 17).

   Ассистент — профиль `поддержка` и песочница с `.mcp.json`. Так же собран помощник дня 31.
   Отвергнуто: своя программа-служба вроде `agents/review`. Она повторяет цикл вызова
   инструментов, который уже есть в `myharness`.

2. **Пользователей и тикеты отдаёт свой местный сервер MCP `support`** (stdio, только
   чтение) из файла `данные.json`. Инструменты:
   - `find_user(user_id | email)` — пользователь и его постоянное окружение: система,
     версия `myharness`, поставщик и модель, подключённые серверы MCP, тариф;
   - `list_tickets(user_id)` — тикеты пользователя: прежние обращения и чем они кончились;
   - `get_ticket(ticket_id)` — тикет: тема, текст, статус, текст ошибки, переписка, автор.

   Данные делятся на два контекста:
   - **контекст пользователя** — что верно для человека всегда: окружение и история
     обращений;
   - **контекст тикета** — один случай: текст ошибки, когда и что сделано.

   Отвергнуто: настоящая CRM (HubSpot, Zendesk). Нужна учётная запись и ключ; выдуманные
   данные туда всё равно пришлось бы заливать. Условие разрешает JSON.
   Отвергнуто: официальный сервер `filesystem` с чтением `данные.json`. Модель получила бы
   файл целиком, а не тикет по номеру, и вопрос «у кого из пользователей…» стал бы чтением
   всей базы.

3. **Оба контекста модель берёт вызовом инструмента.** Условие требует, чтобы они шли через
   MCP.
   - Реплика называет номер тикета — модель зовёт `get_ticket`, затем `find_user` по автору.
   - Реплика называет почту без тикета — модель зовёт `find_user` и `list_tickets`.
   - Реплика не называет ни того, ни другого — модель спрашивает почту или номер тикета.

   Отвергнуто: программа сама кладёт тикет или пользователя в запрос. Для этого нужна
   правка `myharness` и второй канал рядом с инструментами.
   Отвергнуто: закрепить пользователя за сеансом подстановкой `vars` профиля. Тогда нужен
   профиль на каждого пользователя.

4. **База знаний — отдельный индекс поддержки:** `FAQ.md` + `openspec/specs`. Его собирает
   действующая команда `rag/cli.py index`, стратегия `structure`. Контрольный индекс
   `rag/index.sqlite` и индекс помощника `rag/assistant.sqlite` не меняются.
   `FAQ.md` пишем заново: 10–15 вопросов пользователя с ответами по требованиям. Каждый
   ответ FAQ опирается на требование, иначе это выдумка.

5. **Ответ ассистента:**
   - причина по данным тикета: «в тикете ошибка 401, значит ключ отвергнут»;
   - шаги из базы знаний;
   - строка «Источники:» с путём и разделом куска и с номером тикета.

   Данных не хватает — ассистент задаёт один уточняющий вопрос. В базе ответа нет — говорит
   «в документации этого нет» и предлагает передать тикет человеку.

6. **Главная проверка — один вопрос «Почему не работает авторизация?» в трёх контекстах.**
   Ответы обязаны различаться по существу. Это доказывает, что контекст учтён, а не просто
   прочитан.
   - Контекст тикета, T-1001: ошибка 401 у DeepSeek → ключ отвергнут, `/auth`.
   - Контекст тикета, T-1002: отказ соединения с `ollama/…` → служба Ollama не запущена.
   - Контекст пользователя, тикета нет, только почта: пользователь ходит к местной модели
     через шлюз по `OLLAMA_HOST`, а `OLLAMA_API_KEY` в его окружении не задан. Прежний
     тикет пользователя о том же шлюзе закрыт без решения. Ответ опирается на окружение
     и историю, а не на текст ошибки.

7. **Модель — модель сеанса**, по умолчанию `deepseek-v4-flash`. Местную модель не
   замеряем: условие этого не просит.

## Затронутые способности

Требования `openspec/specs` не меняются: код `myharness` не трогаем.

- `openspec/specs/profiles/` — профиль `поддержка` использует действующее поле `rag`.
- `openspec/specs/mcp/` — сервер `support` подключается действующим `.mcp.json`
  и `permissions.allow`.
- `rag/` — новый индекс собирается действующей командой, без правки кода.

## Границы: что делаем и чего НЕ делаем

Делаем, всё в ветке дня `w7d3` и папке `week_7/day_3/`:

- сервер `support` и `данные.json`: 5–6 пользователей и 6–8 тикетов;
- `FAQ.md` и индекс поддержки;
- профиль `поддержка` (пара файлов);
- песочницу `test/` с `.mcp.json` (серверы `rag` и `support`) и `.claude/settings.json`;
- живой сценарий из 5 реплик: один вопрос по двум тикетам, тот же вопрос по почте
  пользователя без тикета, вопрос без тикета и без почты (ждём встречный вопрос), далёкий
  вопрос (ждём отказ);
- видеоотчёт в окне `myharness`.

Не делаем:

- запись в тикеты: смену статуса, ответ клиенту. Условие просит отвечать, а не вести тикет;
- веб-страницу или службу HTTP для клиентов;
- замер качества на контрольном наборе и сравнение режимов поиска;
- правку `myharness` и требований.

## Риски и чем расплачиваемся

- **Текст тикета — чужие данные.** Клиент может вписать в тикет указание модели.
  Защита — сервер только читает, а в песочнице разрешены только инструменты чтения.
  Худший исход — неверный ответ на экране, а не действие.
- **Модель может не вызвать `get_ticket`** и ответить по одной документации. Инструкция
  профиля требует вызова при номере тикета; живой сценарий это проверит.
- **Пакетный режим не отдаёт модели инструменты MCP** (отложенная задача 17). Живой
  сценарий идёт в диалоговом окне, как в дне 31.
- **FAQ пишет модель.** Расплата — сверка каждого ответа FAQ с требованием при просмотре.
