# Дизайн: подключение MCP (день 16)

## Задача и видение

Условие: поставить клиент MCP и написать минимальный код, который устанавливает соединение с
сервером MCP и получает от него список инструментов; проверить, что соединение устанавливается и
список возвращается корректно.

Видение пользователя: взять пару публичных серверов и показать. На этой неделе предстоит
сравнение «MCP против навык + CLI» (слайд целей недели: познакомиться с MCP, публичные
инструменты, оркестровка MCP, реальная работа, сравнение с навыком и CLI) — выбор сделать сразу
таким, чтобы код не переписывать.

## Что решили и почему

### Библиотека — официальная `mcp` для Python, версия 2.x

Проба 2026-09-21: `uv run --with mcp` ставит **2.2.0**. Во второй версии программный интерфейс
изменился против почти всех примеров в сети: `streamablehttp_client` стал
`streamable_http_client`, заголовки идут через `create_mcp_http_client(headers=…)`, поля ответа
названы по-питоновски (`server_info`, `protocol_version`). Поэтому зависимость фиксируется как
`mcp>=2.2,<3`: следующая крупная версия сломает так же молча.

Отвергнуто: писать обмен JSON-RPC самим. Согласование версий протокола, два способа передачи и
сеанс HTTP — ровно то, что библиотека уже держит; своё повторение стало бы вторым каналом рядом с
работающим.

### Серверы — те, у которых есть двойник в CLI

Проба подключилась ко всем шести кандидатам:

| Сервер | Передача | Ключ | Инструментов | Двойник в CLI |
|---|---|---|---|---|
| GitHub (`api.githubcopilot.com/mcp/`, официальный) | HTTP | токен `gh` | 45 | `gh` |
| git (`uvx mcp-server-git`, эталонный) | stdio | нет | 12 | `git` |
| fetch (`uvx mcp-server-fetch`, эталонный) | stdio | нет | 1 | `curl` |
| DeepWiki | HTTP | нет | 3 | нет |
| Microsoft Learn | HTTP | нет | 3 | нет |
| Context7 | HTTP | нет | 2 | нет |

**Берём GitHub и git.** Причина — неделя: сравнение «MCP против CLI» честно только на задаче,
которую можно решить обоими путями одинаково. У GitHub двойник `gh` (уже вошёл в систему на этой
машине), у git — сам `git`. Попутно два сервера покрывают **оба способа передачи** (удалённый HTTP
и местный процесс через stdio), так что код с первого дня не заточен под один.

Отвергнуто: DeepWiki, Microsoft Learn, Context7 — публичные и без ключа, показ проще, но сравнить
их с CLI не с чем, и к середине недели пришлось бы менять выбор. Добавить любой из них позже —
одна запись в файле серверов, кода не требует.

### Где живёт код — модуль `myharness`, а не отдельный сценарий

Сравнение недели пойдёт через агента: DeepSeek получает инструменты либо от MCP, либо «навык +
оболочка», и решает одну задачу. Вызов инструментов у `myharness` уже есть (день 13). Отдельный
сценарий «подключись и выведи» пришлось бы переносить в `myharness` через день — это и есть
«переписывать 30 раз». Поэтому:

- новый модуль `myharness/src/myharness/mcp_client.py` (имя `mcp.py` заслонило бы библиотеку):
  открыть соединение с сервером по записи настроек, получить список инструментов, закрыть;
  соединение открывается как асинхронный контекст, чтобы завтрашний вызов инструмента лёг поверх
  того же сеанса, а не рядом;
- инструменты называются `mcp__<сервер>__<инструмент>` — как в Claude Code; это же имя завтра
  станет именем функции для DeepSeek, и показ с вызовом не разойдутся;
- команда `/mcp` в `myharness`: по каждому серверу — имя, способ передачи, версия протокола,
  число инструментов и их список с первой строкой описания; сбой одного сервера — строка с
  причиной, остальные показываются.

Сегодня **не делаем** перевода инструментов в схему DeepSeek и их вызова: это следующий день, и
заготовка под него была бы заглушкой.

### Где лежит список серверов — `.mcp.json` в рабочем каталоге, формат Claude Code

Ориентир — Claude Code: файл `.mcp.json` в каталоге проекта, ключ `mcpServers`, запись вида
`{"command", "args", "env"}` для stdio либо `{"type": "http", "url", "headers"}` для HTTP,
подстановка `${ПЕРЕМЕННАЯ}` в строках. Тот же файл тогда читает и Claude Code — для сравнения
недели это плюс, а не совпадение. Пишут его только `/mcp add` и `/mcp remove`, и только в рабочем
каталоге; в домашний каталог ничего не пишется.

### Добавление и удаление — `/mcp add` и `/mcp remove` (добавлено пользователем при утверждении)

Ориентир — `claude mcp add` / `claude mcp remove`. Синтаксис:

- `/mcp add <имя> <адрес> [--header "Имя: значение"]…` — сервер HTTP;
- `/mcp add <имя> [--env КЛЮЧ=значение]… -- <команда> [доводы…]` — местный сервер stdio;
  разделитель `--` как у Claude Code: доводы команды сами бывают со знаком `-`;
- `/mcp remove <имя>` — убрать запись.

Расхождение с образцом: у Claude Code способ передачи задаётся флагом `--transport`, потому что
у него два способа по адресу (HTTP и устаревший SSE). Мы поддерживаем один — SSE снят протоколом
с версии 2025-03-26, — поэтому способ определяет сам довод: `http://`/`https://` — HTTP, иначе
нужен `-- <команда>`.

Поведение записи:

- пишется `.mcp.json` рабочего каталога (область «проект» Claude Code); нет файла — заводится;
  остальные ключи файла и прочие серверы сохраняются; запись через временный файл и замену, чтобы
  сбой не оставил полфайла;
- имя уже есть — отказ, как у образца (заменить = `remove`, затем `add`);
- имя — латиница, цифры, `_`, `-`: оно входит в `mcp__<сервер>__<инструмент>`, а это имя
  функции для модели, и API принимает имена функций только из этих знаков; не своя прихоть, а
  требование API;
- `remove` неизвестного имени — отказ со списком имеющихся;
- при добавлении соединение **не** проверяется (как у образца): проверка — `/mcp`, одна для всех.

**Тайны.** Репозиторий челленджа публичный, `.mcp.json` в песочнице дня попадает в него.
Поэтому заголовок `Authorization` с буквальным значением — **отказ** с подсказкой
`${ПЕРЕМЕННАЯ}`; прочие буквальные значения заголовков и `--env` записываются, но с
предупреждением «значение записано в `.mcp.json` открытым текстом». Подстановка — `${ИМЯ}` и
`${ИМЯ:-умолчание}`, как у Claude Code; незаданная переменная без умолчания — строка сбоя у этого
сервера в `/mcp` с именем переменной, а не запрос с пустым токеном.

**Токен GitHub** в файле не хранится: заголовок `Authorization: Bearer ${GITHUB_TOKEN}`,
переменная берётся из `gh auth token` при запуске. Токен не попадает ни в журнал, ни на экран —
то же правило, что для ключа DeepSeek.

## Затронутые способности

- новая способность `openspec/specs/mcp/` — файл серверов, соединение, список инструментов,
  именование, поведение при сбое сервера;
- `openspec/specs/commands/` — команды `/mcp`, `/mcp add`, `/mcp remove`;
- справка (`helpdoc.py`) — раздел о `/mcp`.

## Границы

Делаем: зависимость `mcp`, модуль соединения и списка, `/mcp`, `/mcp add`, `/mcp remove`, проверку без сети (местный
учебный сервер stdio на той же библиотеке, запускаемый проверкой), живой прогон на GitHub и git
из песочницы дня.

Не делаем: вызов инструментов, передачу их модели, ресурсы и подсказки MCP, вход по OAuth,
свой сервер MCP, области записи «пользователь» и «локально» (только проект — `.mcp.json`
рабочего каталога).

## Риски и чем расплачиваемся

- **Сервер GitHub отдаёт и пишущие инструменты** (`create_repository`, `delete_file`, …). Сегодня
  только список — вреда нет. Но с первого вызова инструментов понадобится разрешение на пишущие
  действия; фиксируется здесь, чтобы не всплыло посреди сравнения.
- **Удалённый сервер вне нашей власти**: может сменить адрес или требования ко входу. Проверка
  потому идёт на местном сервере, живой прогон — отдельно.
- **Первый запуск `uvx mcp-server-git`** качает пакет — несколько секунд задержки на видео;
  прогреть до записи.
- Библиотека тянет ещё около 30 пакетов (`httpx`, `pydantic`, `cryptography` и др.) — цена
  официального клиента, принимается.
