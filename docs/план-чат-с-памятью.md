## Изменения требований

Редакция после первого рубежа стадии `Spec` (2026-10-02, восемь находок закрыты формулировками).

Слова: **контекст поиска** — текст, который агент отдаёт поставщику поиска вторым доводом (не
путать с «контекстом запроса» способности `context-strategies`). **Реплика** задания наряда —
сообщение человека из списка `asks`.

- **`agent` → «Найденное в базе знаний идёт в хвост запроса»** (меняется). Поставщик поиска
  зовётся по-прежнему один раз за обмен, до сборки запроса, с двумя доводами: вопрос человека и
  контекст поиска. Состав контекста — по стратегии:
  - `sliding`, `facts` — блок фактов разговора (только `facts`) и строгий хвост завершённых пар,
    тот же, что уйдёт в запрос: выбор хвоста от найденного не зависит;
  - `standard` и `branching` — выжимка, если она есть, и пары памяти агента **на миг вызова
    поиска, до обрезки этого запроса**. Обрезка идёт после поиска и взвешивает найденное, поэтому
    обещать «то же, что уйдёт в запрос» здесь нельзя: состав запроса зависит от найденного.
  При `keep_history` ложь пар в контексте нет. Нет ни фактов, ни выжимки, ни пар — контекст
  пустая строка. Контекст поиска SHALL NOT оседать в памяти агента, файле разговора, выжимке и
  SHALL NOT писаться в журнал своим полем. В контекст SHALL NOT входить слои памяти (карточка,
  рабочее состояние, записи о человеке) и блок «Инварианты».
  Круг получателей поставщика: собеседник главного экрана, задания наряда и **экраны стратегий
  `sliding` и `facts`** (при поле `rag` профиля); исполнители группы, шаги способов, экран и ветви
  Branching — нет. Слои памяти экранам стратегий по-прежнему не достаются (`memory` «Слои памяти
  достаются только собеседнику главного экрана» — цело).
  Соседи: `batch` «Наряд ведёт режим RAG», `mcp` (ниже), `memory` «Рабочее состояние идёт хвостом
  запроса» (место блока найденного не меняется), `profiles` «Режим RAG задаётся полем rag»
  (отсылает к `agent`, не меняется).
- **`mcp` → назначение способности и «Поиск программы»** (меняются). В назначении перечень «у
  собеседника главного экрана и в наряде» заменяется отсылкой к кругу получателей способности
  `agent`. В «Поиске программы» довод вызова — `{"query": <вопрос>}`, а при непустом контексте
  поиска и инструменте `search`, чья входная схема объявляет свойство `context`, —
  `{"query": <вопрос>, "context": <контекст>}`. Схема читается один раз на соединение — заново
  после каждого переоткрытия. Сервер без `context` в схеме получает прежний вызов.
- **`batch`** (меняются четыре требования, одно новое):
  - «Наряд задаёт работу целиком…»: задание несёт вопрос `ask` **либо** список реплик `asks`.
  - Новое **«Задание из нескольких реплик ведёт их одному собеседнику»** (слово «диалог» в
    способности занято смыслом «человек в цикле» и к заданию не применяется). Реплики идут по
    порядку одному собеседнику; что он помнит, решает профиль — `keep_history`, стратегия, окно —
    тем же договором агента, что интерактивный обмен. Хранилища нет: разговор и словарь фактов
    стратегии `facts` живут только в памяти процесса и на диск не пишутся (оговорка к
    `context-strategies` «Состояние стратегии переживает перезапуск» и `memory` «Факты текущего
    разговора хранятся журналом операций»: в наряде журнала операций нет). Сбой реплики
    останавливает задание, остальные задания идут.
  - «Непригодное задание пропускается с предупреждением»: в текст и сценарии — три новых вида
    непригодности: `ask` и `asks` вместе; `asks` не список либо пустой; в `asks` не непустая
    строка.
  - «Результаты идут в журнал с общим run_id»: запись журнала — на **реплику**, а не на задание
    (сценарий «три задания → три записи» сужается до заданий с одним вопросом, добавляется
    сценарий задания из трёх реплик → три записи с номерами обмена 1–3). Строка сводки задания
    из нескольких реплик несёт: исход (`ок` — отвечены все реплики), **время — сумму по
    отправленным репликам**, расход собеседника целиком и «реплик N из M».
  - «Наряд не сохраняет и не восстанавливает разговор»: сценарий уточняется до «ни одно задание
    не получило пар прежнего разговора каталога» — свои пары вторая реплика получает.
  - «Пакетный режим использует стратегию профиля без диалога» — не меняется.
- **`journal` → «Запись прогона содержит всё для кривой расхода»** (одна фраза). «Номер обмена в
  сеансе» уточняется: поле `index`, счёт ведёт агент — это номер обмена **этого собеседника**; у
  задания наряда из нескольких реплик он равен номеру реплики. Требование `batch` ссылается на
  него этими словами.
- **`context-strategies` → «Sticky Facts обновляются после каждого сообщения пользователя»**
  (дополняется). Извлекаемое: явно сказанные устойчивые требования, решения, ограничения,
  **цель разговора и определения терминов**. **Инструкция извлекателя** SHALL требовать ключ с
  приставкой рода и без пробелов: `цель`, `термин:<слово>`, `ограничение:<о_чём>`,
  `уточнение:<о_чём>` (слова внутри — через `_`). Словарь при этом принимает любой непустой
  ключ: ключ, записанный человеком (`/facts set cancel_notice …`), и ключи прежних журналов
  операций остаются годными. Ключ без пробелов — потому что `/facts set <ключ> <значение>`
  (способность `commands`) режет ключ по первому пробелу: ключ с пробелом человек не смог бы
  исправить командой. Приставка `ограничение:` — факт разговора, а не инвариант (`invariants`
  уже говорит, что факты разговора инвариантами не являются).
  Соседи: `journal` «Извлечение Sticky Facts связано с основным обменом», `commands` `/facts` —
  не меняются.
- `memory`, `profiles`, `interface`, `commands`, `invariants` — не задеваются. Строка `/system`
  о режиме RAG (`memory` «Человек видит раскладку слоёв целиком») описана для главного экрана и
  остаётся такой: на экранах стратегий раскладки слоёв нет.

## Договоры модулей

### `rag/server.py` — инструмент `search`
**Владеет**: ничем на диске; индекс только читает.
**Отдаёт**: `search(query: str, k: int | None = None, context: str | None = None) -> str`.
**Обещает**: без `context` (нет либо пустой после `strip`) ответ тот же байт в байт, что в дне 24.
С `context` ответ начинается строкой `Вопрос для поиска: <развёрнутый вопрос>`, за ней пустая
строка, дальше прежний вид: куски `[n] <путь> › <раздел> · <chunk_id> (счёт)` либо строка пустого
итога. Развёрнутый вопрос — одна строка. Весь прежний поиск (переписывание, K₁, K₂, τ) идёт по
развёрнутому вопросу. `rag/cite.py::найденное` разбирает ответ с первой строкой без правок
(заголовок `[1]` стоит после пустой строки).
**Не делает**: не хранит разговор; ключ читает из настроек `myharness`, копий не заводит.

### `myharness` — поставщик поиска агента
**Отдаёт**: вид поставщика `async (вопрос: str, контекст: str) -> str` (было `(вопрос)`).
**Обещает**: контекст — пустая строка, когда у агента нет ни фактов разговора, ни выжимки, ни
отобранных пар; агент зовёт поставщика по-прежнему один раз за обмен.
**Читатели**: `state.поставщик_поиска`, `batch.run_order`, проверки с поддельным поставщиком.

### Файл ожиданий сценариев — `week_5/day_5/test/ожидания.json`
Читает `rag/chat_eval.py`, пишет шаг 7.
```json
{"сценарии": [{
  "agent": "<имя задания наряда>",
  "цель": "<цель словами — для судьи и заголовка>",
  "словарь": [{"приставка": "цель", "содержит": ["памятк"]}],
  "снято":   [{"приставка": "ограничение", "содержит": ["openspec"]}],
  "реплики": [{"вид": "ответ", "ссылка": false, "источники_из": null}]
}]}
```
`реплики` — по записи на реплику наряда, в том же порядке. `вид`: `ответ` либо `отказ`.
`ссылка: true` — реплика с местоимением: отчёт показывает развёрнутый вопрос. `источники_из` —
начало пути, с которого обязан начинаться путь каждого источника этой реплики (`null` — нет
ограничения). `словарь` — ключи, обязанные быть в словаре последней реплики: ключ начинается с
`приставка`, а ключ вместе со значением содержит каждую подстроку из `содержит` без учёта
регистра. `снято` — такие ключи быть не должны.

## Шаг 1. Сервер поиска разворачивает уточняющую реплику по контексту разговора
**Файлы**: `rag/rewrite.py`, `rag/server.py`, `rag/check_rag.py`
**Зависит от**: ничего
**Ход**: быстрый — читатели за границей файлов (поставщик `myharness`, `cite.py`, `chat_eval.py`)
закрыты договором выше; просмотр — общий со швом шага 2.
**Требование**: не про `myharness`
**Проверка**: живой вызов из каталога `rag/` — `найти_текст("а кто их открывает?", …)` без
контекста и с контекстом «Человек: Что такое ворота автомата задачи? / Ассистент: …»: во втором
ответе первая строка «Вопрос для поиска:» называет ворота автомата, и среди кусков есть
`openspec/specs/task-machine/spec.md`; в первом такого куска нет либо сработал порог.
**Содержание**:
- `rewrite.py`: константа `ИНСТРУКЦИЯ_РАЗВОРОТА` — «по контексту разговора (факты и последние
  реплики) перепиши последнюю реплику человека в самостоятельный вопрос: раскрой местоимения и
  отсылки, подставь зафиксированные термины их определениями; реплику, понятную без контекста,
  верни как есть; не отвечай и ничего не добавляй от себя; одна строка». Функция
  `развернуть(вопрос: str, контекст: str, *, клиент=None) -> str`: тело — `МОДЕЛЬ`,
  `temperature` 0, рассуждения выключены, сообщение пользователя
  `"Контекст разговора:\n{контекст}\n\nПоследняя реплика человека:\n{вопрос}"`; ответ сжимается
  в одну строку; пустой — `ОшибкаПереписывания("DeepSeek вернул пустой вопрос")`.
- `server.py`: `найти_текст(вопрос, поиск, настройки, k=None, переписать=пер.переписать, контекст: str | None = None, развернуть=пер.развернуть)`:
  при непустом контексте `вопрос = развернуть(вопрос, контекст)` до всего остального, и итог
  получает приставку `f"Вопрос для поиска: {вопрос}\n\n"` — и перед кусками, и перед строкой
  пустого итога. `search` получает довод
  `context: Annotated[str | None, Field(description="Контекст разговора: факты и последние реплики — чтобы развернуть уточняющий вопрос")] = None`.
  Описание формата в шапке модуля дополняется строкой о первой строке.
- `check_rag.py` (поддельные `переписать` и `развернуть`, без сети): без контекста ответ равен
  прежнему и `развернуть` не зван; с контекстом — зван один раз с обоими доводами, поиск получил
  развёрнутый вопрос, ответ начинается со строки «Вопрос для поиска:», `cite.найденное` от
  «заголовок + ответ + вопрос» даёт те же куски; пустой итог с контекстом несёт обе строки и
  `cite.ПУСТО`; контекст из одних пробелов равен отсутствию.

## Шаг 2. Агент передаёт поиску контекст разговора
**Файлы**: `myharness/src/myharness/agent.py`, `mcp_tools.py`, `state.py`, одна строка `batch.py`,
`myharness/tests/check_units.py`, `openspec/specs/agent/spec.md`, `openspec/specs/mcp/spec.md`
**Зависит от**: шаг 1 (договор `context`)
**Ход**: быстрый — читатель за границей файлов один, сервер шага 1, и он под договором; шов
«агент → `Поиск.найти` → `search`» смотрится одним независимым просмотром вместе с шагом 1.
**Требование**: `agent` → «Найденное в базе знаний идёт в хвост запроса»; `mcp` → «Поиск программы»
**Проверка**: проверка с учебным сервером MCP (`tests/mcp_учебный_сервер.py`, инструмент `search`
с `context` в схеме и без) — второй обмен агента со стратегией `facts` и одним фактом доносит до
сервера `context` с блоком фактов и первой парой; сервер без `context` в схеме получает только
`query`; первый обмен пустого разговора — только `query`.
**Содержание**:
- `agent.py`: метод `_контекст_поиска(self) -> str`. Части через пустую строку: блок фактов
  разговора `context_strategy.conversation_facts_block(self._conversation_facts.values)` — только
  у стратегии `facts`; блок выжимки `self._блок_выжимки()` — только у `standard`; пары —
  у `sliding`/`facts`
  `context_strategy.select_history(self._messages, strategy, self.profile.strategy_window).messages`,
  у `standard` и `branching` — `self._messages` (память на миг вызова, до обрезки); при
  `keep_history` ложь пар нет. Пары печатаются под строкой `Разговор до этой реплики:` как
  `Человек: <текст>` / `Ассистент: <текст>`. Ничего нет — пустая строка. `_найти` зовёт
  `await self._поиск(content, self._контекст_поиска())`. Пояснение у `self._поиск` — новый вид.
- `mcp_tools.py`: `_Держатель` получает поле `доводы_поиска: frozenset[str] | None = None`.
  `Поиск.найти(self, каталог, сервер, вопрос, контекст: str = "")`: при непустом контексте и
  `доводы_поиска is None` — `list_tools()` сессии под тем же пределом вызова, имена свойств
  `inputSchema["properties"]` инструмента `search` кладутся в поле (нет инструмента — пустое
  множество); сбой чтения схемы — тот же `RuntimeError` через `описать_сбой`. Доводы вызова —
  `{"query": вопрос}`, плюс `"context": контекст`, когда контекст непуст и `"context"` в
  множестве. Два вызова `call_tool` сводятся к одной переменной доводов.
- `state.py`: `def поставщик_поиска(state: State, profile: Profile)` — возвращает `None` без
  `profile.rag`, иначе `lambda вопрос, контекст: state.поиск.найти(Path.cwd(), profile.rag, вопрос, контекст)`;
  `главный_агент` берёт его. `batch.py:238` — лямбда с двумя доводами.
- Проверки: `_контекст_поиска` у пустого агента — `""`; у `facts` с фактом и шестью парами при
  окне 4 — блок фактов и ровно четыре последние пары; у `standard` — все пары; контекста нет в
  `agent._messages` и в файле разговора после обмена; существующие проверки с поддельным
  поставщиком переведены на два довода.
- Требования: правка двух требований по разделу «Изменения требований», сценарии «второй обмен
  несёт контекст», «сервер без довода context».

## Шаг 3. Экраны Sliding Window и Sticky Facts ищут в базе знаний
**Файлы**: `myharness/src/myharness/strategies.py`, `myharness/tests/check_units.py`,

**Зависит от**: шаг 2 (`state.поставщик_поиска`)
**Ход**: быстрый — читателя за границей файлов нет.
**Требование**: `agent` → «Найденное в базе знаний идёт в хвост запроса» (круг получателей)
**Проверка**: проверка — у экрана `facts`, созданного `create_strategy_screen` для профиля с

вопросу:»; у экрана Branching и у профиля без `rag` блока нет. Живьём: шаг 8, видео.
**Содержание**: `_linear_strategy_agent(profile, pane_key, поиск=None)` передаёт `поиск` в
`Agent`; `create_strategy_screen` зовёт его с `поиск=поставщик_поиска(state, profile)`. Остальные

## Шаг 4. Задание наряда ведёт диалог из списка реплик
**Файлы**: `myharness/src/myharness/batch.py`, `myharness/tests/check_units.py`,
`openspec/specs/batch/spec.md`, `openspec/specs/journal/spec.md` (одна фраза)
**Зависит от**: шаг 2 (вид вызова поставщика в `batch.py`)
**Ход**: быстрый — читатель за границей файлов — журнал, а его запись не меняется (`agent`,
`run_id`, `index` уже есть).
**Требование**: `batch` → «Наряд задаёт работу целиком…», «Непригодное задание пропускается…»,
«Результаты идут в журнал с общим run_id», «Наряд не сохраняет…» (сценарий), новое «Задание из нескольких реплик ведёт их одному собеседнику»
**Проверка**: **первый живой обмен дня.** Песочница в каталоге черновиков сеанса: профиль
(`context_strategy: facts`, `rag`, `keep_history: true`, инструкция дня 24), `.mcp.json` дня 24,
наряд из одного задания с `asks` из трёх реплик («Что такое ворота автомата задачи?», «А кто их
открывает?», «А что с ними делает пауза?»). В журнале три записи одного `agent` с `index` 1–3; у
второй и третьей последнее сообщение несёт «Вопрос для поиска:» с воротами автомата и куски
`task-machine`; ответы с тремя разделами.
**Содержание**:
- `Task`: поле `asks: tuple[str, ...]` вместо `ask`; свойство `ask` — первая реплика (для строки
  хода и старых читателей).
- `_task_from_dict`: есть оба поля — «заданы и «ask», и «asks» — пропущено»; `asks` — не список,
  пустой список либо в нём не непустая строка — «поле «asks» — ожидался непустой список реплик —
  пропущено»; только `ask` — как раньше, `asks = (ask,)`.
- `run_order.one`: цикл по `task.asks` одним `Agent`; строка хода на реплику
  `[{position}/{total}] {task.agent} → {order.model} [{n}/{len(task.asks)}]: {реплика}` (у задания
  с одной репликой — прежняя строка без скобок); первый `turn` с `ok` ложь обрывает цикл.
  Возвращается последний `Turn` копией (`dataclasses.replace`) с `elapsed_ms`, равным сумме по
  отправленным репликам; запись журнала каждой реплики уже сделана агентом и своё время несёт.
  Новых полей у `Turn` нет: номер отправленной реплики — его существующее поле `index` (счётчик
  обменов собеседника).
- `summary_lines`: у задания с `len(task.asks) > 1` расход — `turn.agent_session_tokens` (как у
  `facts`); отвечено реплик — `turn.index` при `turn.ok`, иначе `turn.index - 1`; состояние `ок`
  только когда отвечены все; в хвост строки дописывается `реплик {отвечено} из {len(task.asks)}`.
- Проверки: разбор трёх негодных видов и годного; три реплики поддельным клиентом — три вызова,
  второй запрос несёт первую пару, записи журнала с `index` 1, 2, 3; сбой второй реплики —
  третья не отправлена, сводка «сбой … реплик 1 из 3», соседнее задание выполнено; в каталоге
  состояния файлов не появилось.
- Требование `batch`: правки по разделу «Изменения требований».

## Шаг 5. Извлекатель кладёт в словарь цель и термины с приставкой рода
**Файлы**: `myharness/src/myharness/sticky_facts.py`, `myharness/tests/check_units.py`,
`openspec/specs/context-strategies/spec.md`
**Зависит от**: шаг 4 (живая проверка идёт нарядом-диалогом)
**Ход**: быстрый — читателя за границей файлов нет: ключи словаря программа не разбирает.
**Требование**: `context-strategies` → «Sticky Facts обновляются после каждого сообщения пользователя»
**Проверка**: **отладочный сценарий** (в отчёт не идёт) — наряд-диалог из шести реплик в той же
песочнице: цель, термин, ограничение, уточнение, отмена ограничения, вопрос. Системная часть
шестого запроса несёт ключи `цель`, `термин:…`, `уточнение:…`, ключа отменённого ограничения
нет. Инструкция правится на этом сценарии до годного словаря; на контрольных сценариях шага 7 она
не правится.
**Содержание**: в `EXTRACTOR_INSTRUCTION` — перечень извлекаемого: «устойчивые требования,
решения и ограничения разговора, **цель разговора и определения терминов**»; абзац о ключах:
«Ключ начинай приставкой рода: `цель` — одна на разговор, новая цель заменяет прежнюю;
`термин:<слово>`; `ограничение:<о_чём>`; `уточнение:<о_чём>`. В ключе нет пробелов: слова
соединяй знаком `_`. Вопрос человека фактом не является». Пример в конце инструкции — с
приставками. Проверка: инструкция называет четыре приставки и правило о пробелах;
`parse_changes` принимает ключ `термин:ворота`; `/facts set термин:ворота <новое значение>`
заменяет значение того же ключа, а не заводит второй.

## Шаг 6. Отчёт по журналу диалога: источники, цитаты, цель, словарь
**Файлы**: `rag/chat_eval.py`, `rag/check_rag.py`

**Ход**: быстрый — читатель за границей файлов — файл ожиданий, он под договором.
**Требование**: не про `myharness`
**Проверка**: отчёт по журналу отладочного сценария шага 5 с маленьким файлом ожиданий: таблица
шести реплик, развёрнутые вопросы, словарь, вердикты судьи файлом; повторный запуск судью не
зовёт.
**Содержание**:
- Запуск: `uv run --project rag rag/chat_eval.py --journal <журнал> --run <run_id> --ожидания <файл> --вердикты <файл.json> --выход <проверка.md>`.
- Записи сценария: строки журнала с `run_id`, `agent` из ожиданий, без записей извлекателя
  (`agent` ≠ имя задания), по возрастанию `index`. Число записей меньше числа реплик — отчёт
  называет недостающие, а не молчит.
- По реплике: `cite.разобрать(response)`; куски — `cite.найденное(messages[-1].content, query)`;
  источники есть и годны (`cite.источник_годен`), цитаты есть и дословны
  (`cite.цитата_дословна`); `источники_из` — путь каждого источника начинается с него; для

  (ложный отказ); развёрнутый вопрос — первая строка блока после заголовка, начинающаяся

- Словарь реплики — строки `- ключ: значение` блока «Факты текущего разговора (Sticky Facts):»

- Судья цели: `deepseek-v4-pro`, рассуждения включены, через `пер.спросить`; вход — цель из
  ожиданий, словарь реплики, реплика, раздел «Ответ»; выход JSON
  `{"вердикт": "служит" | "уходит в сторону" | "нарушает", "довод": "<одна строка>"}`. Зовётся
  только для `вид: ответ`. Вердикты — файлом по ключу `<agent>:<index>`, как `Вердикты` в
  `cite_eval.py` (класс переиспользуется ввозом оттуда).
- Отчёт: шапка с `run_id` и номером фиксации сценариев (довод `--фиксация`); по сценарию —
  итоговая строка (источники n из N ответов, цитаты дословны, ограничение соблюдено, служит цели,
  отказы k из K, словарь), таблица по репликам, под ней по реплике: реплика, развёрнутый вопрос,
  ответ целиком, вердикт судьи с доводом; словарь на последней реплике.
- `check_rag.py`: сборка отчёта из поддельного журнала двух реплик и поддельного судьи —
  годный ответ, ложный отказ, источник вне `источники_из`, недостающая запись, сверка словаря.
