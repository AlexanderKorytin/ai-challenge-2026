# Дизайн: веб-чат поддержки (продолжение дня 33)

## Задача и видение

День 33 сдал ассистента поддержки в окне терминала `myharness`. Вход в нём задавала переменная
`SUPPORT_USER`, а CRM только читалась. Ментор сказал: «чат логичнее» и «сделать из этого рабочий
продукт». Отсюда решение пользователя: учебный веб-чат. Человек входит по имени без пароля,
спрашивает, а ассистент заводит тикеты и ведёт их.

Решения пользователя:

- новое имя на входе заводит нового пользователя;
- страницы специалиста нет, только клиент.

## Что решили и почему

1. **Веб-сервер в папке дня, агент — `myharness` библиотекой.** Каталог `week_7/day_3/web/`
   содержит своё приложение Starlette с `uvicorn`, тот же стек, что у шлюза дня 30. Ответ даёт
   класс `Agent` из `myharness`, инструменты подключает тот же мост `mcp_tools.Соединения`, что и в
   окне. Код `myharness` не меняется. Отвергнуто: свой круг вызовов DeepSeek в веб-сервере. Это был
   бы второй агент рядом с работающим.
2. **Вход по имени.** Человек вводит имя, сервер ищет его без учёта регистра. Если имя найдено,
   это вход под этим пользователем. Если нет, сервер заводит нового пользователя со следующим
   номером `U-NN` и пустым окружением. Окружение ассистент узнаёт из разговора и пишет в тикет.
   Сеанс держит случайный номер в куке, а соответствие номера пользователю хранит память сервера.
   Пароля нет: под любым именем может войти любой. Это учебное допущение, и страница говорит о нём.
3. **Пользователь сеанса задаётся файлом, а не окружением процесса.** На каждого пользователя
   заводится каталог `web/сеансы/<U-NN>/`. В нём лежат `.mcp.json`, где `SUPPORT_USER` записан
   значением, и `.claude/settings.json` с разрешёнными инструментами. Мост `Соединения` читает этот
   каталог и запускает сервер `support` под этим пользователем. Два человека в браузере получают
   два процесса сервера, и данные не путаются. Отвергнуто: менять `os.environ` перед запуском
   сервера. Два одновременных входа подменили бы пользователя друг другу.
4. **Запись в CRM — три новых инструмента сервера `support`.**
   - `create_ticket(subject, text, error)` заводит тикет вошедшего пользователя со статусом
     «открыт» и номером `T-NNNN` по порядку;
   - `add_message(ticket_id, text)` дописывает в переписку своего тикета ответ ассистента
     (автор «ассистент»);
   - `set_status(ticket_id, status, resolution)` ставит статус «открыт», «ждёт специалиста» или
     «закрыт». Для «закрыт» поле `resolution` обязательно.

   Чужой тикет любой из трёх инструментов отвергает так же, как `get_ticket`. Запись идёт под
   блокировкой файла (`fcntl.flock`) через временный файл и переименование. Обрыв не оставит
   половину JSON, а два процесса сервера не затрут записи друг друга. Новые инструменты разрешены
   только в веб-сеансах. Терминальная песочница дня 33 остаётся только для чтения.
5. **Рабочие данные отдельно от данных в git.** При первом запуске веб-сервер копирует
   `support/данные.json` в `web/данные.json`, и путь передаётся серверу через `SUPPORT_DATA`.
   Записи чата не портят исходные данные сценария. Рабочая копия в git не попадает.
6. **Когда ассистент пишет.** Порядок задаёт инструкция профиля:
   - ответ нашёлся в документации — ассистент отвечает и дописывает ответ в тикет, если тикет есть;
   - проблема без тикета — ассистент предлагает завести тикет и заводит его, когда человек согласен;
   - ответа в документации нет — тикет получает статус «ждёт специалиста»;
   - человек сказал, что всё заработало, — тикет закрывается с причиной.

   Профиль остаётся одним, `поддержка`. Строки о записи срабатывают, только если у модели есть эти
   инструменты.
7. **Страница.** Одна страница HTML без сборки:
   - вход — поле имени;
   - чат — реплики, ответ приходит потоком, вызовы инструментов показаны короткими строками
     («открыл тикет T-1001», «искал в документации»);
   - справа список тикетов пользователя со статусами, обновляется после каждого ответа;
   - выбор модели: `deepseek-v4-flash` или местная `ollama/qwen3.5:9b-q4_K_M-32k`.

   Разговор хранит `memory.SessionStore` в каталоге пользователя. Повторный вход продолжает
   разговор, кнопка «Новый разговор» начинает заново. Одновременно идёт один обмен на пользователя.
8. **Где работает.** Адрес `127.0.0.1:8790`, только этот Мак. Наружу сервер не открывается: без
   пароля это открытая дверь.

## Затронутые способности

Требования `openspec/specs` не задеваются: код `myharness` не меняется, веб-чат зовёт его открытые
`Agent`, `memory.SessionStore`, `mcp_tools.Соединения`, `api.Clients`, `profiles`.

## Границы

Делаем: вход по имени, новый пользователь, чат с потоком ответа, три инструмента записи, список
тикетов, выбор модели, проверки сервера и веб-приложения, живой прогон в браузере, новый ролик.

Не делаем: пароли и настоящую проверку личности, страницу специалиста, доступ из сети, правку
окружения пользователя из чата, удаление тикетов.

## Риски

- **Вход без пароля.** Любой войдёт под Анной и увидит её тикеты. Учебное допущение, адрес только
  `127.0.0.1`.
- **Модель решает, когда писать.** Модель может завести лишний тикет или закрыть тикет без
  согласия человека. Инструкция требует согласия, а запись видна в списке тикетов. Местная модель
  ошибается здесь чаще: в дне 33 она пропускала поиск.
- **Процессы серверов MCP.** У каждого вошедшего свои процессы `support` и `rag`. Выход и остановка
  сервера их закрывают. Сеанс, брошенный без выхода, держит процессы до остановки веб-сервера.
  Срок простоя я не ставлю: такого предела нет в задании.
