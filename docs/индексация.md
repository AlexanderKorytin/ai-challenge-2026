# Дизайн: индексация документов (день 21)

## Задача и видение

Условие: взять набор документов (≥20–30 страниц), нарезать на куски, посчитать эмбеддинги,
сохранить индекс (FAISS / SQLite / JSON). Усиление: метаданные куска (source, title, section,
chunk_id) и две стратегии нарезки — фиксированным размером и по структуре — со сравнением.

Неделя — RAG, цели: работать с эмбеддерами, искать по базе знаний, включить это в агента,
использовать в реальной работе. Видение пользователя: «придумай, на чём будем проверять».
Эмбеддер выбран пользователем: **Ollama + `bge-m3`, локально**.

## Что решили и почему

### Корпус — знания самого проекта

`openspec/specs/*/spec.md` (18 способностей `myharness`), `docs/**/*.md` (дизайны, планы,
состояния, грабли, отложенное) и `CLAUDE.md`. Около 1,5 МБ русского текста — сотни страниц,
условие перекрыто многократно.

Почему он, а не случайные статьи: к концу недели агент отвечает на вопросы о самом `myharness`
по его же требованиям — это и есть цель «использовать в реальной работе». И только на своём
корпусе правильный ответ известен заранее, а значит сравнение стратегий — число, а не
впечатление.

Корпус берётся снимком рабочего дерева `main`; хеш фиксации пишется в индекс, чтобы было видно,
от какого состояния знаний он собран.

### Эмбеддер — `bge-m3` через Ollama

Ollama — местная служба с HTTP API (`POST /api/embed`, пачкой). `bge-m3` многоязычный, русский
знает хорошо, вектор 1024 числа, окно 8192 токена. Программа говорит со службой по HTTP, как со
всеми службами челленджа, и не тащит в себя PyTorch. Векторы нормируются, близость — косинус.

Отвергнуто: `sentence-transformers` в процессе (PyTorch ~2 ГБ зависимостей ради одного вызова);
облачные эмбеддеры (нет ключа, решение пользователя).

### Две стратегии нарезки

- **`fixed` — фиксированным размером.** Окно в N символов с перекрытием 20 %. Доля перекрытия
  взята по умолчаниям LangChain (`RecursiveCharacterTextSplitter` в документации: 1000/200) и
  LlamaIndex (`SentenceSplitter`: 1024/200). **N не выдумывается**: оно равно медиане длины
  кусков стратегии `structure` на этом же корпусе. Так сравнение меряет *где режем*, а не
  *сколько кладём в кусок* — иначе разница в размере смешалась бы с разницей в границах.
- **`structure` — по структуре.** Файл режется по заголовкам Markdown; кусок — раздел вместе с
  подразделами до уровня `###`. Для OpenSpec это ровно «требование со всеми его сценариями»
  (`### Requirement:` + `#### Scenario:`), для `docs/` — раздел `##`/`###`. Раздел, не
  влезающий в окно эмбеддера (8192 токена), делится по абзацам — это не выдуманный предел, а
  граница модели. Текст до первого заголовка — отдельный кусок.

В обеих стратегиях эмбеддится сам текст куска без подмешивания заголовков — чтобы сравнение
было честным. Подмешивание «хлебных крошек» — известный приём, его можно будет замерить
третьей строкой в следующие дни.

### Метаданные куска

| поле | что |
|---|---|
| `chunk_id` | `<стратегия>:<путь>:<номер>` — устойчив при пересборке того же снимка |
| `strategy` | `fixed` / `structure` |
| `source` | путь файла от корня репозитория |
| `title` | заголовок `#` файла (для спецификации — имя способности) |
| `section` | цепочка заголовков, под которой кусок начинается: `Requirement: … › Scenario: …` |
| `start`, `end` | смещения в символах внутри файла |
| `commit` | хеш снимка корпуса |

### Индекс — SQLite

Один файл `index.sqlite`: таблица кусков (метаданные + текст + вектор `float32` блобом) и
таблица сведений о сборке (модель, размерность, фиксация, дата, стратегия). Поиск — полным
перебором через `numpy`: на нескольких тысячах кусков это миллисекунды. FAISS отвергнут — при
таком объёме он даёт только лишнюю зависимость; понадобится, когда кусков будут сотни тысяч.

### На чём проверяем — контрольный набор

Файл контрольных вопросов (25–30 штук): вопрос своими словами (не цитатой) и **ключевой
фрагмент** — дословная короткая строка из текста, где лежит ответ. Попадание: ключевой фрагмент
целиком содержится в найденном куске. Порогов перекрытия нет — фрагмент либо в куске, либо
разрезан/не найден. Разрезанный фрагмент — это ровно беда нарезки фиксированным размером, и
мера её честно ловит.

Сравнение (`сравнение.md`, собирается программой):

- число кусков, длина — наименьшая / медиана / наибольшая;
- сколько кусков `fixed` пересекают границу раздела (режут требование пополам);
- `hit@1`, `hit@5`, MRR по контрольному набору;
- время сборки индекса и размер файла;
- по каждому вопросу: на каком месте нашёлся нужный кусок в каждой стратегии.

### Где живёт код

Отдельный проект `rag/` в корне репозитория (свой `pyproject.toml` на `uv`, как
`mcp_servers/pipeline`): `rag index --strategy fixed|structure|all`, `rag search "<вопрос>"`,
`rag compare`. Код общий на неделю — завтрашний поиск и включение в агента (вероятно, MCP-сервер
по образцу дня 17–19) строятся поверх него, поэтому он в `main`, а не в ветке дня. Проверки —
`rag/tests/` без Ollama (подставной эмбеддер).

## Затронутые способности

`myharness` не меняется, требования `openspec/specs/` не задеваются. Включение поиска в агента —
следующие дни недели, тогда и появится изменение OpenSpec.

## Границы

Делаем: нарезку двумя стратегиями, эмбеддинги, индекс SQLite с метаданными, поиск из командной
строки (без него нечем мерить), контрольный набор и сравнение.

Не делаем: ответ модели по найденному (генерацию), повторное упорядочивание, смешанный поиск
по словам, включение в `myharness`, PDF — корпус уже текстовый.

Для дня: ветка `w5d1`, в ней папка `week_5/day_1/` с `README.md`, итоговым `сравнение.md` и
видеоотчётом.

## Риски и чем расплачиваемся

- **Контрольный набор пишет тот же, кто пишет нарезку** — возможен перекос в пользу одной
  стратегии. Смягчение: вопросы формулируются до первого прогона и фиксируются в git до
  результатов; ключевые фрагменты берутся из разных мест разделов, не только из заголовков.
- Корпус — русский Markdown одного стиля: вывод о стратегиях верен для структурированной
  документации и не переносится на сплошной текст без заголовков.
- Ollama — ещё одна служба на Маке (`brew services`), модель ~1,2 ГБ на диске.
- Индекс устаревает при правке документов — пересборка вручную командой; наблюдение за
  изменениями не делаем.
