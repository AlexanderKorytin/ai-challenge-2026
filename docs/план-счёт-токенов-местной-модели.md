# План: счёт токенов местной модели словарём модели

Дизайн: `docs/счёт-токенов-местной-модели.md`. Состояние:
`docs/состояние-счёт-токенов-местной-модели.md`. Общая задача в `main`, ветка и папка дня не
заводятся.

Все пути ниже — от `myharness/`. Проверки запускаются так:
`uv run --project myharness python myharness/tests/check_units.py`.

## Изменения требований

Раздел переписан после первого рубежа стадии `Spec` (2026-10-06, четыре находки).

**`tokens`**

- «Точный счёт офлайн» меняется. Слово «словарь» получает уточнение: словарь DeepSeek из пакета
  либо словарь местной модели от службы. Счёт местной модели точен, когда служба отдала словарь
  знакомого вида (`gpt2` с разбивкой `qwen2` или `qwen35`); иначе идёт словарём DeepSeek и
  помечен приблизительным. Счёт по знакам действует, когда для модели нет ни одного словаря.
  Сценарий «модель местная, словарь на месте» делится на два. Запомненные подсчёты различают
  словари.
- Там же закрепляется смысл слова «точный»: оно относится к счёту текста. Надбавка обёртки
  разговора (83) и обёртка инструментов (190) замерены на DeepSeek и для местной модели служат
  начальным приближением; надбавку разговора подстройка исправляет по первому ответу службы.
  Замер местной модели 2026-10-06 вписывается справкой: 5 токенов на реплику и 7 сверх них,
  197–199 сверх JSON схем.
- Фразы «точный итог знает только сервер» и «точный расход местной модели приходит от службы»
  получают оговорку о числе рассуждений.
- «Вес запроса известен до отправки» дополняется: вес реплик, инструментов и памяти считается
  словарём той модели, которой уходит запрос.
- «Итог сеанса складывается из обменов» дополняется явным исключением. Служба Ollama числа
  рассуждений не называет. При точном словаре модели программа считает его по тексту
  рассуждений, не даёт ему превысить `completion_tokens` и ставит признак
  `"reasoning_tokens_source": "program"` на верхнем уровне расхода обмена. Число, которое
  служба назвала сама, программа не заменяет. Правило «известный серверный расход не подменён
  вычисленным числом» остаётся: подмены нет, заполняется отсутствующее, и это помечено.

**`journal`** — «Журнал позволяет сравнить стратегии без догадок» дополняется фразой: число
рассуждений с признаком `reasoning_tokens_source: program` посчитано программой, а не службой.

**`api`** — новое требование «Словарь местной модели»: клиент запрашивает словарь у службы
(`/api/show`, `verbose: true`) при той же подготовке модели, что и окно (требование об окне
живёт в `tokens`, «О переполнении окна сказано до отправки», — ссылка на него), один раз на
модель за сеанс, когда служба ответила; молчащую службу спрашивают снова при следующей
подготовке (находка второго рубежа); сбой запроса и незнакомый вид словаря запуск и обмен не
роняют. Туда же три обязанности, появившиеся при исполнении: выражения разбивки берутся из
исходников (`tokens`), подготовка идёт до первого счёта и в пакетном режиме, сборка счётчика не
задерживает отрисовку (`api`).

**`agent`**

- «Пустой ответ не считается успехом» переписывается. Действующий текст знает одну причину
  обрыва по длине — «весь `max_tokens` ушёл на рассуждения» — и про окно молчит, хотя код его
  уже различает. Станет три причины: выход последнего круга достиг заданного `max_tokens` —
  предел; вход вместе с выходом достиг окна — окно, с обоими числами; иначе — общая строка
  «ответ оборван по длине, не начавшись». Сценарий «бюджет съеден рассуждениями» получает
  условие «выход достиг `max_tokens`»; добавляются сценарии «окно кончилось» и «предел не
  задан, окно свободно».
- Требование о круге вызовов инструментов: фраза «по входу ПОСЛЕДНЕГО круга» меняется на «по
  расходу ПОСЛЕДНЕГО круга» — теперь сравнивается и выход.
- Там же «оценка веса звеньев приблизительна» остаётся: правило отправки от точности не зависит.

Соседи. `/tokens` описан в `commands`; знака «≈» и строки о причине оценки в требованиях нет —
они живут только в коде, шаг 1 правит текст строки. `interface` помечает приблизительность по
другой причине (нет серверных чисел) и не задет. `context-strategies`, `batch`, `params`,
`memory`, `profiles` проверяющий сверил — противоречий с замыслом нет.

## Уточнение к дизайну, пункт 7

Дизайн называл два исхода: предел либо окно. Чтение кода дало третий: DeepSeek обрывает ответ по
своему умолчанию `max_tokens`, когда человек предел не задавал, а окно свободно. Назвать это
окном — неправда. Поэтому исходов три, третий — общая строка. Числа по-прежнему нет.

## Договор модуля `tokens` (читатели: `api`, `agent`, `compact`, `output`, `ui`, `commands_context`)

**Владеет**: словарём DeepSeek (как сейчас), словарями местных моделей
`_LOCAL_VOCABULARIES: dict[str, Any]` (ключ — полное имя с приставкой `ollama/`), запомненными
подсчётами.

**Отдаёт**:

```python
def build_vocabulary(model_info: dict) -> Any | None
def remember_vocabulary(model: str, vocabulary: Any) -> None
def exact(model: str) -> bool
def count_text(text: str, model: str) -> int
def count_message(message: dict, model: str) -> int
def count_messages(messages: list[dict], model: str, *, overhead: int = BASE_OVERHEAD) -> int
def count_tools(схемы: list[dict], model: str) -> int
```

**Обещает**:

- `model` — обязательный довод без умолчания. Пропущенное место вызова падает с `TypeError` при
  первой же проверке, а не считает чужим словарём молча. Пустая строка означает DeepSeek.
- Местная модель с запомненным словарём считается им, и `exact` для неё истинно. Местная модель
  без словаря считается словарём DeepSeek, `exact` ложно.
- Ключ запомненного подсчёта — пара «имя местной модели со словарём либо пустая строка,
  отпечаток текста». Один текст для двух моделей даёт два числа.
- `build_vocabulary` возвращает `None`, когда `tokenizer.ggml.model` не `gpt2`, когда
  `tokenizer.ggml.pre` нет в таблице `РАЗБИВКИ`, когда полей нет или библиотеки нет.

**Не делает**: в сеть не ходит, на диск словарь местной модели не пишет, исключений из счёта не
выпускает.

## Шаг 1. Текст для местной модели весит столько, сколько скажет её словарь

**Файлы**: `src/myharness/tokens.py`, `agent.py`, `compact.py`, `output.py`, `ui.py`,
`commands_context.py`, `tests/check_units.py`, `tests/check_app.py`

**Зависит от**: ничего

**Ход**: быстрый. Все места вызова меняются в этом же шаге; чужого читателя за его файлами нет.

**Требование**: `openspec/specs/tokens/spec.md` → «Точный счёт офлайн», «Вес запроса известен до
отправки»

**Содержание**:

- Таблица `РАЗБИВКИ: dict[str, str]` — имя `tokenizer.ggml.pre` → выражение. Два имени, оба
  выражения дословно из `llama.cpp`, `src/llama-vocab.cpp` (ветви `LLAMA_VOCAB_PRE_TYPE_QWEN2` и
  `LLAMA_VOCAB_PRE_TYPE_QWEN35`):
  - `qwen2`: `(?:'[sS]|'[tT]|'[rR][eE]|'[vV][eE]|'[mM]|'[lL][lL]|'[dD])|[^\r\n\p{L}\p{N}]?\p{L}+|\p{N}| ?[^\s\p{L}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+`
  - `qwen35`: `(?:'[sS]|'[tT]|'[rR][eE]|'[vV][eE]|'[mM]|'[lL][lL]|'[dD])|[^\r\n\p{L}\p{N}]?[\p{L}\p{M}]+|\p{N}| ?[^\s\p{L}\p{M}\p{N}]+[\r\n]*|\s*[\r\n]+|\s+(?!\S)|\s+`
- `build_vocabulary(model_info)`: читает `tokenizer.ggml.model`, `.pre`, `.tokens`, `.merges`,
  `.token_type`. Собирает `Tokenizer(models.BPE(vocab, merges))`, слияние делит по первому
  пробелу. Разбивка — `Sequence([Split(Regex(выражение), "isolated"), ByteLevel(add_prefix_space=False, use_regex=False)])`.
  Нормализатора нет: NFC ломает счёт (замер: 43 против 47). Токены типа 3 и 4 добавляются как
  `AddedToken(special=True, normalized=False)`.
- `count_text(text, model)`: словарь выбирает `_словарь_для(model)` — местный запомненный, иначе
  DeepSeek. Запасной счёт по знакам остаётся для случая, когда нет ни одного.
- `Agent.history_tokens(model: str)` получает довод; его зовут `output.py:254`,
  `commands_context.py:59` и сам агент — все знают модель.
- `ui.py:1524`: причина оценки для местной модели — «служба не отдала словарь модели либо его
  вид незнаком, счёт идёт словарём DeepSeek».
- Проверки без службы: малый словарь в коде проверки (десяток токенов, три слияния, вид `gpt2`,
  разбивка `qwen35`).

**Проверка**: в `check_units.py` — (а) один текст даёт разные числа для `""` и для местной
модели с малым словарём, и повторный вызов для каждой отдаёт своё число (ключ запомненного);
(б) `exact("ollama/x")` ложно до `remember_vocabulary` и истинно после — парная проверка
соседнего значения; (в) `build_vocabulary` даёт `None` на `tokenizer.ggml.model = "llama"` и на
`pre = "неизвестная"`; (г) вызов `count_text("а")` без модели падает с `TypeError`.

## Шаг 3. Строка «из них рассуждения» у местной модели показывает число

**Файлы**: `src/myharness/agent.py`, `tests/check_units.py`

**Зависит от**: шаг 1

**Ход**: быстрый. Число идёт существующим полем `completion_tokens_details.reasoning_tokens`;
его читатели (`tokens.normalize`, `output.py`, `ui.py`) не меняются.

**Требование**: `openspec/specs/tokens/spec.md` → «Итог сеанса складывается из обменов»

**Содержание**: в агенте, там, где `usage` круга встречается с текстом рассуждений круга:
модель местная, `tokens.exact(model)` истинно, служба числа не дала, текст рассуждений не пуст —
записать в `usage` круга `completion_tokens_details = {"reasoning_tokens": min(tokens.count_text(рассуждения, model), completion_tokens)}` и признак `"reasoning_tokens_source": "program"` на верхнем уровне `usage` (уточнено при исполнении: сумма кругов плоская, вложенный признак в ней терялся).
При неточном словаре поле не трогать: оценка в поле серверного расхода не кладётся.

**Проверка**: `check_units.py`, подменный клиент: местная модель с малым словарём, поток с
рассуждениями и `usage` без подробностей — `normalize(usage)["reasoning_tokens"]` больше нуля и
не больше `completion_tokens`, признак `reasoning_tokens_source` равен `program`; та же модель без словаря — ноль. Живьём: вопрос из наряда шага 2 с
включёнными рассуждениями, число рассуждений плюс счёт текста ответа отличается от
`completion_tokens` службы не больше чем на 5 токенов (метки начала и конца рассуждений).

## Шаг 4. Причина обрыва по длине названа без порога

**Файлы**: `src/myharness/agent.py`, `tests/check_units.py`

**Зависит от**: шаг 3 (тот же файл)

**Ход**: быстрый. Читатель строки ошибки — человек; программного читателя нет.

**Требование**: `openspec/specs/agent/spec.md` → требование о пустом ответе при обрыве по длине

**Содержание**: константа `ОСТАТОК_НА_ОТВЕТ` удаляется. Ветка пустого ответа при
`finish_reason == "length"`, по последнему кругу: `выход = completion_tokens`;
`предел and выход >= предел` → «весь max_tokens ушёл на рассуждения…»; иначе окно известно и
`вход + выход >= окно` → «в окне модели не осталось места на ответ: занято … из …»; иначе —
«ответ оборван по длине, не начавшись». Тексты строк не меняются.

**Проверка**: `check_units.py` — три случая на три строки; проверка на строке 6678 получает
`usage` с `вход + выход = окно`. Живьём на Ollama: родной запрос `/api/chat` с `num_ctx` 256 и
входом около 200 токенов — записать, чему равны `prompt_eval_count + eval_count` и
`done_reason`. Сумма меньше окна — сказать пользователю до фиксации: тогда ветка окна у местной
модели не срабатывает, и решение о ней принимает он.
