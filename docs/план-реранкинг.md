# План: реранкинг и фильтрация (день 23)

Дизайн — `docs/реранкинг.md`. Состояние — `docs/состояние-реранкинг.md`.

## Установлено при составлении плана

- Агент `myharness` зовёт `search` **только с `query`** (`mcp_tools.py:475`) — K₂ поэтому
  задаётся и умолчанием сервера (`RAG_K2`), а не одним доводом `k`.
- Пустое найденное агент в запрос не кладёт вовсе (`agent.py:1398`, `if найденное`), и
  `eval.py` тогда считает, что поиск не состоялся. Значит, при пустом итоге отсечения сервер
  обязан вернуть **непустую** строку — блок найденного будет, а кусков в нём ноль.
- Куски `structure`: 893, средняя длина 1120 символов, самый длинный 15 965 (~5 тыс. токенов) —
  в окно перекрёстного кодировщика (8192) входит без обрезки; своих пределов длины не ставим.
- Адрес DeepSeek — `https://api.deepseek.com/chat/completions`, как у `mcp_servers/pipeline`.

## Договоры

### `rag/rerank.py`
**Владеет**: куски и матрица стратегии, индекс BM25 — загружаются один раз в `Поиск`;
кодировщик грузится лениво при первом вызове режима `model`.
**Отдаёт**:
```python
РЕЖИМЫ = ("base", "threshold", "heuristic", "model")
@dataclass(frozen=True)
class Найденный:
    кусок: Кусок
    счёт: float      # счёт режима: косинус | RRF | вероятность кодировщика
    косинус: float   # наибольший косинус по всем запросам
@dataclass(frozen=True)
class Итог:
    куски: list[Найденный]   # отданные, по убыванию счёта
    кандидатов: int          # вошло во второй этап («до»)
    прошло: int              # прошло порог
class Поиск:
    def __init__(self, индекс: Path, strategy: str = "structure", считать=эм.эмбеддинги,
                 оценщик: Callable[[str, list[str]], list[float]] | None = None): ...
    def упорядочить(self, вопрос: str, режим: str, k1: int, переписанный: str | None = None) -> list[Найденный]
    def отобрать(self, вопрос: str, режим: str, k1: int, k2: int, порог: float | None,
                 переписанный: str | None = None) -> Итог
```
**Обещает**:
- кандидаты = объединение K₁ лучших по косинусу для исходного и (если есть) переписанного
  запроса, без повторов; у `base` K₁ приравнивается K₂;
- `threshold`: счёт = косинус, отсечение `косинус < порог`;
- `heuristic`: счёт = RRF (`Σ 1/(60 + место)`, 60 — постоянная из статьи Cormack и др. 2009 и
  умолчание Elasticsearch и OpenSearch) по выдачам косинуса и BM25 каждого запроса на
  кандидатах; отсечение `косинус < порог`;
- `model`: счёт = вероятность кодировщика для пары (**исходный** вопрос, текст куска);
  отсечение `счёт < порог`;
- `base` порог не принимает; остальные без порога — `ValueError`;
- `упорядочить` возвращает всех кандидатов по убыванию счёта без отсечения — на нём сравнение
  перебирает пороги, не пересчитывая кодировщик.
**Не делает**: на диск не пишет; в сеть ходит только через `считать` (Ollama) и кодировщик
(первая загрузка весов с Hugging Face в `$HF_HOME`).

### `rag/rewrite.py`
**Отдаёт**: `переписать(вопрос: str, *, клиент: httpx2.Client | None = None) -> str`,
`class ОшибкаПереписывания(RuntimeError)`.
**Обещает**: `deepseek-v4-flash`, `temperature` 0, рассуждения выключены; ответ — одна строка
поискового запроса; ключ — поле `api_key` файла `$MYHARNESS_CONFIG_DIR/config.json`, иначе
`~/.config/myharness/config.json`, только чтение; ключ не попадает ни в исключения, ни в вывод.
**Не делает**: на диск не пишет; предела ожидания своего не заводит сверх того, что у
`myharness` (`api.REQUEST_TIMEOUT` — берётся то же число).

### `rag/server.py` (окружение запуска)
`RAG_MODE` (умолчание `base`), `RAG_REWRITE` (`1` — включено), `RAG_K1`, `RAG_K2` (умолчание 5,
как в дне 22), `RAG_THRESHOLD`. Для режимов кроме `base` `RAG_K1` и `RAG_THRESHOLD`
обязательны — умолчания порога в коде нет. Пустой итог — строка
`В базе не нашлось достаточно близкого (режим <режим>, порог <порог>).`

## Шаг 2. Второй этап поиска и переписывание запроса

**Файлы**: `rag/rerank.py`, `rag/rewrite.py`, `rag/pyproject.toml`, `rag/check_rag.py`
**Зависит от**: ничего
**Ход**: полный, потому что `Поиск` читают сервер (шаг 3) и сравнение (шаг 4) за границей
файлов шага.
**Требование**: не про myharness
**Проверка**: `uv run --project rag rag/check_rag.py` — новые проверки на поддельных векторах и
поддельном оценщике: порядок и отсечение каждого режима; `base` = косинус дня 22 байт в байт на
том же вопросе; объединение кандидатов с переписанным без повторов, `кандидатов` ≤ 2·K₁;
парная проверка порога (кусок ровно на пороге проходит, на 0,001 ниже — нет); `переписать` на
`httpx2.MockTransport` — тело запроса и отсутствие ключа в тексте ошибки. Затем живьём:
`uv run --project rag python -c` на одном вопросе в режиме `model` — кодировщик загрузился на
`mps`, счёт в (0, 1).
**Содержание**: BM25 — своя реализация (k1 = 1,2, b = 0,75 — умолчания Lucene/Elasticsearch)
по словам, приведённым к основе `snowballstemmer` (русский, затем английский); слова —
`[\w-]+` без учёта регистра, так `top_k` и `SEP-2577` остаются целыми. Кодировщик —
`sentence_transformers.CrossEncoder("BAAI/bge-reranker-v2-m3", device="mps" если доступно,
иначе "cpu")`, вероятность — `activation_fn=Sigmoid`.

**Зависит от**: шаг 2

**Требование**: не про myharness
**Проверка**: проверки сервера — окружение каждого режима, отказ без `RAG_K1`/`RAG_THRESHOLD`,

**Содержание**: `Поиск` создаётся один раз на процесс сервера; `найти_текст` получает режим и
числа доводами, окружение читает только точка входа.

## Шаг 4. Сравнение поиска: сетка K₁ × K₂, пороги, «до / после»

**Файлы**: `rag/rerank_compare.py`, `rag/cli.py`, `rag/check_rag.py`
**Зависит от**: шаги 1, 2
**Ход**: быстрый: читатель отчёта — человек.
**Требование**: не про myharness
**Проверка**: `rag/cli.py rerank-compare --out <песочница>/поиск.md` на настоящем индексе;
проверка на поддельных данных — мера «отсечено начисто» для `base` всегда 0.
**Содержание**: наборы — `control.jsonl` (подбор) и `answers.jsonl` (проверка; попадание —
кусок из `источники`), `negative.jsonl` по полю `часть`. Переписывание — один раз на вопрос,
тексты переписанных — в отчёте. Разделы: (1) сетка K₁ ∈ {5, 10, 20, 30, 50} × K₂ ∈ {3, 5, 10}
по 8 вариантам (4 режима × переписывание); (2) перебор порогов для `threshold`/`heuristic`
(косинус) и `model` (вероятность): доля потерянных попаданий против доли отрицательных,
отсечённых начисто, — на части «подбор»; (3) выбранные K₁, K₂, τ, θ с причиной и итог на части
«проверка»: hit@1, hit@K₂, MRR, средние «кандидатов / прошло / отдано», доля отрицательных,
отсечённых начисто; (4) по вопросам. Выбранные числа идут в `.mcp.json` дня (шаг 6).

## Шаг 5. Сравнение ответов по списку режимов и мера отказа

**Файлы**: `rag/eval.py`, `rag/check_rag.py`
**Зависит от**: шаг 1
**Ход**: быстрый: вход — журнал `myharness`, формат которого не меняется; день 22 остаётся
воспроизводимым (имена `q<NN>-plain|rag` — частный случай).
**Требование**: не про myharness
**Проверка**: проверки `eval` на поддельном журнале: режимы из имён заданий, отрицательные
вопросы, отказ; старые проверки дня 22 проходят без правки.
**Содержание**: имя задания `q<NN>-<режим>` (вопрос `answers.jsonl`) или `n<NN>-<режим>`
(вопрос `negative.jsonl`), режимы — из журнала в порядке первой встречи. Отказ — ответ
начинается словами «В базе нет ответа» (без учёта регистра и знаков): на отрицательном вопросе
это верно, на обычном — ложный отказ. Таблица: режим × (доля фактов, полных ответов, источник
найден, верных отказов из 5, ложных отказов из 10, токенов).
