# Дизайн: стадия проверки спецификаций на противоречия

## Задача и видение

Решение пользователя 2026-09-16: добавить в конвейер разработки стадию проверки спецификаций на
противоречивость требований, двумя рубежами — после `Plan` и после `Executing`.

Повод — день 13. Требования правились шагами `Executing`, каждый шаг просматривался по своему
шву, и противоречия между способностями оставались незамеченными:
- `commands` говорил «этап переводит только человек», а `task-machine` — «модель двигает стадии»;
- `commands` говорил «команда принимает любое слово», хотя рядом стоял отказ по карте;
- `memory` говорил «любой ручной этап снимает ворота», хотя равный этап их не трогает.

Два из них нашёл только итоговый просмотр связности, одно — просмотр шага. `openspec validate
--specs --strict` проверяет форму — заголовки, `SHALL`, сценарии, — но не смысл.

## Что решили и почему

### Р1. Одна стадия `Spec`, два входа

Новая стадия — `Spec` (проверка требований), навык `/требования`. Вход в неё — из `Plan` и из
`Executing`, и что именно проверяется, решает то, откуда пришли:

```
Research   → Plan | Executing
Plan       → Spec
Spec       → Executing | Validation | Plan | Research
Executing  → Spec | Research
Validation → Report | Executing | Research
Report     → Done
```

- **Первый рубеж (после `Plan`)** — проверяются ЗАМЫСЛЕННЫЕ изменения требований: план обязан
  нести раздел «Изменения требований» — по каждой задетой способности, какое требование
  появляется или меняется и что оно будет говорить одной-двумя фразами. Проверяющий сверяет это с
  действующими `openspec/specs/*`. Выход — в `Executing`; нашлось противоречие — назад в `Plan`
  (или в `Research`, если противоречие в самом замысле).
- **Второй рубеж (после `Executing`)** — проверяется НАПИСАННОЕ: `git diff` по
  `openspec/specs/` от исходной точки задачи плюс требования, которые ссылаются на задетые
  способности. Выход — в `Validation`; нашлось — назад в `Executing`.

`Research → Executing` без плана остаётся для мелочей; такая задача проходит только второй рубеж.

Отвергнуто: две разные стадии с разными именами — переходов вдвое больше, а процедура одна.
Отвергнуто: проверка внутри `Validation` — итоговый просмотр смотрит связность кода, и противоречия
в требованиях там тонут; к тому же первый рубеж без отдельной стадии некуда поставить.

### Р2. Что считается противоречием

Проверяющий ищет:
1. прямое противоречие — два требования предписывают несовместимое в одном положении;
2. устаревшую оговорку — текст, отменённый новым требованием, но оставшийся («сегодня карты нет»);
3. разный смысл одного слова или значения между способностями (`None` против пустого списка);
4. висящую ссылку — на способность или требование, которого нет;
5. на втором рубеже — расхождение написанного с планом (требование ушло в сторону без записи).

Расхождение требования с КОДОМ — дело итогового просмотра `Validation`, не этой стадии.

### Р3. Кто и чем

Одно поручение независимому проверяющему на `opus` (`general-purpose` в Claude Code, `reviewer`
на Sol в OMP): это суждение, дешёвой модели его не отдают. Проверяющий получает раздел плана или
срез спецификаций и список соседних способностей, а возвращает находки с `файл:строка`. Круг
«замечание → исправление → повторный просмотр» — как в `Executing`. Вердикт — строкой в файле
состояния задачи и в сообщении фиксации.

### Р4. Соразмерность

Задача, не меняющая требований `myharness` (правка навыков, документации), проходит стадию одной
строкой: «требований не задевает» — без проверяющего. Первый рубеж без раздела «Изменения
требований» в плане не проходится: раздел обязателен, даже если он говорит «не задевает».

## Затронутые файлы

- `CLAUDE.md` — перечень стадий, карта переходов, список навыков.
- `.claude/skills/требования/SKILL.md` — новый навык стадии.
- `.claude/skills/задание/SKILL.md` — схема конвейера и таблица ролей.
- `.claude/skills/план/SKILL.md` — раздел «Изменения требований», самопроверка, передача в `Spec`.
- `.claude/skills/исполнение/SKILL.md` — конец стадии: `Executing → Spec`.
- `.claude/skills/проверка/SKILL.md` — условие начала: второй рубеж пройден.
- `openspec/` не меняется: это правка процесса, а не поведения `myharness`.

## Границы и риски

НЕ делаем: перевод задач на дельты `openspec/changes/` — план остаётся носителем замысла.
Не делаем машинной проверки смысла: её нет у образцов (Claude Code, Codex, Hermes такой стадии не
имеют; OpenSpec проверяет только форму).

Цена: два поручения проверяющему на задачу, по 0,1–0,2 млн токенов; для задачи без требований —
ноль. Риск: первый рубеж проверяет пересказ, а не текст, и пропустит то, что появится по ходу, —
ради этого и второй рубеж.
