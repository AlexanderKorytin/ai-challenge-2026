# Дизайн: утилита калорий и гликемического индекса (день 27)

## Задача и видение

Условие дня 27: встроить местную языковую модель в настоящее приложение. Приложение шлёт запросы
местной модели, показывает ответы и работает без облачных моделей.

Видение пользователя: утилита командной строки. Она работает в двух направлениях:

- название блюда → калорийность и гликемический индекс (дальше — ГИ);
- число килокалорий → список блюд с их ГИ.

## Что решили и почему

**Отдельная утилита `калории`, а не режим `myharness`.** Условие просит приложение, в которое
встроена модель. `myharness` — клиент разговора с моделью, день 26 его уже показал. Утилита живёт
в папке дня `week_6/day_2/` своим проектом `uv`. Код `myharness` не меняется.

**Числа называет модель** (решение пользователя 2026-10-06). Утилита помечает каждое число словом
«оценка». Ошибку модели показывает замер на контрольном наборе. Отвергнута справочная таблица:
она точна, но блюдо вне таблицы утилита не знает. Отвергнута связка «таблица, затем модель»:
объём работы равен сумме двух подходов.

**Модель — `qwen3.5:9b-q4_K_M-32k`, рассуждения выключены.** Замер 2026-10-06 на шести блюдах:
ответ за 1,6–1,8 с, первый запрос 7,4 с. Пять блюд из шести названы верно, у картофельного пюре
ГИ занижен (65 против 80–90). Имя модели меняет переменная окружения `CALORIES_MODEL`.

**Обмен — родной API службы Ollama, `POST /api/chat`.** Довод `format` принимает схему JSON, и
служба не даёт модели выйти за схему. Довод `think: false` выключает рассуждения. У пути `/v1`
обоих доводов в таком виде нет. Клиент — `httpx`, адрес службы — `http://127.0.0.1:11434`,
меняет его переменная `OLLAMA_HOST` (то же имя, что у самой Ollama).

**Арифметику считает программа, а не модель.** Модель называет три числа: килокалории на 100 г,
ГИ и вес обычной порции в граммах. Калорийность порции программа получает умножением. Так
модель не ошибётся в счёте.

**Прямое направление.** `калории "борщ со свининой"` печатает: калорийность на 100 г, порцию в
граммах, калорийность порции, ГИ и его разряд (низкий до 55, средний 56–69, высокий от 70 —
общепринятые границы). В схеме есть поле `еда`: на ввод «табуретка» модель ставит `false`, и
утилита отвечает «не знаю такого блюда».

**Обратное направление.** `калории 450` просит у модели блюда, порция которых даёт около 450
ккал. Программа пересчитывает калорийность каждой порции сама, показывает отклонение от
запрошенного и сортирует список по отклонению. Блюда программа не отбрасывает: порога
отклонения нет, человек видит отклонение сам. Число блюд задаёт ключ `--блюд`, умолчание — 5.

**Проверка ответа модели.** Программа отвергает физически невозможные числа: калорийность на
100 г выше 900 (столько даёт чистый жир) и отрицательные значения. ГИ сверху не ограничен: у
части продуктов он выше 100. На отвергнутый ответ утилита пишет причину и числа не показывает.

**Без доводов утилита ведёт разговор**: читает строку, отвечает, ждёт следующую. Строка из
одного числа идёт в обратное направление, прочие — в прямое.

**Отказы службы.** Служба не отвечает — утилита пишет, как её запустить, и выходит с кодом 1.
Модели нет в службе — утилита называет команду `ollama pull`. Своих пределов ожидания утилита
не заводит.

**Замер точности.** Файл `контроль.jsonl`: 20–30 блюд со справочными числами. Калорийность — из
таблиц химического состава Скурихина, ГИ — из международных таблиц (Atkinson и др., 2021).
Каждая строка называет источник. Команда `калории --замер` прогоняет набор и печатает: среднюю
ошибку калорийности в процентах, среднюю ошибку ГИ в единицах и долю блюд с верным разрядом ГИ.
Итог идёт в README дня.

**Работа без облака.** У утилиты один адрес — местная служба. Проверка сверяет, что клиент не
знает других адресов. На видео утилита отвечает при выключенной сети.

## Затронутые способности

Нет. Требования `openspec/specs/` описывают `myharness`, он не меняется. Стадия `Spec` сведётся
к этой отметке.

## Границы

Делаем: утилиту двух направлений, разговорный режим, замер точности, проверки без службы
(поддельный ответ службы), README дня, видеоотчёт.

Не делаем: справочную таблицу в составе утилиты, дневник питания, счёт белков, жиров и
углеводов, разбор блюда на составные части, телеграм-бот и веб-страницу.

## Риски и чем расплачиваемся

- **Число модели — оценка, а не справка.** ГИ читают люди с диабетом. Утилита пишет слово
  «оценка» у каждого числа и строку «не для врачебных решений». README называет измеренную
  ошибку.
- **ГИ блюда зависит от способа готовки и состава.** Справочники дают диапазон. Замер считает
  разряд, а не только точное число.
- **Обратное направление модель может исполнить плохо**: назвать блюда далеко от запрошенных
  калорий. Отклонение видно в выводе; долю попаданий назовёт живой прогон.
- **Ответ модели не повторяется** от запуска к запуску. Температура 0 это сглаживает, но не
  устраняет (наблюдение дня 24).

## Уточнения по ходу исполнения (2026-10-06)

Живой прогон и просмотр шва изменили пять решений. Причины — в `docs/состояние-калории.md`.

- **Подбор по килокалориям идёт в два этапа.** Модель называет только имена блюд, втрое больше
  просимого. Каждое имя идёт отдельным запросом в оценку блюда; этот запрос цели не знает.
  Подбор одним запросом отвергнут: модель подгоняла вес порции под число.
- **Утилита шлёт запросы только на этот компьютер** (решение пользователя). Адрес другой машины
  в `OLLAMA_HOST` даёт отказ. Клиент не читает посредника из окружения.
- **Калорийность 0 допустима**: вода, чай без сахара. Отвергаются отрицательные числа и числа
  выше 900.
- **Источник ГИ контрольного набора** — Atkinson и др., 2008, Table 1; калорийность — USDA.
- **Работу без облака доказывает песочница**, а не выключенная сеть: `test/без-сети.sh`
  разрешает соединения только на этот компьютер. Сеть ведущий выключить не может: он сам
  работает через неё.
