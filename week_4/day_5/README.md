# День 20. Оркестрация MCP

## Постановка

Зарегистрировать несколько MCP-серверов. Агент выбирает нужный инструмент, корректно
маршрутизирует запросы и выполняет длинную цепочку взаимодействия. Проверить сценарий с
инструментами разных серверов и корректность выбора и порядка вызовов.

Дизайн — `docs/оркестрация-mcp.md`, план — `docs/план-оркестрация-mcp.md` (ветка `main`).

## Сценарий: справка по юаню

Одна просьба человека:

> Подготовь справку по китайскому юаню: курс ЦБ на сегодня и как он менялся за последний месяц,
> и что о юане пишет Википедия. Выжимку статей сохрани отдельным файлом, а сводную справку с
> цифрами ЦБ и выводами положи в справки/. Всё зафиксируй в git.

| Сервер | Где | Что даёт модели |
|---|---|---|
| `cbr` | наш, VPS `188.120.230.58`, HTTPS с токеном | `get_rate`, `get_rate_dynamics` |
| `pipeline` | наш, местный stdio (день 19) | `search` → `summarize` → `saveToFile` |
| `filesystem` | официальный `@modelcontextprotocol/server-filesystem@2026.8.31` | `write_file`, чтение каталога |
| `git` | официальный `mcp-server-git==2026.8.18`, `--repository` | `git_status`, `git_add`, `git_commit`, `git_log` |

Данные между серверами переносит модель: курс и динамика ЦБ и выжимка Википедии сходятся в
тексте справки, путь выжимки от `saveToFile` и путь справки от `write_file` — в доводах
`git_add`.

**Развилка выбора.** Файлы пишут два сервера: `saveToFile` принимает только ссылку на выжимку,
`write_file` — любой текст. Профиль не говорит, какой для чего: модель различает их по описаниям.

## Как маршрутизация устроена

Код `myharness` не менялся: он уже умеет несколько серверов. Каждый инструмент уходит модели
под именем `mcp__<сервер>__<инструмент>`, и вызов по этому имени находит своё соединение.
Параллель с JVM: несколько бинов одного интерфейса, нужный выбирается квалификатором —
здесь квалификатор вписан прямо в имя. Поэтому ошибки «маршрута» отдельно от ошибки выбора не
бывает: выбрав имя, модель выбрала и сервер. Проверять значит проверять выбор модели.

## Безопасность

- Песочница `test/справки/` — **свой** репозиторий git (не репозиторий челленджа). Сервер `git`
  видит только его (`--repository`), а `filesystem` и `pipeline` пишут только в `справки/файлы/`,
  где нет `.git`. Будь им открыт корень репозитория, модель по указанию из выжимки могла бы
  переписать `.git/config` (`core.fsmonitor`), и ближайший `git_status` исполнил бы чужую команду
  на Маке — находка независимого просмотра.
  Вторая опора той же защиты — `create_directory` не разрешён: без него модель не заведёт в
  `файлы/` вложенный `.git` со своими настройками. Разрешать его — только пересмотрев корни.
- Фиксации в песочнице подписывает «песочница» (`git config` репозитория), а не глобальный адрес
  владельца.
- Модели предлагаются 13 инструментов точными именами (`test/.claude/settings.json`); запрещены
  `edit_file`, `move_file`, `git_reset`, `git_checkout`, `git_create_branch` и `git_diff`
  (CVE-2025-68144). Серверы их объявляют, но модель их не видит.
- Остаточный риск: указание, пережившее выжимку Википедии, может заставить модель записать и
  зафиксировать мусор — только внутри песочницы, видно по `git log`.
- Поведение `myharness`, не песочницы: местные серверы наследуют окружение целиком, вместе с
  `CBR_MCP_TOKEN`. Модели он не виден, в журнал не попадает.

## Проверка выбора и порядка — `след.py`

Читает последний обмен с вызовами из `myharness-journal.jsonl` и сверяет:

1. **выбор** — вызваны все восемь нужных инструментов на своих серверах, посторонних нет;
2. **порядок** — только причинные рёбра (`search → summarize → saveToFile`, всё нужное справке →
   `write_file`, оба файла → `git_add → git_commit`), а не точная последовательность;
3. **перенос** — `search_id` и `summary_id` взяты из предыдущих ответов, `git_add` взял оба файла,
   курс ЦБ стоит в тексте справки;
4. **итог** — фиксация прошла, её хэш назван в ответе.

Справкой считается последняя запись `write_file`, вошедшая в фиксацию; добавленное — объединение
всех `git_add` до фиксации, каталог покрывает всё под ним. Сверяется последний обмен с вызовами —
запускать сразу после прогона (или `--run-id`). Не сверяется: цифры динамики в тексте справки.
Один прогон проверяется, устойчивость на многих — нет.

## Живой прогон 2026-09-25

Первый прогон — 13 вызовов, «ВСЁ СОШЛОСЬ»; после него корни серверов разнесены (см.
«Безопасность»), и прогон повторён.

Второй прогон — 18 вызовов на четырёх серверах: `list_allowed_directories` → `get_rate` →
`search` → `get_rate_dynamics` → `summarize` → `list_directory` ✗ → `list_directory` →
`git_status` ✗ ✗ → `git_status` → `git_log` → `saveToFile` → `read_text_file` → `write_file` →
`git_status` → `git_add ["файлы"]` → `git_commit` → `git_status`. Модель трижды промахнулась
путём (корень `filesystem` теперь уже репозитория), получила «ошибку инструмента» и сама нашла
верный — без повтора тех же доводов. `search` снова раньше `get_rate_dynamics` — частичный
порядок это допускает. `след.py` — «ВСЁ СОШЛОСЬ».

`след.py` проверен и на подложенных копиях записи: без `git_commit` — провал, код 1; файлы
добавлены двумя `git_add` по одному — «ВСЁ СОШЛОСЬ»; запуск из чужого каталога — то же.
