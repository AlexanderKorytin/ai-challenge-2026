# День 18. Планировщик и фоновые задачи

**Стадия: Executing.**
Код — в `main`: сервер `mcp_servers/cbr/` (`store.py`, `scheduler.py`, `server.py`). Здесь
постановка, песочница и видеоотчёт.

## Условие

Сделать MCP-инструмент с отложенным или периодическим выполнением (напоминание, периодический
сбор данных, регулярная сводка). Инструмент должен сохранять данные (JSON или SQLite),
выполняться по расписанию и возвращать агрегированный результат.

## Видение пользователя

Построить на сервере курсов ЦБ из дня 17.

## Что решили

Дизайн — `docs/планировщик.md` в `main`, план — `docs/план-планировщик.md`, ход и вердикты —
`docs/состояние-планировщик.md`.

- **Периодический сбор курсов со сводкой.** Модель по просьбе человека заводит задание, а сервер
  сам, без клиента и без модели, ходит в ЦБ по расписанию и складывает курсы в SQLite.
- **Планировщик живёт в процессе службы** на VPS: задача `asyncio` рядом с сервером MCP спит до
  ближайшего срока. Параллель с JVM — `@Scheduled` внутри того же Spring-приложения.
  - Расписание — выражение cron из пяти полей по московскому времени, как у `CronCreate` в
    Claude Code. Следующий срок считает библиотека `croniter`.
  - Пропущенные сроки после простоя службы — один запуск, а не пачка, как у `anacron`.
  - Один запрос к ЦБ на запуск, сколько бы валют ни было. Курс хранится один раз на пару
    «валюта + дата установления», поэтому лишний запуск ничего не портит.
- **Хранилище — SQLite** `/var/lib/cbr-mcp/cbr.sqlite3`: задания, журнал запусков, курсы.
- **Четыре новых инструмента** рядом с `get_rate` и `get_rate_dynamics`:

  | Инструмент | Что делает |
  |---|---|
  | `schedule_collect(currencies, cron)` | заводит сбор, отвечает ближайшим сроком |
  | `list_schedules()` | задания, сроки, удачные и неудачные запуски, последняя ошибка |
  | `delete_schedule(job_id)` | снимает задание; собранное остаётся |
  | `get_summary(currency, date_from?, date_to?)` | **агрегированный результат**: число курсов, изменение в рублях и процентах, минимум и максимум с датами, среднее |

- `myharness` не менялся: мост дня 17 отдаёт модели новые инструменты сам.

## Переезд сервера по ходу дня

С Мака прямые соединения к прежнему VPS `38.180.117.69` замерзали через 2–9 обменов. С самого
сервера всё проходило, `tcpdump` показал ответ сервера без подтверждения от Мака: поток глушится
на пути. `myharness` держит одно соединение весь сеанс и замерзал бы на втором-третьем вызове.
Сначала служба переехала на `83.136.235.149` (FirstVDS, nginx панели), а когда пользователь
заказал чистый сервер, — на `188.120.230.58`: Ubuntu 24 без панели, Caddy с сертификатом Let's
Encrypt на IP, вход `https://188.120.230.58/mcp`. База с рабочим заданием переехала копией файла.
